# Термины и определения

| Реквизит | Значение |
|---|---|
| Обозначение | ТРМ |
| Версия | 1.0 |
| Состояние | Действует |
| Автор | Письмеров Кирилл |
| Категория контроля | КК1 |

## 1. Назначение

Документ — единый список терминов и сокращений всех правил команды. Каждый участник знает эти определения. Если термин в другом документе расходится с этим списком, действует этот список, а расхождение регистрируется сообщением о проблеме.

## 2. Документы правил

| Сокращение | Документ | Назначение |
|---|---|---|
| ПРК | Правила работы команды | Роли, замещение, сквозная схема работы, порядок изменения правил |
| ПЛР | План разработки | Этапы: вход, работы, выход, проверка, условие завершения |
| ПКУ | План управления конфигурацией | Где что лежит, как обозначается, по какой категории контроля меняется |
| ПВР | План верификации | Что, когда, каким методом и кем проверяется; чем подтверждается принятие |
| ПФИ | Процедура формальной инспекции | Роли, вход, шаги и решение инспекции |
| ЧЛ-БТ | Чек-лист инспекции постановки задачи | Вопросы «да/нет» для постановки и её разделов |
| СТТ | Стандарт разработки требований | Как формулировать, нумеровать и связывать требования |
| СОД | Стандарт оформления документов | Формат, имена, реквизиты, состояния, версии |
| ТРМ | Термины и определения | Этот документ |
| Ш-ДОК, Ш-ПИ | Шаблон документа, шаблон протокола инспекции | Образцы для нового документа и протокола |

## 3. Управление конфигурацией

| Термин | Определение |
|---|---|
| Правила игры | Документы каталога `process/`: правила, планы, процедура, стандарты, чек-листы, шаблоны, термины. Описывают процесс без привязки к теме проекта |
| Документ разработки | Результат этапа: постановка задачи и её разделы, системные требования, требования к ПО, проект, код |
| Единица конфигурации | Файл или задача, которой управляют отдельно. Определяется парой «уникальное имя, версия» |
| Версия | Номер редакции документа в его реквизитах: 0.N у черновика, 1.0 у принятого или введённого в действие документа, далее 1.1, 1.2 |
| Лист изменений | Последний раздел документа: по строке на каждую версию с автором и содержанием изменения |
| Категория контроля | Строгость правил изменения объекта. Категорий две: КК1 и КК2 |
| КК1 | Категория контроля 1: объект изменяется только по формально описанной процедуре. Относятся принятые документы разработки (процедура — ПКУ, раздел 7) и действующие правила (процедура — ПРК, раздел 7) |
| КК2 | Категория контроля 2: объект после создания не изменяется. Относятся протоколы, отчёты анализа, описания СП и ЗИ. Ошибка исправляется новым объектом с новым номером |
| Базовая версия | Зафиксированный набор принятых документов и действующих правил на контрольную точку. Метка Git `baseline-N`; состав не меняется |
| СП | Сообщение о проблеме: задача в Issues с фактами «как должно быть, как есть», без способа решения. Регистрирует любой участник |
| Анализ СП | Оценка автором документа: где ошибка, на что влияет, сколько стоит исправление |
| ЗИ | Запрос на изменение: задача в Issues с перечнем того, что именно меняется и в каких единицах конфигурации. Создаётся по итогам анализа СП |
| Запрос на объединение | Предложение влить ветку автора в основную ветку. Рассматривает и одобряет участник, не являющийся автором |

## 4. Состояния документа

| Состояние | Определение |
|---|---|
| Черновик | Документ разработки до принятия. Автор изменяет его без процедуры |
| Готов к инспекции | Не отдельное состояние документа: автор зафиксировал проверяемую версию и перевёл задачу в состояние «на проверке». До конца инспекции документ не изменяется |
| Принят | Документ разработки прошёл итоговую инспекцию: протокол без замечаний, с заключением «принять» и подписями. С этого момента документ относится к КК1. Соответствует понятию «утверждён» |
| Действует | Правило, запрос на объединение которого одобрен участником, не являющимся автором изменения. Относится к КК1 |

## 5. Верификация

| Термин | Определение |
|---|---|
| Верификация | Проверка результата на соответствие требованиям и правилам. Находит и регистрирует несоответствия; исправляет их автор |
| Рассмотрение | Метод верификации: качественная оценка по контрольным вопросам. Виды — формальная инспекция и рассмотрение запроса на объединение |
| Анализ | Метод верификации: исследование количественных свойств, например полноты покрытия. Результат выражен числом и воспроизводим |
| Испытание | Метод верификации: исполнение программы и фиксация фактического поведения |
| Формальная инспекция | Рассмотрение документа по чек-листу по записанной процедуре (ПФИ) с распределёнными ролями и протоколом |
| Предварительная инспекция | Инспекция, в том числе автоматизированная, по тому же чек-листу. Помогает автору найти недостатки; документ по ней не принимается |
| Итоговая инспекция | Инспекция назначенным инспектором-участником. Только её протокол может быть основанием для принятия |
| Повторная инспекция | Инспекция исправленного документа новым протоколом со ссылкой на прежний. Проверяется весь чек-лист |
| Чек-лист | Перечень вопросов с ответом «да» или «нет» для одного вида документа |
| ПИ | Протокол инспекции: ответы по чек-листу с основаниями, замечания, заключение, подписи. Обозначение ПИ-<КОД>-NN. КК2 |
| Замечание | Запись в протоколе к ответу «нет»: место, как есть, как должно быть. Способ исправления не указывается |
| Заключение | Решение инспекции: «принять» — все ответы «да»; «доработать» — есть хотя бы один ответ «нет» |
| АП | Отчёт анализа покрытия: что сопоставлено, число покрытых элементов, перечень непокрытых и лишних, заключение. КК2 |
| Покрытие | Каждый элемент верхнего уровня уточнён хотя бы одним элементом нижнего уровня, и у каждого элемента нижнего уровня есть источник наверху |
| Независимость проверки | Автор не проверяет собственную работу: не бывает инспектором, исполнителем анализа и рассматривающим своего запроса на объединение |

## 6. Роли

| Роль | Определение |
|---|---|
| Автор | Участник, создавший документ. Передаёт его на проверку и исправляет замечания |
| Инспектор | Участник, не являющийся автором. Отвечает на вопросы чек-листа и регистрирует замечания |
| Ведущий инспекции | Назначает инспектора, следит за процедурой, оформляет и подписывает протокол |
| Служба качества | Проверяет формальную сторону: шаблон, реквизиты, именование, место хранения |
| Руководитель проекта | Планирует работу на две недели, распределяет задачи, ведёт разбор задач |
| Заместитель | Выполняет обязанности отсутствующего участника по ПРК, раздел 6 |

## 7. Требования

| Термин | Определение |
|---|---|
| Постановка задачи (ПЗ) | Документ этапа 1: проблема заказчика, задачи заказчика, границы системы, разделы по направлениям |
| Раздел постановки (ПЗ-<КОД>) | Часть постановки по одному направлению: проблема, бизнес-требования, границы, готовые решения, вопросы к заказчику |
| Задача заказчика (З-NN) | Задача, которую заказчик назвал на семинаре. Источник бизнес-требований |
| Бизнес-требование (БТ-<КОД>-NN) | Возможность, которую система должна дать заказчику. Ссылается на задачу заказчика |
| Источник | Элемент верхнего уровня, из которого следует требование |
| Производное требование | Требование без источника наверху, введённое по решению команды. Помечается отдельно (СТТ) |
