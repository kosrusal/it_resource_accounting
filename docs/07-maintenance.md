# 07. Регламентные работы

## 7.1 Назначение и границы

Подсистема регламентных работ предназначена для планирования и учёта обслуживания
ИТ-ресурсов организации. Она хранит сроки, исполнителей и результаты работ,
определяет потенциально затронутые ресурсы, обеспечивает согласование и оповещение.
Наряду с плановым обслуживанием подсистема учитывает аварийные работы.

**Окно работ** — запись о конкретном выполнении работ. **Плановый интервал** — время,
отведённое для их выполнения. Эти понятия не тождественны: окно работ содержит также
состав ресурсов, согласования и фактический результат.

**Шаблон регламентных работ** задаёт повторяющееся обслуживание. По шаблону создаются
отдельные окна работ, каждое со своей историей. Примеры: обновление операционной
системы, проверка восстановления из резервной копии, замена сертификата.

Заявка (`Request`) фиксирует обращение сотрудника, например о выдаче ресурса. Окно
работ (`MaintenanceWindow`) фиксирует обслуживание ресурсов. Общий механизм
согласования используется для обоих объектов, но их состояния не отождествляются.

Система не выполняет технические действия над ресурсами, не проверяет их доступность
и не восстанавливает прежнюю конфигурацию. Начало, результат проверки и завершение
работ подтверждает человек. Этот раздел содержит предметные правила, проектные
решения и сценарии будущей приёмки. Начальная редакция проверяемых требований
выделена в [системные требования](requirements/system.md) и
[требования к ПО](requirements/software.md); программной реализации пока нет.

## 7.2 Данные

### Окно работ — `MaintenanceWindow`

| Поле | Назначение |
|---|---|
| `id`, `title` | Идентификатор и название работ |
| `description` | Цель, действия, способ проверки результата и порядок восстановления прежней конфигурации, если такое восстановление предусмотрено |
| `urgency` | Срочность: плановые (`planned`) или аварийные (`emergency`) работы |
| `state` | Состояние выполнения по §7.3 |
| `planned_start`, `planned_end`, `time_zone` | Плановый интервал и часовой пояс его представления |
| `actual_start`, `actual_end` | Фактическое начало и окончание; до соответствующего действия отсутствуют |
| `executor_id` | Ответственный исполнитель с ролью `it_specialist` или `it_admin` |
| `org_unit_id` | Подразделение-инициатор: для разовых работ определяется по создателю, для повторяемых — по шаблону; впоследствии не меняется |
| `expected_downtime` | Ожидается ли недоступность ресурсов; это оценка исполнителя, а не измерение |
| `template_id`, `template_revision`, `occurrence_at` | Шаблон, его редакция и неизменный момент по расписанию; для разовых работ отсутствуют |
| `requires_approval`, `approval_state` | Необходимость согласования и состояние решения по §7.5 |
| `approval_route_id` | Ссылка на маршрут общего механизма согласования |
| `plan_revision`, `version` | Редакция плана и версия записи для защиты от одновременного изменения |
| `result`, `result_comment` | Общий результат и пояснение; заполняются при завершении |
| `emergency_reason` | Причина аварийного начала без предварительного согласования |
| `created_by`, `created_at`, `updated_at` | Автор и время создания и изменения записи |

До начала работ номер редакции плана увеличивается при изменении цели, действий,
сроков, исполнителя, срочности, состава ресурсов или ожидаемой недоступности.
Версия записи увеличивается при любом изменении, в том числе при принятии решения
о согласовании.
Ссылка на внешнюю задачу хранится в `TrackerLink`, а не дублируется в окне работ.

### Ресурс работ — `MaintenanceResource`

Связь окна с ресурсом содержит следующие поля:

| Поле | Назначение |
|---|---|
| `maintenance_id`, `resource_id` | Окно и ресурс; пара идентификаторов уникальна |
| `prev_status` | Учётное состояние ресурса непосредственно перед началом этого окна |
| `previous_maintenance_id` | Предыдущее завершённое окно обслуживания того же ресурса; заполняется по правилам §7.3 |
| `restore_status` | Состояние до начала непрерывного пребывания ресурса в `maintenance`, если оно подтверждено историей |
| `result`, `result_comment`, `status_after` | Результат, пояснение и итоговое состояние этого ресурса |

Поля `prev_status`, `previous_maintenance_id` и `restore_status` определяет система
при подтверждении начала. До начала они пусты, после начала не изменяются.
Связь с предыдущими работами устанавливается для каждого ресурса отдельно:
у ресурсов одного окна может быть разная история обслуживания.

### Шаблон — `MaintenanceTemplate`

Шаблон содержит название, описание, ресурсы, исполнителя, подразделение-инициатора,
признак ожидаемой недоступности, расписание `recurrence`, часовой пояс `time_zone`,
плановую длительность `duration`, срок предварительного создания `lead_time`,
признак активности `enabled` и номер редакции. Подразделение-инициатор определяется
по создателю шаблона. `duration` и `lead_time` задаются целым числом минут.
Правила повторения приведены в §7.8.
Повторяемость не является значением срочности: созданные по шаблону работы плановые.

### История расчётов и решений

Для каждой редакции плана сохраняются результаты расчёта затронутых ресурсов:
время расчёта, исходные ресурсы, найденные связи, владельцы, подразделения,
критичность, среда использования, полнота расчёта и причина его ограничения.
Решение согласующего ссылается на редакцию плана и результат расчёта.

В журнале изменений сохраняются автор, время, действие, прежние и новые значения,
основания исключений и результаты по ресурсам. Прежние редакции и решения
не заменяются новыми. Сведения о получателях и доставке хранит подсистема оповещений.

## 7.3 Состояния, начало и завершение

### Переходы окна работ

| Исходное состояние | Следующее состояние | Условие |
|---|---|---|
| Черновик (`draft`) | На согласовании (`pending_approval`) | Плановые работы требуют предварительного согласования |
| Черновик (`draft`) | Запланировано (`scheduled`) | Плановые работы не требуют согласования; проверки плана пройдены |
| На согласовании (`pending_approval`) | Запланировано (`scheduled`) | Все обязательные решения по текущей редакции положительные либо после изменения плана согласование больше не требуется |
| На согласовании (`pending_approval`) | Отклонено (`rejected`) | Получено отрицательное решение по плановым работам |
| Запланировано (`scheduled`) | На согласовании (`pending_approval`) | Изменение плана или сведений о затронутых ресурсах требует нового согласования |
| Запланировано (`scheduled`) | Выполняется (`in_progress`) | Исполнитель подтвердил начало; проверки начала пройдены |
| Черновик, на согласовании, запланировано | Отменено (`cancelled`) | Работы ещё не начаты; указана причина отмены |
| Черновик, на согласовании, запланировано | Выполняется (`in_progress`) | Аварийное начало по §7.5; срочность и основание фиксируются вместе с началом |
| Выполняется (`in_progress`) | Завершено (`completed`) | Исполнитель указал результат и итоговое состояние каждого ресурса |

Состояния «завершено», «отклонено» и «отменено» конечные. Повторное выполнение
оформляется новым окном. После начала отмена недопустима: прекращение работ
фиксируется завершением с фактическим результатом. Неудачное выполнение работ
и восстановление прежней конфигурации учитываются как результаты, а не как состояния окна.

### Подтверждение начала

Для публикации плана и начала обязательны название, описание действий и проверки,
срочность, корректный плановый интервал, подразделение-инициатор, действующий исполнитель
и хотя бы один существующий ресурс работ. До заполнения этих данных допускается
только черновик. Аварийный порядок не отменяет эти требования.

Наступление планового срока не меняет состояние окна и ресурсов. Обычное начало
допускается в пределах планового интервала. Для начала вне него исполнитель сначала
изменяет план с повторной проверкой согласования либо применяется аварийный порядок.

При начале система повторно проверяет полномочия, согласование, актуальность расчёта,
состояния ресурсов и отсутствие других выполняемых окон над теми же ресурсами.
Допустимые исходные состояния ресурсов: `in_stock`, `in_use`, `returned`,
`maintenance`. Ресурс в этом состоянии можно включить в новое окно, если над ним
не выполняется другое окно. Для неназначаемых типов `returned` неприменимо
по [модели ресурсов](02-domain-model.md).

Для ресурсов работ сохраняется `prev_status` и устанавливается `maintenance`.
Если ресурс уже находится в `maintenance`, его состояние не меняется.
Зависимые ресурсы и соседи по серверу автоматически в обслуживание не переводятся.
Состояние обслуживания само по себе не означает недоступность.

### Состояние до обслуживания и повторные работы

Непрерывное пребывание в `maintenance` может включать несколько последовательно
выполняемых окон. Поле `prev_status` описывает начало текущего окна, а `restore_status`
сохраняет состояние до этого периода обслуживания.

Если при начале ресурс находится не в `maintenance`, система устанавливает
`restore_status = prev_status`; `previous_maintenance_id` остаётся пустым.

Если ресурс уже в `maintenance`, система находит последнее завершённое окно,
в котором он был ресурсом работ. Связь с ним допустима, только если его
`status_after = maintenance` и после завершения ресурс не выходил из этого состояния.
Непрерывность проверяется по журналу изменений. При выполнении этих условий
`previous_maintenance_id` ссылается на найденное окно, а `restore_status` копируется
из его записи `MaintenanceResource` для того же ресурса, в том числе если оно пусто.
Ссылка на другое, незавершённое или текущее окно недопустима.

При отсутствии такой записи или подтверждения непрерывности
`previous_maintenance_id` и `restore_status` остаются пустыми. Давнее состояние
из несвязанных работ не используется. Эти проверки и запись полей выполняются
в одной транзакции с началом. Попытка задать или изменить эти поля в запросе отклоняется.

Пример: ресурс ожидал приёмки (`returned`), но первые работы завершились неудачно,
и он остался в `maintenance`. Во вторых работах `prev_status = maintenance`,
а унаследованное `restore_status = returned`. После успешного завершения специалист
может вернуть ресурс в ожидание приёмки. Если между окнами ресурс выходил из
`maintenance`, прежнее основание возврата не наследуется.

### Результат по ресурсам

| Результат ресурса | Значение | Состояние после завершения |
|---|---|---|
| Успешно (`success`) | Предусмотренные действия выполнены; исполнитель проверил и подтвердил результат | Исполнитель подтверждает допустимое итоговое состояние |
| Частично (`partial`) | Выполнена только часть действий либо проверок | `maintenance`; обязательны описание оставшихся работ и причина |
| Неудачно (`failed`) | Цель не достигнута, восстановление не подтверждено | `maintenance`; обязательны причина и дальнейшее действие |
| Прежняя конфигурация восстановлена (`rolled_back`) | Изменения отменены, восстановление проверено исполнителем | Исполнитель подтверждает допустимое итоговое состояние |

При результатах `success` и `rolled_back` система предлагает `restore_status`,
если оно известно. Исполнитель подтверждает его либо выбирает другое допустимое
итоговое состояние. При пустом `restore_status` состояние выбирается явно;
неизвестное значение не заменяется состоянием из давних работ.

Каждый переход проверяется по общей модели ресурсов. В частности, переход в `in_use`
требует действующего владельца. Возврат в `returned` при завершении окна разрешён
только при `restore_status = returned`, установленном по правилам выше. Одного
`prev_status = maintenance` недостаточно ни для разрешения, ни для запрета такого
возврата. Состояние `returned` означает ожидание приёмки, а не приёмку на склад.
Это исключение закреплено в общей модели ресурсов. При результатах `partial`
и `failed` ресурс остаётся в `maintenance`, независимо от `restore_status`.

Если результаты всех ресурсов одинаковы, общий `result` равен этому результату.
Для разных результатов устанавливается `partial`; по общему результату нельзя
заключать, какие именно ресурсы восстановлены. Завершение окна не подтверждает
восстановление зависимых ресурсов. При отмене или отклонении до начала состояния
ресурсов не меняются, `actual_start`, `actual_end` и `result` остаются пустыми.

### Сроки и сохранение данных

Планировщик отдельно выявляет пропущенный срок начала у `scheduled` и превышение
срока окончания у `in_progress`. Просрочка согласования учитывается отдельно:
окно `pending_approval` не считается готовым к началу. Допуск просрочки задаётся
администратором; значение по умолчанию — ноль. Плановые сроки после начала
не изменяются, поэтому продление фактических работ не скрывает просрочку.

При начале и завершении состояние окна, фактическое время, изменения ресурсов,
записи журнала и исходящие события сохраняются в одной транзакции:
либо сохраняются все изменения, либо не сохраняется ни одно. Пока окно выполняется,
изменение состояний его ресурсов через другие операции, включая импорт, запрещено. После завершения дальнейшие изменения
выполняются по общей модели ресурсов и не переписывают результат прежних работ.

## 7.4 Определение затронутых ресурсов

Подсистема использует модуль графа, а не хранит собственную копию связей.
Расчёт определяет возможное влияние по известным связям; он не устанавливает
фактическую недоступность и не оценивает исправность резервных ресурсов.

| Группа | Правило получения | Назначение |
|---|---|---|
| Ресурсы работ | Явно выбраны исполнителем | Непосредственные объекты обслуживания |
| Зависимые ресурсы | Обратный обход связей `depends_on` и `hosted_on` от ресурсов работ | Возможное распространение недоступности |
| Соседи по серверу | Другие ресурсы, непосредственно размещённые на том же сервере или виртуальной машине, что и ресурс работ | Предупреждение о совместном использовании оборудования |

Связь `A depends_on B` означает, что ресурс `A` зависит от `B`. Поэтому при обслуживании
`B` нужно искать `A` против направления этой связи. Аналогично, при обслуживании сервера
находятся размещённые на нём ресурсы по обратным связям `hosted_on`, затем их
зависимые ресурсы. Обход повторяется до исчерпания достижимых узлов; посещённые узлы
не обрабатываются повторно. Для каждого результата сохраняется путь от ресурса работ.

Связи других типов автоматически не распространяют влияние. В частности, связь
`backup_of` не доказывает готовность резервной системы. Эта граница расчёта указывается
в интерфейсе. Соседство не является зависимостью: перезапуск приложения сам по себе
не означает перезагрузку общей машины. Если перезагружается машина, именно она
должна входить в ресурсы работ.

Один ресурс может иметь несколько оснований включения, но выводится один раз
с перечислением оснований. Владельцы определяются по модели владения, без дублирования
учётных записей пользователей.

Расчёт повторяется перед согласованием, при изменении плана, перед созданием события
для оповещения и непосредственно перед началом. До начала изменение затронутых
ресурсов, владельцев, подразделений или условий риска делает прежнее согласование
плановых работ неактуальным. После начала новые сведения используются для оповещения,
но не меняют ранее принятые решения. Если эти данные изменились между проверкой
и записью начала, операция отклоняется без изменения окна и состояний ресурсов.

Ограничения изображения графа — глубина три и число отображаемых узлов — не являются
критерием полноты расчёта влияния. При вычислительном ограничении возвращаются
`truncated = true` и причина. Неполный расчёт запрещает обычное согласование
и начало, но не сохранение черновика. Аварийное начало допускается руководителем
ИТ-отдела с отдельным подтверждением неполноты; предупреждение сохраняется в истории
и передаётся с уведомлениями. Даже полный расчёт отражает только внесённые в реестр
связи и не гарантирует полноту сведений о реальной инфраструктуре.

## 7.5 Согласование и полномочия

### Условия согласования

Предварительное согласование плановых работ обязательно, если хотя бы один ресурс
работ, зависимый ресурс, сосед по серверу или сервер из цепочки размещения (§7.7) имеет
`criticality = critical` либо `environment = prod`. Согласование также обязательно,
если в этих группах есть ресурс подразделения, отличного от `org_unit_id` окна,
или не определён действующий владелец. Отсутствие подразделения-инициатора
не позволяет направить плановые работы на согласование или запланировать их.

Если согласование требуется из-за критичности ресурса, его использования в рабочей
среде или отсутствия владельца, согласующим назначается руководитель ИТ-отдела
(`it_admin`). Для ресурсов другого подразделения добавляются их владельцы;
каждый пользователь включается в маршрут один раз. Исполнитель и создатель
не согласуют собственные работы: вместо них назначается другой
пользователь с ролью `it_admin`. Если подходящего согласующего нет, обычное начало
невозможно; исключение допускается только по аварийному порядку.

Используется общий механизм маршрутов `E6-2`, с привязкой решения к типу сущности
`maintenance`, её идентификатору и редакции плана. Положительное решение требуется
на каждом обязательном шаге. Администратор может вводить дополнительные условия,
но не отключать перечисленные обязательные проверки.

### Состояние согласования и изменение плана

`approval_state` принимает значения: не требуется (`not_required`), ожидается
(`pending`), согласовано (`approved`), отклонено (`rejected`). Оно не заменяет
состояние выполнения `state`.

Изменение редакции плана до начала делает прежние решения неприменимыми,
но не удаляет их. Система заново проверяет условия и определяет маршрут.
Для окна в состоянии `pending_approval` или `scheduled` после допустимого изменения
плана устанавливаются `state = pending_approval` и `approval_state = pending`,
если согласование требуется. Если оно не требуется, устанавливаются
`state = scheduled` и `approval_state = not_required`, независимо от того,
в каком из этих двух состояний окно находилось до изменения.

Черновик после редактирования остаётся в `draft`; для передачи на согласование
или публикации требуется отдельное действие. Неполные данные допустимы только
в черновике: изменение уже направленного на согласование или опубликованного плана,
нарушающее обязательные требования §7.3, отклоняется без сохранения.
Если владельцам уже создавались уведомления, им направляется сообщение об изменении,
в том числе об ожидании нового согласования.

После начала состав и плановые условия работ не редактируются. Дополнительный объём
оформляется новым окном с соблюдением ограничений одновременного обслуживания.
Последующее согласование аварийных работ изменяет только решение, а не факт начала
или завершения.

### Аварийные работы

Начало без предварительного согласования разрешено только `it_admin` при заполненном
`emergency_reason`. При этом фиксируются текущий план, исполнитель, известные
затронутые ресурсы и все подтверждённые предупреждения; `requires_approval = true`,
`approval_state = pending`.
Запрос последующего согласования создаётся вместе с записью начала.

Результат последующего согласования сохраняется и после завершения. Отказ не отменяет
уже выполненные действия и не меняет состояние ресурсов; о нём уведомляются
исполнитель и руководитель ИТ-отдела. Незавершённое последующее согласование видно
в отдельном списке. Его контрольный срок задаёт администратор; истечение срока
порождает напоминание согласующему и руководителю, но не положительное решение.

### Права

| Операция | Кто вправе выполнить |
|---|---|
| Создать и изменить план до начала | `it_specialist`, `it_admin` |
| Начать обычные работы и подтвердить результат | Назначенный исполнитель либо `it_admin` с указанием основания; фактический автор действия записывается в журнал |
| Начать аварийные работы | `it_admin` |
| Принять решение о согласовании | Назначенный согласующий по текущему шагу маршрута |
| Настроить правила, расписания и допуски | `it_admin` |
| Просмотреть сведения | По общей области видимости; `auditor` имеет только чтение |

Все проверки выполняются на сервере. Получение уведомления не предоставляет доступ
к чужим ресурсам. В списках, ответах программных интерфейсов и сообщениях скрываются
сведения, недоступные получателю, в том числе названия ресурсов в описании работ.

## 7.6 Допустимое время обслуживания

Плановый интервал задаётся как `[planned_start, planned_end)`: начало включено,
окончание исключено; начало строго предшествует окончанию. Моменты времени хранятся
по всемирному координированному времени (`UTC`), а отображаются в выбранном
часовом поясе, например `Europe/Moscow`.
Фактические моменты фиксируются сервером при подтверждении действий;
`actual_end` не может предшествовать `actual_start`.

Необязательное поле ресурса `allowed_maintenance_window` хранит часовой пояс
и список разрешённых недельных интервалов: день начала, время начала и время окончания.
Если время окончания раньше времени начала, интервал заканчивается на следующие сутки.
Равные значения времени недопустимы. Отсутствие поля означает отсутствие ограничения,
а не запрет обслуживания.

Весь плановый интервал должен входить в разрешённое время каждого ресурса работ.
Выход за него вызывает предупреждение. Сохранение плана допускается с указанием
причины; причина и затронутые ограничения доступны согласующему. Предупреждение
не отменяет требований предварительного согласования и не разрешает автоматически
аварийное начало.

## 7.7 Пересечение работ

Плановые интервалы пересекаются, если начало каждого из них раньше окончания другого.
Смежные интервалы, например 02:00–03:00 и 03:00–04:00, не пересекаются.
Проверяются окна в состояниях `scheduled` и `in_progress`, кроме самого изменяемого
окна. Выполняемые работы без фактического окончания считаются продолжающимися,
даже если их плановый срок уже истёк.

Конфликт показывается при общем ресурсе работ или общем сервере размещения.
Для вложенного размещения учитывается вся известная цепочка `hosted_on`, включая
сам ресурс, если он является сервером или виртуальной машиной. Неполный расчёт
цепочки обозначается явно. Сохранить пересекающиеся планы можно после указания
причины; сохраняются ссылки на конфликтующие окна.

Одновременное выполнение двух независимых окон над одним ресурсом запрещено.
Ограничение проверяется при начале в той же транзакции, что и изменение состояний.
При одновременных запросах начать работы успешно завершается только один запрос.
Аварийный порядок не отменяет этого ограничения.

Пересечение только по серверу размещения требует подтверждения предупреждения,
но не создаёт исключительного права на весь сервер. Это ограничение модели:
подсистема не гарантирует совместимость технических действий над разными ресурсами.
Согласованные совместные действия над одним ресурсом учитываются одним окном работ.

## 7.8 Повторяемые работы

Расписание `recurrence` задаётся строкой `cron` из пяти полей: минута, час, день
месяца, месяц и день недели. Секунды не используются. Допустимы числа, диапазоны,
списки, шаг и символ `*`; день недели задаётся числами 0–6, где 0 — воскресенье.
Одновременное ограничение дня месяца и дня недели не допускается. Перед сохранением
показываются ближайшие плановые даты в часовом поясе шаблона.

Планировщик заранее создаёт окно с началом, вычисленным по расписанию, и окончанием
через `duration`. Длительность положительная, `lead_time` неотрицателен. Окно получает
`pending_approval`, если требуется согласование, иначе `scheduled`. При неполных
данных или неполном расчёте создаётся `draft` с причиной, о которой уведомляется
исполнитель. Фактическое начало планировщик не устанавливает.

Неизменный `occurrence_at` хранит момент по расписанию; при создании он равен
`planned_start`, но при переносе работ не изменяется. Пара `(template_id, occurrence_at)`
уникальна. Конкурирующие или повторные запуски не создают второе окно, в том числе
после изменения планового срока. После сбоя планировщик обрабатывает пропущенные
даты начиная с последней успешно обработанной; наступившие сроки отмечаются как пропущенные,
но не приводят к автоматическому выполнению. Создание окна и запись об обработке даты
сохраняются совместно.

Редактирование или отключение шаблона влияет только на ещё не созданные окна.
Существующее окно хранит копию условий и редакцию шаблона; его перенос или отмена
выполняются отдельно. История завершённых работ не меняется.

Если при переводе часов местное время отсутствует, соответствующее выполнение
по расписанию пропускается; причина записывается, исполнитель получает уведомление.
Если местное время повторяется, создаётся одно окно по первому соответствующему
моменту. Правило одинаково для предварительного просмотра и планировщика; часовой пояс обязателен и не зависит от настроек сервера.

## 7.9 Оповещения

Модуль работ создаёт события с `event_id`, идентификатором окна, редакцией плана,
временем события и ссылкой на сохранённый результат расчёта. Выбор получателей,
каналов и доставка относятся к [подсистеме оповещений](05-notifications.md).
В таблице заданы обязательные группы получателей, а не способы доставки.

| Событие | Когда возникает | Получатели |
|---|---|---|
| `maintenance.scheduled` | План опубликован впервые или повторно согласован | Владельцы ресурсов трёх групп из §7.4 |
| `maintenance.changed` | Изменён опубликованный план или значимые сведения о затронутых ресурсах | Новые получатели и все, кому ранее созданы уведомления по окну |
| `maintenance.reminder` | Наступил срок напоминания | Владельцы затронутых ресурсов и исполнитель |
| `maintenance.started` | Начало подтверждено | Владельцы затронутых ресурсов; ожидаемая недоступность указана отдельно |
| `maintenance.completed` | Все ресурсы имеют результат `success` либо все имеют `rolled_back` | Все прежние получатели и текущие владельцы затронутых ресурсов |
| `maintenance.failed` | Общий результат `partial` или `failed` | Те же получатели и `it_admin` |
| `maintenance.cancelled` | Опубликованные работы отменены или отклонены до начала | Все прежние получатели; причина указывается явно |
| `maintenance.overdue` | Нарушен срок начала или окончания | Исполнитель и `it_admin`; вид просрочки указан в событии |
| `maintenance.approval_required` | Требуется решение либо нарушен его контрольный срок | Согласующий; при просрочке также `it_admin` |
| `maintenance.approval_rejected` | Аварийные работы отклонены при последующем согласовании | Исполнитель и `it_admin` |
| `maintenance.outside_allowed_window` | Подтверждён выход за допустимое время | `it_admin` |
| `maintenance.notice` | Специалист создал дополнительное сообщение с причиной | Владельцы текущих затронутых ресурсов и прежние получатели |

Напоминания по умолчанию создаются за семь суток и за одни сутки до начала.
Если план опубликован позже соответствующего срока, отдельное напоминание
за прошедший срок не создаётся: используется уведомление о публикации.
После изменения сроков ещё не обработанные напоминания прежней редакции отменяются.
Перед обработкой проверяются текущая редакция и состояние окна.

При отказе предварительного согласования исполнитель получает решение через общий
механизм согласования. Если план ранее публиковался, прежние получатели дополнительно
получают `maintenance.cancelled`. При отсутствии владельца его уведомление заменяется
уведомлением `it_admin`. Для аварийных работ отсутствие предварительной публикации
не препятствует событию начала.

Для каждой пары «событие — пользователь» создаётся одна внутренняя запись уведомления
со списком доступных пользователю ресурсов независимо от числа сработавших правил.
Уведомление ссылается на событие через `event_id`; все применённые правила сохраняются
в `NotificationRuleMatch` по [модели оповещений](05-notifications.md), §5.9.
Разные события, в том числе изменение плана и отмена, не подавляют друг друга.
Повторная обработка одного события не создаёт новую запись; для напоминаний
дополнительно уникальна комбинация окна, редакции плана и срока напоминания.

Изменения состояний отдельных ресурсов внутри окна содержат его идентификатор
и не порождают параллельные сообщения о тех же работах. История получателей
сохраняется, даже если состав ресурсов изменился. Перед внешней отправкой повторно
проверяются актуальность сообщения и права получателя. Уже переданное внешнему
каналу сообщение не отзывается; отмена или изменение оформляются новым сообщением.

## 7.10 Программные интерфейсы и внешняя задача

### Операции подсистемы

| Метод и путь | Назначение |
|---|---|
| `GET /api/v1/maintenance` | Список; фильтры по состоянию, периоду, ресурсу, исполнителю и состоянию согласования |
| `POST /api/v1/maintenance` | Создать черновик |
| `GET /api/v1/maintenance/{id}` | Прочитать окно, редакцию, результаты и историю |
| `PATCH /api/v1/maintenance/{id}` | Изменить план до начала с проверкой версии записи |
| `POST /api/v1/maintenance/{id}/transition` | Выполнить разрешённый переход; при завершении передать результаты всех ресурсов |
| `POST /api/v1/maintenance/{id}/approval` | Принять решение по назначенному шагу общего маршрута |
| `GET /api/v1/maintenance/{id}/affected` | Получить три группы ресурсов, основания включения и полноту расчёта |
| `GET /api/v1/maintenance/{id}/conflicts` | Получить конфликты по времени, ресурсам и серверам |
| `POST /api/v1/maintenance/{id}/notify` | Создать дополнительное оповещение с причиной; доступно специалисту и руководителю ИТ-отдела |
| `GET /api/v1/resources/{id}/maintenance` | История и планы по доступному ресурсу |
| `GET /api/v1/me/maintenance` | Работы, затрагивающие доступные пользователю ресурсы |
| `GET /api/v1/maintenance-templates` | Список шаблонов |
| `POST /api/v1/maintenance-templates` | Создать шаблон |
| `PATCH /api/v1/maintenance-templates/{id}` | Изменить или отключить шаблон без изменения созданных окон |

Ответ о затронутых ресурсах содержит `resources`, `dependents`, `cotenants`,
`truncated` и причину ограничения. Список по ресурсу учитывает как непосредственное
участие в работах, так и сохранённое влияние на него; основание связи показывается.
Списки выдаются постранично. Наличие следующей страницы не означает неполноту расчёта.

Изменяющие запросы содержат `operation_id`, а для существующей записи — ожидаемую
версию `version`. Повтор успешно обработанного запроса с теми же данными возвращает
сохранённый результат без повторных событий. Повторное использование идентификатора
с другими данными и изменение устаревшей версии отклоняются с кодом `409`.
При отсутствии полномочий возвращается код `403`, при нарушении правил данных
или перехода — `422`.
Проверка полномочий обязательна и при повторном запросе.

### Связь с системой ведения задач

При первом переходе в `scheduled` создаётся одна основная внешняя задача на окно.
При аварийном начале задача создаётся после фиксации начала, если её ещё нет.
Повторное согласование и изменение состояний ресурсов не создают дополнительных
задач. Используется `TrackerLink` с `entity_type = maintenance`.

Для окна допускается не более одной основной записи `TrackerLink`; в ней указаны
подключение и внешняя задача. Источником состояния выполнения является подсистема
работ. Закрытие внешней задачи не завершает окно и не восстанавливает ресурсы.
Различие состояний показывается исполнителю; сведения во внешней задаче обновляются по состоянию окна.
После завершения передаются фактические сроки и результаты, после отмены — причина.

Отправка выполняется отдельно от сохранения окна: запись исходящего события
сохраняется вместе с изменениями, затем обрабатывается фоновым обработчиком.
Ошибки и повторные попытки видны в журнале. Отказ внешней системы не отменяет
уже подтверждённое начало или завершение работ.

Ключ создания задачи связывается с идентификатором окна и подключением. Если внешний
сервис поддерживает защиту от повторного создания, используется этот ключ. При
потере ответа без такой поддержки сначала выполняется поиск созданной задачи
по сохранённому идентификатору окна. Если результат нельзя установить однозначно,
операция получает состояние «требуется сверка»; повторное создание до сверки запрещено.
Уникальность `TrackerLink` сама по себе не гарантирует отсутствие внешних дубликатов.

## 7.11 Пользовательские действия

Специалист открывает список работ, задаёт фильтры по сроку, состоянию, исполнителю
и ресурсу. В форме планирования видны три группы затронутых ресурсов, полнота расчёта,
конфликты и необходимость согласования. Предупреждение содержит причину и действие,
необходимое для продолжения; сообщение «возможна ошибка» без пояснения недопустимо.

Карточка окна показывает плановые и фактические сроки раздельно, текущую редакцию,
исполнителя, согласования, внешнюю задачу и историю уведомлений. Действия «Начать»
и «Завершить» доступны только уполномоченному пользователю. Завершение требует
результата по каждому ресурсу; общий результат вычисляется системой.

На карточке ресурса раздел «Работы» содержит планы, историю и основание включения.
Сотрудник видит только сведения в своей области доступа. Для запланированных работ
показывается предупреждение с датой, часовым поясом и ожидаемой недоступностью;
для просроченных не начатых работ нельзя показывать состояние «выполняется».

Для первой реализации используется список с фильтром по датам. Отдельная календарная
сетка не требуется. Сводные списки выделяют просроченные работы, незавершённые
согласования и ресурсы, оставшиеся в обслуживании после неудачного результата.

## 7.12 Ограничения и обоснование решений

| Решение | Основание |
|---|---|
| Начало и результат подтверждает человек | В проекте отсутствует проверка фактического выполнения технических действий |
| Шаблон отделён от окна | Изменение расписания не должно менять историю выполненных работ |
| Результат отделён от состояния выполнения | Завершение работ не тождественно успешному восстановлению ресурсов |
| Пересекающиеся планы разрешены, одновременное выполнение над одним ресурсом запрещено | Исключается восстановление состояния ресурса до окончания другого окна |
| Предварительное согласование привязано к редакции | Согласование старого состава работ не разрешает новый состав |
| Одна внешняя задача связана с окном | Групповое обслуживание не должно создавать задачу на каждый ресурс |
| Модуль использует общую базу данных, очередь и планировщик | Отдельные службы не требуются для описанных обязанностей |

Расчёт влияния ограничен указанными в §7.4 типами связей и качеством реестра.
Подтверждение результата исполнителем не заменяет независимую проверку доступности
и не означает автоматического выполнения или восстановления.
Выбор средств хранения графа, каналов доставки и конкретной системы ведения задач
относится к соответствующим разделам проекта.

Связанные положения приведены в документах [предметной модели](02-domain-model.md),
[архитектуры](03-architecture.md), [интеграций](04-integrations.md),
[оповещений](05-notifications.md), [графа](06-graph.md) и [перечне задач](backlog.md).

## 7.13 Критерии приёмки

Это составные сценарии будущей приёмки. Они дополняют требования `СТ-РР` и `ТП-РР`
общих спецификаций и не являются отчётом о проведённых испытаниях.

| Код | Проверяемая ситуация | Ожидаемый результат |
|---|---|---|
| РР-01 | Наступил срок, начало не подтверждено | Окно остаётся `scheduled`, состояния ресурсов не меняются; учитывается пропущенный срок |
| РР-02 | Попытка обычного начала без обязательного согласования | Операция отклонена, фактическое время отсутствует |
| РР-03 | После согласования добавлен ресурс или изменён срок | Старая редакция сохранена; решения неприменимы к новому плану; выполнена повторная проверка |
| РР-04 | При обслуживании сервера на нём размещена база данных, от которой зависит сервис | Расчёт включает базу и сервис, показывает пути по `hosted_on` и `depends_on` |
| РР-05 | Перезапускается приложение, рядом размещено независимое приложение | Второе показано как сосед; его недоступность не утверждается |
| РР-06 | Граф содержит цикл или цепочку длиннее трёх связей | Цикл не вызывает повторной обработки; глубина изображения не обрезает расчёт влияния |
| РР-07 | Расчёт неполон | Показаны признак и причина; обычное согласование и начало запрещены; аварийное исключение записано |
| РР-08 | Одновременно начинаются два окна над одним ресурсом | Начинается только одно; второе отклонено без частичного изменения ресурсов |
| РР-09 | Плановые интервалы смежные; другие работы фактически продолжаются после срока | Смежность сама по себе не даёт конфликта, но незавершённые работы учитываются |
| РР-10 | Отмена или отказ до начала | Ресурсы и фактические сроки не меняются; прежние получатели узнают об отмене опубликованного плана |
| РР-11 | Часть ресурсов обслужена неудачно | Сохранены отдельные результаты; проблемные ресурсы остаются в `maintenance`; общий результат `partial` |
| РР-12 | Предлагаемый возврат состояния нарушает общую модель | Завершение с таким состоянием отклонено; возврат в `returned` разрешён только при `restore_status = returned`, установленном по §7.3 |
| РР-13 | Шаблон обработан повторно, одновременно или после переноса созданного окна | По одному `occurrence_at` создано одно окно; после сбоя пропущенные даты не теряются |
| РР-14 | Шаблон изменён или отключён | Уже созданные окна и история результатов не изменены |
| РР-15 | Местное время пропущено или повторено при переводе часов | Применено правило §7.8; предварительный просмотр и создание окон дают одинаковые даты |
| РР-16 | Сорок ресурсов принадлежат одному владельцу; событие обработано повторно | На событие создана одна внутренняя запись уведомления; новое событие отмены не подавлено |
| РР-17 | Перенос опубликованного плана | Прежние напоминания не отправлены; старые и новые получатели получили актуальное изменение |
| РР-18 | Внешняя задача создана, но ответ потерян | Выполнено безопасное сопоставление либо назначена сверка; повторное создание без проверки запрещено |
| РР-19 | Внешняя задача закрыта или внешний сервис недоступен | Состояние окна не изменено внешним закрытием; подтверждённые данные не потеряны |
| РР-20 | Запрос повторён, версия устарела или произошёл сбой сохранения | Нет повторных событий, потери чужих изменений и частично сохранённого начала или завершения |
| РР-21 | Аварийные работы завершены до последующего решения | Факт выполнения сохранён; позднее решение не меняет его и не восстанавливает ресурсы |
| РР-22 | Получатель не вправе видеть часть затронутых ресурсов | Сведения о них не раскрыты в интерфейсе, ответе на запрос и уведомлении |
| РР-23 | Первые работы над ресурсом в `returned` завершились неудачно; последующие окна последовательно продолжили обслуживание | Во всех продолжениях сохраняется `restore_status = returned`; после успешного результата допустим возврат в ожидание приёмки, хотя `prev_status = maintenance` |
| РР-24 | Ресурс уже в `maintenance`, но подходящих предыдущих работ нет либо после них он выходил из этого состояния | `previous_maintenance_id` и `restore_status` пусты; давнее состояние `returned` не разрешает возврат; подмена полей клиентом отклоняется |
| РР-25 | По одному событию работ для одного пользователя сработали два правила; обработка повторена | Создано одно уведомление с обязательным `event_id`; сохранены обе записи `NotificationRuleMatch` с параметрами правил; повтор не создаёт новых записей |
| РР-26 | Изменён план на согласовании, после чего согласование не требуется; отдельно изменён черновик | В первом случае установлены `scheduled` и `not_required`; во втором сохранён `draft` без публикации; прежние решения остаются в истории |
