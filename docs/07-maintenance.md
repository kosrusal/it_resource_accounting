# 07. Регламентные работы

## 7.1 Что это и чем отличается от заявки

**Заявка** (`Request`) — сотрудник просит ресурс. **Регламентные работы**
(`MaintenanceWindow`) — IT-специалист планирует действие *над* ресурсами: обновление,
перезагрузка, замена диска, продление сертификата, миграция БД.

Отдельная сущность нужна по одной причине: у работ есть **время**, **затронутые
ресурсы** и **те, кого заденет**. Заявка ничего из этого не имеет.

Всё остальное переиспользуется: статус `maintenance` из жизненного цикла ресурса,
расчёт затронутых из `/impact` и соседей по хосту (`06-graph.md` §6.4), оповещения
из `05-notifications.md`, задача в трекере из `04-integrations.md`.

## 7.2 Сущность `MaintenanceWindow`

| Поле | Описание |
|---|---|
| `id`, `title`, `description` | Что делаем |
| `kind` | `planned` / `emergency` / `recurring` |
| `state` | Статус окна (см. 7.3) |
| `planned_start`, `planned_end` | Плановое окно |
| `actual_start`, `actual_end` | Фактическое |
| `executor_id` | Ответственный IT-специалист |
| `resources` | Список ресурсов, над которыми ведутся работы (M2M) |
| `recurrence` | Cron-выражение для регулярных работ, иначе пусто |
| `requires_approval`, `approver_id`, `approved_at` | Согласование (см. 7.5) |
| `expected_downtime` | Ожидается ли недоступность: да / нет |
| `tracker_key` | Связанная задача в трекере |
| `result` | `success` / `partial` / `failed` / `rolled_back` + комментарий |
| `created_by`, `created_at` | Служебные |

`MaintenanceResource` (строка M2M) хранит `prev_status` — статус ресурса до начала работ,
чтобы вернуть его туда же по завершении.

## 7.3 Жизненный цикл окна

| Из | В | Что происходит |
|---|---|---|
| `draft` | `pending_approval`, `scheduled`, `cancelled` | Согласование нужно — на согласование, иначе сразу в план |
| `pending_approval` | `scheduled`, `rejected` | Решение согласующего |
| `scheduled` | `in_progress`, `cancelled` | Наступило время или запущено вручную |
| `in_progress` | `completed`, `failed`, `rolled_back` | Работы закрыты исполнителем |
| `completed` / `failed` / `rolled_back` / `rejected` / `cancelled` | — | Терминальные |

**Автоматика на границах:**

- Переход в `in_progress`: все ресурсы окна переводятся в `maintenance`, их текущий
  статус сохраняется в `prev_status`.
- Переход в терминальное состояние: ресурсы возвращаются в `prev_status`.
  Если результат `failed` — возврат не делается автоматически, ресурс остаётся
  в `maintenance` и попадает в отчёт «зависли после работ».
- `in_progress` дольше `planned_end` + допуск → окно помечается просроченным,
  исполнителю и его руководителю уходит оповещение.

Запуск и закрытие — **вручную исполнителем**. Планировщик только напоминает и помечает
просрочку: система не знает, действительно ли работы начались, и не должна врать
об этом владельцам ресурсов.

## 7.4 Расчёт затронутых

При создании окна система показывает три списка (используется существующий обход графа):

| Список | Откуда | Зачем |
|---|---|---|
| **Ресурсы работ** | Выбраны вручную | Над чем работаем |
| **Зависимые** | `/impact` downstream по `depends_on` | Сломаются, если будет недоступность |
| **Соседи по хосту** | Два шага по `hosted_on` (`06-graph.md` §6.4) | Не сломаются сами, но делят железо и окно недоступности |

Владельцы всех трёх списков — кандидаты на оповещение. Списки пересчитываются при
изменении состава ресурсов окна и фиксируются в момент рассылки.

## 7.5 Когда нужно согласование

`requires_approval` выставляется автоматически, если выполняется хотя бы одно:

- любой ресурс окна имеет `criticality = critical`;
- любой ресурс окна в `environment = prod`;
- в списке затронутых есть ресурсы чужой команды;
- работы аварийные (`emergency`) — согласование постфактум.

Правила настраиваются админом. Согласующий — владелец ресурса или `it_admin`.
Переиспользуются маршруты согласования из E6-2, своей логики согласования нет.

## 7.6 Разрешённые окна обслуживания

У ресурса есть необязательное поле `allowed_maintenance_window` — правило вида
«будни 02:00–05:00» или «суббота 22:00–06:00». Если работы планируются вне его,
UI **предупреждает, но не блокирует**: у аварий регламента не бывает. Факт работы вне
окна фиксируется в записи окна и попадает в отчёт.

## 7.7 Конфликты

Перед сохранением проверяется пересечение по времени с другими окнами `scheduled` /
`in_progress`, затрагивающими те же ресурсы или тот же хост. Конфликт показывается со
ссылкой на второе окно; сохранение не блокируется — два инженера могут сознательно
работать в одно окно.

## 7.8 Регулярные работы

`recurrence` — cron-выражение. Планировщик за N дней до очередного срабатывания создаёт
конкретное окно в состоянии `scheduled` (или `pending_approval`, если требуется
согласование) и задачу в трекере. Шаблон и порождённые окна связаны: отмена шаблона не
трогает уже созданные окна.

Типовые регламенты, ради которых это и делается: обновление ОС и патчи, проверка
бэкапов, ротация ключей и сертификатов, чистка логов, плановая перезагрузка, продление
лицензий.

## 7.9 Оповещения

Добавляются к каталогу из `05-notifications.md`:

| Событие | Кому | Severity |
|---|---|---|
| `maintenance.scheduled` | Владельцы ресурсов работ, зависимых и соседей по хосту | info |
| `maintenance.reminder` | Им же, за 7 и за 1 день | info / warning |
| `maintenance.started` | Владельцы ресурсов с ожидаемой недоступностью | warning |
| `maintenance.completed` | Все оповещённые ранее | info |
| `maintenance.failed` | Владельцы, `it_admin` | critical |
| `maintenance.overdue` | Исполнитель, `it_admin` | warning |
| `maintenance.approval_required` | Согласующий | warning |
| `maintenance.outside_allowed_window` | `it_admin` | warning |

Работают общие правила борьбы с шумом: одно окно на 40 ресурсов даёт владельцу одно
уведомление со списком, а не сорок.


## 7.11 UI

**Админ / IT-специалист**
- Список окон с фильтрами по состоянию, периоду, исполнителю, ресурсу.
- Форма окна: ресурсы, время, повторяемость; сразу под ней — затронутые и конфликты.
- Кнопки «Начать» / «Завершить» с выбором результата.
- В карточке ресурса — вкладка «Работы»: история и запланированные.

**Сотрудник**
- На «Моих ресурсах» — плашка «плановые работы 14.10, 02:00–05:00» на затронутых карточках.
- В центре уведомлений — предупреждения о предстоящих работах.

Календарная сетка не делается: список с фильтром по датам решает ту же задачу.
Добавить, если окон станет столько, что список перестанет читаться.

## 7.12 Что сознательно не делается

- **Выполнение работ.** Система планирует, оповещает и учитывает — не запускает скрипты
  и не ходит на серверы. Это Ansible/Terraform.
- **Проверка, что работы реально начались.** Нет агентов и мониторинга; состояние
  ставит человек.
- **Свой календарь-конструктор.** Повторяемость — cron-строка.
- **Автооткат.** Результат `rolled_back` фиксируется, но откат делает инженер.
