# 07. Регламентные работы

Проектное описание подсистемы планирования и учёта обслуживания ресурсов.
Требования находятся в [системной спецификации](requirements/system.md)
и [спецификации ПО](requirements/software.md); здесь они не повторяются.
Раздел содержит модель данных, правила выполнения операций и сценарии проверки.
Программная реализация и результаты её испытаний в этом документе не представлены.

## 7.1 Назначение и границы

Подсистема хранит планы обслуживания, исполнителей, согласования, фактические сроки
и результаты. Для выбранных ресурсов она получает расчёт влияния от модуля графа,
проверяет пересечения работ и создаёт события для оповещений и внешних задач.
Плановые и аварийные работы учитываются раздельно по признаку срочности.

| Понятие | Значение в этом разделе |
|---|---|
| Окно работ | Учётная запись одного выполнения обслуживания, а не только время его проведения |
| Плановый интервал | Время, отведённое на выполнение работ: от планового начала до планового окончания |
| Ресурс работ | Ресурс, непосредственно выбранный для обслуживания |
| Затронутый ресурс | Ресурс, для которого по известным связям установлено возможное влияние работ |
| Шаблон работ | Описание повторяемого обслуживания, по которому создаются отдельные окна |
| Редакция плана | Сохранённые условия работ, к которым относится решение согласующего |
| Учётное состояние | Состояние ресурса в реестре; оно не является измерением его доступности |

Заявка фиксирует обращение сотрудника, например о выдаче оборудования. Окно работ
фиксирует обслуживание: обновление операционной системы, проверку восстановления
из резервной копии или замену сертификата. Для обоих объектов используется общий
механизм согласования, но их состояния и результаты различаются.

Технические действия выполняет специалист вне системы учёта. Подсистема не запускает
команды на серверах, не измеряет доступность и не восстанавливает конфигурацию.
Записанный результат означает подтверждение исполнителя, а не независимое измерение.

Устройство графа, способы доставки уведомлений и выбор внешней системы задач
относятся к соседним разделам. Их данные используются через описанные ниже связи;
собственные копии реестра, графа и правил доставки не создаются.

## 7.2 Данные

Технические обозначения сохранены для связи с общей моделью. В пользовательском
тексте применяются русские названия. Идентификатор обозначает существующую запись;
пустое значение отличается от отрицательного ответа или нулевой длительности.

### Окно работ — `MaintenanceWindow`

| Данные | Обозначение | Состав и ограничения |
|---|---|---|
| Идентификатор и название | `id`, `title` | Идентификатор постоянен; название обязательно для публикации |
| Описание | `description` | Цель, действия, способ проверки результата; порядок возврата к прежней конфигурации, если такой возврат предусмотрен |
| Срочность | `urgency` | Плановые — `planned`; аварийные — `emergency` |
| Состояние выполнения | `state` | Одно из состояний §7.3 |
| Плановые сроки | `planned_start`, `planned_end`, `time_zone` | Начало, окончание и часовой пояс по §7.6 |
| Фактические сроки | `actual_start`, `actual_end` | До подтверждения соответствующего действия значения отсутствуют |
| Исполнитель | `executor_id` | Действующий пользователь с ролью специалиста или руководителя ИТ-отдела |
| Подразделение-инициатор | `org_unit_id` | Для разовых работ определяется по создателю, для повторяемых — по шаблону; после создания не меняется |
| Ожидаемая недоступность | `expected_downtime` | Логический признак, заданный исполнителем; ожидаемые последствия для конкретных ресурсов описываются в плане |
| Основание повторения | `template_id`, `template_revision`, `occurrence_at` | Шаблон, его редакция и исходный момент по расписанию; для разовых работ отсутствуют |
| Согласование | `requires_approval`, `approval_state`, `approval_route_id` | Необходимость решения, его состояние и маршрут по §7.5 |
| Редакция и версия | `plan_revision`, `version` | Редакция условий плана и версия записи для проверки одновременных изменений |
| Общий результат | `result`, `result_comment` | Вычисленный результат окна и пояснение после завершения |
| Аварийное основание | `emergency_reason` | Причина начала в аварийном порядке |
| История записи | `created_by`, `created_at`, `updated_at` | Автор, время создания и последнего изменения |

До публикации допускается неполный черновик. Для публикации и начала обязательны
название, описание действий и проверки, срочность, корректный плановый интервал,
подразделение, действующий исполнитель, признак ожидаемой недоступности и хотя бы
один существующий ресурс работ. Аварийный порядок не разрешает пропустить эти данные.

Изменение цели, действий, сроков, исполнителя, срочности, состава ресурсов или оценки
недоступности до начала создаёт новую редакцию плана. Любое успешно сохранённое
изменение записи увеличивает её версию; повтор уже выполненной операции — нет.
Прежние редакции и решения остаются в истории. Связь с внешней задачей хранится
в общей записи `TrackerLink`, а не дублируется в окне.

### Связь с ресурсом — `MaintenanceResource`

| Данные | Обозначение | Назначение |
|---|---|---|
| Окно и ресурс | `maintenance_id`, `resource_id` | Пара уникальна: один ресурс не повторяется в составе окна |
| Прежнее состояние | `prev_status` | Состояние непосредственно перед началом текущего окна |
| Предыдущие работы | `previous_maintenance_id` | Последнее завершённое окно непрерывного обслуживания этого ресурса |
| Основание восстановления | `restore_status` | Подтверждённое состояние до непрерывного периода обслуживания |
| Результат ресурса | `result`, `result_comment`, `status_after` | Результат действий и проверки, пояснение и итоговое учётное состояние |

Прежнее состояние, связь с предыдущими работами и основание восстановления вычисляются
при начале по §7.3. До начала они пусты, после начала неизменны; задавать их в запросе
пользователя нельзя. История обслуживания определяется отдельно для каждого ресурса.

### Шаблон — `MaintenanceTemplate`

Шаблон содержит название, описание, ресурсы, исполнителя, подразделение-инициатора,
оценку недоступности, расписание `recurrence`, часовой пояс `time_zone`, длительность
`duration`, срок предварительного создания `lead_time`, признак активности `enabled`
и редакцию. Длительность задаётся положительным целым числом минут, срок предварительного
создания — неотрицательным целым числом минут. Подразделение определяется по создателю.

Шаблон задаёт плановые работы. Повторяемость не является отдельным видом срочности.
Созданное окно хранит копию условий и номер редакции шаблона.

### Расчёты и история

Сохранённый расчёт влияния включает исходные ресурсы, основания включения найденных
ресурсов, владельцев, подразделения, критичность, среду использования, время расчёта,
признак полноты и причину ограничения. Решение согласующего связано с редакцией плана
и конкретным расчётом. Изменение реестра не переписывает уже сохранённый расчёт.

История работ содержит автора, время, действие, прежние и новые значения, причины
исключений и результаты по ресурсам. Историю получателей и доставки ведёт подсистема
оповещений. Учётная запись работ сохраняет связь с её событиями, а не копию доставки.

## 7.3 Состояния, начало и завершение

### Переходы окна

| Состояние | Техническое значение |
|---|---|
| Черновик | `draft` |
| На согласовании | `pending_approval` |
| Запланировано | `scheduled` |
| Выполняется | `in_progress` |
| Завершено | `completed` |
| Отклонено | `rejected` |
| Отменено | `cancelled` |

| Исходное состояние | Действие и условие | Следующее состояние |
|---|---|---|
| Черновик | Передача заполненного плана при обязательном согласовании | На согласовании |
| Черновик | Публикация заполненного плана, согласование не требуется | Запланировано |
| На согласовании | Все обязательные решения по актуальному плану положительные | Запланировано |
| На согласовании | Получено отрицательное предварительное решение | Отклонено |
| На согласовании или запланировано | Изменённый план требует согласования | На согласовании |
| На согласовании или запланировано | Изменённый план не требует согласования | Запланировано |
| Запланировано | Уполномоченный пользователь подтвердил обычное начало; проверки пройдены | Выполняется |
| Черновик, на согласовании или запланировано | Руководитель ИТ-отдела подтвердил аварийное начало по §7.5 | Выполняется |
| Черновик, на согласовании или запланировано | Отмена до начала с указанием причины | Отменено |
| Выполняется | Подтверждён результат каждого ресурса и допустимость итоговых состояний | Завершено |

Публикация означает переход в состояние «Запланировано». Редактирование черновика
его не публикует. Состояния «Завершено», «Отклонено» и «Отменено» конечные.
Позднее решение по аварийным работам изменяет только согласование, но не состояние
выполнения. Повторные работы оформляются новым окном.

После начала отмена не применяется: прекращение действий оформляется завершением
с фактическим результатом. Неудача и возврат к прежней конфигурации — результаты,
а не отдельные состояния окна.

### Начало

Обычное начало допустимо внутри планового интервала. Для начала вне него
сначала изменяется план либо применяется аварийный порядок.
Наступление срока само по себе не создаёт фактического начала.

При подтверждении начала проверяются полномочия, обязательные данные, актуальность
расчёта и согласования, допустимое время, состояния ресурсов и отсутствие другого выполняемого окна
над тем же ресурсом. Допустимы исходные состояния «На складе», «Используется»,
«Ожидает приёмки» и «На обслуживании». Для ресурсов, которые не выдаются сотруднику,
ожидание приёмки не используется. Ограничения типов определены в
[модели ресурсов](02-domain-model.md), §2.4.

Успешное начало сохраняет фактическое время, прежнее состояние каждого ресурса работ
и переводит эти ресурсы в обслуживание. Уже обслуживаемый ресурс сохраняет это
состояние. Зависимые ресурсы и соседи по серверу автоматически в обслуживание
не переводятся. Все изменения начала сохраняются совместно по §7.10.

### Повторное обслуживание

Несколько последовательных окон могут относиться к одному непрерывному периоду
обслуживания. Прежнее состояние текущего окна и основание восстановления различаются.

| Состояние при начале | Проверяемое условие | Записываемое основание |
|---|---|---|
| Ресурс ещё не в обслуживании | Допустимость исходного состояния | `restore_status = prev_status`; предыдущие работы не указываются |
| Ресурс в обслуживании | Последнее завершённое окно оставило этот ресурс в обслуживании; после него ресурс из этого состояния не выходил | Ссылка на это окно; копия его `restore_status`, в том числе пустого |
| Ресурс в обслуживании | Подходящего предыдущего окна или подтверждения непрерывности нет | Ссылка на предыдущие работы и основание восстановления пусты |

Непрерывность подтверждается журналом изменений. Незавершённое, текущее или не связанное
с ресурсом окно не используется. Расчёт основания и запись начала выполняются совместно.

Примечание. Ресурс ожидал приёмки, первые работы завершились неудачно. При повторных
работах его прежнее состояние — обслуживание, но подтверждённое основание
восстановления — ожидание приёмки. После успешной повторной попытки возврат в ожидание
приёмки допустим. Если между попытками ресурс выходил из обслуживания, это основание
не наследуется.

### Результат

| Результат ресурса | Техническое значение | Смысл и итоговое состояние |
|---|---|---|
| Успешно | `success` | Действия выполнены; проверка подтверждена. Исполнитель выбирает допустимое итоговое состояние |
| Частично | `partial` | Выполнена часть действий или проверок. Ресурс остаётся в обслуживании; записываются причина и оставшиеся действия |
| Неудачно | `failed` | Цель не достигнута, восстановление не подтверждено. Ресурс остаётся в обслуживании; записываются причина и дальнейшее действие |
| Прежняя конфигурация восстановлена | `rolled_back` | Изменения отменены и восстановление проверено. Исполнитель выбирает допустимое итоговое состояние |

По каждому ресурсу указываются результат, сведения о выполненной проверке и итоговое
состояние. Невыполненная проверка отмечается с причиной, а не выдаётся за успешную.
Для успешных работ и подтверждённого восстановления система предлагает известное
основание восстановления; исполнитель подтверждает его либо выбирает другое
допустимое состояние. При неизвестном основании состояние выбирается явно.

Переход проверяется по общей модели. Использование ресурса требует действующего
владельца. Возврат в ожидание приёмки допустим только при подтверждённом
`restore_status = returned` и результате `success` либо `rolled_back`.
При частичном или неудачном результате ресурс остаётся в обслуживании независимо
от этого основания. Ожидание приёмки не означает принятия на склад.

Если результаты ресурсов совпадают, общий результат равен этому значению. Иначе
общий результат — частичный. Восстановление зависимых ресурсов
этот результат не подтверждает.

При отмене или отклонении до начала состояния ресурсов не меняются; фактические
сроки и результат отсутствуют. После завершения история работ неизменна, а новые
изменения ресурса выполняются по общей модели.

### Нарушение сроков

| Условие | Вид нарушения |
|---|---|
| Окно запланировано; текущее время позже планового начала с учётом допуска | Пропущен срок начала |
| Окно выполняется; текущее время позже планового окончания с учётом допуска | Превышен срок окончания |
| Решение ожидается дольше контрольного срока согласования | Просрочено согласование, а не начало готовых к выполнению работ |

Допуск задаётся администратором; предварительное значение — ноль. Эти проверки не меняют
состояние выполнения. Плановые сроки после начала не редактируются: продолжение
действий не скрывает просрочку. Неопределённые параметры времени перечислены в §7.12.

## 7.4 Определение затронутых ресурсов

Расчёт выполняет модуль графа. Подсистема работ использует три группы:

| Группа | Основание включения |
|---|---|
| Ресурсы работ | Непосредственно выбраны для обслуживания |
| Зависимые ресурсы | Достижимы от ресурсов работ против направления связей зависимости и размещения |
| Соседи по серверу | Непосредственно размещены на той же машине, что и ресурс работ |

Связь `A depends_on B` означает зависимость ресурса `A` от `B`.
При обслуживании `B` расчёт идёт против направления связи и находит `A`.
Для `hosted_on` применяется то же направление: обслуживание сервера затрагивает
размещённые на нём ресурсы, затем зависящие от них ресурсы. Обход продолжается до
исчерпания достижимых узлов; циклы не создают повторных записей.

Результат содержит владельцев, основания включения и связи, объясняющие влияние.
Один ресурс выводится один раз с сохранением разных оснований. Соседство само по
себе не доказывает недоступность. При перезагрузке всей машины ресурсом работ
указывается машина, а не только одно из размещённых приложений.

В этой редакции влияние распространяется только по `depends_on` и `hosted_on`,
как в ТП-ГР-05. Отношение «включает в себя» для изображения состава не расширяет
этот расчёт автоматически. Связь `part_of` рассматривается отдельно в ОВ-07;
`backup_of` не подтверждает исправность резерва. Полнота означает завершённый расчёт
по внесённым связям поддержанных типов, а не полноту сведений о реальной инфраструктуре.

Расчёт обновляется при изменении плана, перед согласованием, созданием события
оповещения и началом. До начала изменение состава затронутых ресурсов, владельцев,
подразделений, критичности или среды делает прежнее согласование неприменимым.
После начала новые сведения используются в оповещениях, не изменяя прежних решений.
Если исходные данные изменились между проверкой и записью начала, система отклоняет
операцию без частичного сохранения.

Ограничения изображения графа и пользовательские фильтры не ограничивают служебный
расчёт влияния. Незавершённый расчёт имеет `truncated = true` и причину.
С таким результатом нельзя принять обычное согласование или начать обычные работы.
Черновик сохранить можно. Аварийное исключение по §7.5 сохраняет подтверждение
неполноты и передаёт его с событием. Постраничная выдача полного списка неполнотой
расчёта не считается.

## 7.5 Согласование и полномочия

### Основания и участники

Проверяются ресурсы работ, зависимые ресурсы, соседи и серверы цепочки размещения.

| Основание обязательного согласования | Участник решения |
|---|---|
| Критический ресурс: `criticality = critical` | Руководитель ИТ-отдела |
| Ресурс рабочей среды: `environment = prod` | Руководитель ИТ-отдела |
| Нет действующего владельца | Руководитель ИТ-отдела |
| Подразделение ресурса отличается от подразделения-инициатора окна | Владелец такого ресурса; при его отсутствии — руководитель ИТ-отдела |

Повторяющиеся участники объединяются. Создатель и исполнитель не согласуют
собственные работы: вместо них назначается другой руководитель ИТ-отдела.
Отсутствие подходящего согласующего запрещает обычное начало.
Администратор может добавить условия согласования, но не отключить перечисленные.

Общий механизм согласования получает тип сущности `maintenance`, идентификатор
окна, редакцию плана и маршрут. Согласование действительно при положительном
решении на каждом обязательном шаге и актуальности исходных данных расчёта.

### Решение и изменение плана

| Состояние согласования | Значение |
|---|---|
| Не требуется | `not_required` |
| Ожидается | `pending` |
| Согласовано | `approved` |
| Отклонено | `rejected` |

Состояние согласования хранится отдельно от состояния выполнения.
При допустимом изменении направленного на согласование или опубликованного плана
условия и маршрут проверяются заново. Если решение требуется, устанавливаются
«На согласовании» и «Ожидается»; иначе — «Запланировано» и «Не требуется».
Старые решения сохраняются, но к новому плану не применяются.

Редактирование черновика оставляет его черновиком. Изменение опубликованного плана,
нарушающее обязательные условия §7.2, отклоняется без сохранения.
Прежним получателям направляется событие изменения, включая возврат на согласование.

После начала состав и плановые условия неизменны. Дополнительные работы оформляются
новым окном с проверкой пересечения. Последующее согласование аварийных работ
не изменяет факты выполнения.

### Аварийное начало

Аварийное начало без предварительного решения доступно только руководителю
ИТ-отдела. Обязательны причина срочности, данные плана и подтверждение обнаруженных
предупреждений, включая неполный расчёт. Ограничение одного выполняемого окна
на ресурс сохраняется.

Вместе с началом фиксируются редакция плана, исполнитель, известные затронутые
ресурсы, предупреждения и запрос последующего согласования. Согласование обязательно,
его состояние — «Ожидается». Отрицательное последующее решение не отменяет уже
выполненных действий и не восстанавливает ресурсы. О решении создаётся событие
для исполнителя и руководителя ИТ-отдела.

До получения решения согласование остаётся незавершённым, в том числе после окончания
работ. Превышение контрольного срока создаёт напоминание, а не положительное решение.

### Полномочия

| Действие | Пользователь |
|---|---|
| Создание и изменение плана до начала | Специалист `it_specialist` или руководитель ИТ-отдела `it_admin` |
| Обычное начало и подтверждение результата | Назначенный исполнитель; руководитель ИТ-отдела — с основанием замещения |
| Аварийное начало | Руководитель ИТ-отдела |
| Решение по согласованию | Участник текущего шага маршрута |
| Изменение правил, шаблонов, расписаний и допусков | Руководитель ИТ-отдела |
| Чтение | По общей области доступа; аудитор `auditor` не изменяет сведения |

Полномочия проверяются на сервере при каждом обращении, включая повтор операции.
Доступность кнопки не заменяет этой проверки. Полученное уведомление не даёт права
читать чужой ресурс. Свободное описание работ также проверяется на раскрытие
недоступных сведений; при невозможности безопасного показа используется общее
сообщение без названий и ссылок на закрытые ресурсы.

## 7.6 Допустимое время обслуживания

Плановый интервал — `[planned_start, planned_end)`: начало включено, окончание
исключено. Начало строго предшествует окончанию. Время хранится по всемирному
координированному времени `UTC` и показывается с выбранным часовым поясом,
например `Europe/Moscow`. Фактические моменты записывает сервер при подтверждении;
окончание не может предшествовать началу.

Правило ресурса `allowed_maintenance_window` содержит часовой пояс и недельные
интервалы: день начала, время начала и время окончания. Если окончание раньше
начала по местным часам, оно относится к следующим суткам. Равные значения времени
не допускаются. Отсутствие правила означает отсутствие этого ограничения.

Проверяется, полностью ли плановый интервал входит в разрешённое время каждого
ресурса работ. Выход за границы вызывает предупреждение. Сохранение возможно
с причиной, доступной согласующему. Такое подтверждение не заменяет обязательного
согласования и само по себе не разрешает аварийный порядок.

## 7.7 Пересечение работ

Интервалы пересекаются, если начало каждого раньше окончания другого.
Интервалы 02:00–03:00 и 03:00–04:00 смежные и только по времени не конфликтуют.
Проверяются запланированные и выполняемые окна, кроме самого изменяемого окна.
Выполняемое окно без фактического окончания учитывается как продолжающееся,
даже после истечения планового срока.

Если интервалы пересекаются, конфликт определяется по общему ресурсу работ
или общему серверу размещения. Для вложенного размещения учитывается известная цепочка `hosted_on`,
включая сам ресурс, когда это сервер или виртуальная машина. Неполнота цепочки
показывается явно. Сохранение пересекающихся планов требует причины; вместе с ней
сохраняются ссылки на конфликтующие окна.

Одновременное выполнение двух независимых окон над одним ресурсом запрещено.
Проверка и запись начала выполняются в одной транзакции. Из двух одновременных
попыток начала над общим ресурсом успешно завершается не более одной.
Аварийный порядок этого ограничения не отменяет.

Пересечение только по серверу требует подтверждения предупреждения, но не блокирует
все размещённые ресурсы. Подсистема не устанавливает совместимость технических
действий над разными ресурсами. Совместные действия над одним ресурсом учитываются
одним окном.

## 7.8 Повторяемые работы

Расписание `recurrence` — выражение `cron` из пяти полей: минута, час, день месяца,
месяц, день недели. Поддерживаются числа, диапазоны, списки, шаг и `*`.
Секунды не задаются; день недели — от 0 до 6, где 0 означает воскресенье.
День месяца и день недели одновременно не ограничиваются.
Перед сохранением показываются ближайшие даты в часовом поясе шаблона.

Для очередного момента расписания планировщик создаёт окно за указанный срок
предварительного создания. Плановое окончание вычисляется прибавлением длительности
к началу. При обязательном согласовании окно получает состояние «На согласовании»,
иначе — «Запланировано». Неполные данные или неполный расчёт дают черновик с причиной
для исполнителя. Планировщик не подтверждает фактическое начало.

Исходный момент `occurrence_at` при создании равен плановому началу, но не меняется
при переносе окна. Пара шаблона и исходного момента уникальна. Повторные и одновременные
запуски используют существующее окно, в том числе после переноса его сроков.
Создание окна и запись об обработке даты сохраняются совместно.

После сбоя обрабатываются ещё не обработанные даты начиная с последней успешной.
Наступившие сроки отражаются как пропущенные; работы не выполняются автоматически.
Изменение или отключение шаблона не меняет уже созданные окна: их перенос и отмена
выполняются отдельно.

Проектное уточнение этой редакции: после включения ранее отключённого шаблона
обрабатываются даты начиная с момента включения; даты периода отключения пропускаются.
Это не технический сбой активного шаблона. Новая редакция расписания применяется
к ещё не созданным окнам с исходным моментом не раньше времени её сохранения.
Необработанные даты до изменения относятся к прежней редакции. Время изменения
и периоды активности определяются по истории шаблона.

При переводе часов отсутствующее местное время пропускается с записью причины
и сообщением исполнителю. Повторённое местное время используется один раз — по
первому соответствующему моменту. Предварительный просмотр и планировщик применяют
одно правило. Часовой пояс задан в шаблоне и не зависит от настроек сервера.

## 7.9 Оповещения

Подсистема работ сохраняет события. Выбор каналов и доставка выполняются
[подсистемой оповещений](05-notifications.md), §5.9–5.10. Событие содержит
`event_id`, идентификатор окна, редакцию плана, время и ссылку на сохранённый
расчёт влияния. Для результата передаются сведения по ресурсам; для просрочки — её вид.

| Событие | Основание | Обязательная группа получателей |
|---|---|---|
| `maintenance.scheduled` | Первая публикация или публикация после нового согласования | Владельцы трёх групп ресурсов из §7.4 |
| `maintenance.changed` | Изменение опубликованного плана или значимых сведений расчёта | Текущие и прежние получатели окна |
| `maintenance.reminder` | Наступление срока напоминания | Владельцы затронутых ресурсов и исполнитель |
| `maintenance.started` | Подтверждённое начало | Владельцы затронутых ресурсов; оценка недоступности передаётся отдельно |
| `maintenance.completed` | Все результаты успешные либо все подтверждают восстановление прежней конфигурации | Прежние получатели и текущие владельцы затронутых ресурсов |
| `maintenance.failed` | Общий результат частичный или неудачный | Те же получатели и руководитель ИТ-отдела |
| `maintenance.cancelled` | Отмена или отклонение ранее опубликованного плана до начала | Прежние получатели; передаётся причина |
| `maintenance.overdue` | Пропущено начало или превышено окончание | Исполнитель и руководитель ИТ-отдела |
| `maintenance.approval_required` | Запрос решения или просрочка согласования | Согласующий; при просрочке также руководитель ИТ-отдела |
| `maintenance.approval_rejected` | Отрицательное последующее решение по аварийным работам | Исполнитель и руководитель ИТ-отдела |
| `maintenance.outside_allowed_window` | Подтверждён выход за разрешённое время | Руководитель ИТ-отдела |
| `maintenance.notice` | Дополнительное сообщение специалиста с указанной причиной | Текущие владельцы затронутых ресурсов и прежние получатели |

Отрицательное предварительное решение передаётся исполнителю общим механизмом
согласования. Если план ранее публиковался, дополнительно создаётся событие отмены.
Отсутствующего владельца в группе получателей заменяет руководитель ИТ-отдела.
Для аварийного начала предварительная публикация не требуется.

Предварительные сроки напоминаний — за семь суток и за одни сутки до начала. При поздней
публикации отдельные напоминания за уже прошедшие сроки не создаются. После переноса
старые необработанные напоминания снимаются; перед обработкой проверяются редакция
и состояние окна. Основание напоминания уникально по окну, редакции и сроку.

Уровни важности берутся из раздела 05, §5.10. Успешное завершение отличается от
возврата к прежней конфигурации по результату события, даже при одинаковом имени
события. Частичный результат не означает отказ всех ресурсов.

Каждое событие создаёт одному пользователю одну внутреннюю запись со списком
доступных ему ресурсов. Уведомление связано с событием, а применённые правила
сохраняются в `NotificationRuleMatch`. Повторная обработка не создаёт новых записей.
Изменение плана, отмена и завершение — разные события, их сообщения не подавляют
друг друга и не объединяются в сводку.

Изменения состояний ресурсов внутри окна содержат его идентификатор и не создают
дополнительных сообщений о тех же работах. Прежние получатели сохраняются в истории.
Перед внешней отправкой повторно проверяются актуальность и доступ. Уже переданное
сообщение не отзывается: перенос или отмена сообщаются новым событием.
Отсутствие повторов во внешнем канале не гарантируется самой подсистемой работ.

## 7.10 Программные интерфейсы и внешняя задача

### Операции

| Метод и путь | Результат операции |
|---|---|
| `GET /api/v1/maintenance` | Список с фильтрами по состоянию, периоду, ресурсу, исполнителю и согласованию |
| `POST /api/v1/maintenance` | Новый черновик |
| `GET /api/v1/maintenance/{id}` | Окно, редакция, результаты и история в области доступа |
| `PATCH /api/v1/maintenance/{id}` | Изменённый план до начала при совпадении версии |
| `POST /api/v1/maintenance/{id}/transition` | Разрешённый переход; завершение принимает результаты всех ресурсов |
| `POST /api/v1/maintenance/{id}/approval` | Решение по назначенному шагу общего маршрута |
| `GET /api/v1/maintenance/{id}/affected` | Три группы ресурсов, основания включения и полнота расчёта |
| `GET /api/v1/maintenance/{id}/conflicts` | Конфликтующие окна и причины пересечения |
| `POST /api/v1/maintenance/{id}/notify` | Событие дополнительного сообщения с причиной |
| `GET /api/v1/resources/{id}/maintenance` | История и планы, непосредственно или косвенно затрагивающие доступный ресурс |
| `GET /api/v1/me/maintenance` | Работы по доступным пользователю ресурсам |
| `GET /api/v1/maintenance-templates` | Список шаблонов |
| `POST /api/v1/maintenance-templates` | Новый шаблон |
| `PATCH /api/v1/maintenance-templates/{id}` | Изменённый или отключённый шаблон без изменения существующих окон |

Ответ о влиянии содержит `resources`, `dependents`, `cotenants`, `truncated`
и причину ограничения. Основание связи с ресурсом показывается отдельно.
Списки выдаются постранично; размер страницы не задаёт предел расчёта влияния.

### Сохранение и повтор запросов

Изменяющий запрос содержит `operation_id`; для существующей записи также передаётся
ожидаемая версия `version`. Проверка полномочий предшествует выдаче результата,
в том числе результата ранее выполненной операции.

| Ситуация | Ответ |
|---|---|
| Операция с этим идентификатором уже успешно выполнена с теми же данными | Сохранённый результат без повторных изменений и событий |
| Идентификатор операции повторно использован с другими данными | `409`: конфликт операции |
| Новая операция с устаревшей версией | `409`: конфликт версии |
| Нет полномочия | `403`: действие запрещено |
| Нарушены ограничения данных или перехода | `422`: причина и относящиеся к ней поля |

Повтор успешной операции проверяется раньше совпадения ожидаемой версии: увеличение
версии самой выполненной операцией не превращает её допустимый повтор в новый запрос.
Это правило не отменяет повторной проверки доступа.

Начало и завершение записывают состояние окна, фактическое время, состояния ресурсов,
историю и исходящие события в одной транзакции. При ошибке ни одно из этих изменений
не сохраняется. Проверки одновременного обслуживания выполняются в той же транзакции.
Пока окно выполняется, другие операции не меняют учётные состояния его ресурсов;
импорт не является исключением. Отправка наружу выполняется после сохранения.

### Связь с внешней задачей

Обмен выполняется через модуль связи с [системой задач](08-task-tracker.md),
§8.4–8.6. При первой публикации окна создаётся запрос на одну основную задачу.
При аварийном начале такой запрос сохраняется вместе с началом, если задачи ещё нет.
Новое согласование и изменения ресурсов внутри окна дополнительных задач не создают.

Основная связь `TrackerLink` имеет `entity_type = maintenance` и `role = primary`.
Она указывает подключение и устойчивый внешний идентификатор задачи. Подсистема
работ передаёт изменения сроков, отмену и результат для обновления связанной задачи. Закрытие задачи
во внешней системе не начинает и не завершает работы и не восстанавливает ресурсы.
Различие состояний показывается исполнителю.

Отказ подключения не отменяет подтверждённое начало или завершение. Состояние
передачи и ошибка показываются отдельно от состояния работ. При потере ответа на
создание сначала определяется результат прежней попытки по устойчивому основанию.
При неизвестном результате требуется сверка. Способ безопасного повтора определяет
подключение, а не этот раздел.

## 7.11 Пользовательские действия

Специалист видит список работ с фильтрами по сроку, состоянию, исполнителю и ресурсу.
В форме плана показываются затронутые ресурсы, основания включения, полнота расчёта,
пересечения и необходимость согласования. Предупреждение содержит конкретную
причину и условие продолжения.

Карточка окна раздельно показывает плановые и фактические сроки, часовой пояс,
редакцию плана, исполнителя, согласования, внешнюю задачу, состояние передачи
и историю уведомлений. Действия начала и завершения доступны по полномочиям §7.5.
При завершении указываются результаты и проверки по каждому ресурсу.

В карточке ресурса раздел «Работы» показывает планы и историю с основанием включения.
Сотрудник видит только доступные сведения. Просроченный не начатый план не отображается
как выполняемые работы. Сводные списки отдельно показывают нарушения сроков,
незавершённые согласования и ресурсы, оставшиеся в обслуживании.

Для первой реализации используется список с фильтром по датам. Отдельная календарная
сетка не включена в выбранное решение.

## 7.12 Устройство решения, основания и вопросы

### Место подсистемы и потоки данных

Подсистема использует общие хранилище, очередь и планировщик, описанные в
[архитектуре](03-architecture.md). Выделение отдельного приложения не предусмотрено.

| Источник | Данные | Использование или получатель |
|---|---|---|
| Пользовательский запрос | План, подтверждение начала, решение или результаты | Проверка доступа и выполнение операции работ |
| Реестр и модуль графа | Ресурсы, связи, владельцы, среда и критичность | Расчёт влияния, проверки плана и начала |
| Общий механизм согласования | Решение по редакции и шагу | Разрешение обычного начала либо запись последующего решения |
| Планировщик | Наступившая дата расписания или контрольный срок | Создание окна либо события напоминания; без фактического начала |
| Операция работ | Изменённые данные и исходящее событие | Совместная запись в хранилище |
| Сохранённое событие | Окно, редакция, расчёт и результат | Подсистемы оповещений и внешних задач |
| Внешнее подключение | Состояние передачи и связанной задачи | Показ исполнителю; без изменения факта выполнения работ |

Порядок обработки пользовательского действия: проверка доступа, проверка повтора,
проверка версии и предметных условий, совместное сохранение, выдача результата.
Внешняя отправка продолжается отдельно. Неудачная проверка прекращает операцию
до записи её предметных изменений.

### Обоснование проектных решений

| Решение | Основание в требованиях или границах |
|---|---|
| Начало подтверждает человек | СТ-РР-03; система не измеряет выполнение технических действий |
| Результат хранится по каждому ресурсу | СТ-РР-06–СТ-РР-08; групповое завершение не доказывает восстановление каждого ресурса |
| Шаблон отделён от окна | СТ-РР-10; изменение расписания не меняет историю конкретного выполнения |
| Основание восстановления переносится только при непрерывном обслуживании | СТ-РР-08; старая несвязанная история не разрешает возврат в ожидание приёмки |
| Один ресурс не участвует в двух выполняемых окнах | СТ-РР-04; одно завершение не восстанавливает ресурс во время других работ |
| Решение относится к редакции плана | СТ-РР-02; согласование старых условий не разрешает изменённые работы |
| События сохраняются вместе с результатом | СТ-РР-05; потеря внешнего подключения не приводит к потере предметного факта |
| Одна основная внешняя задача на окно | Сценарий Т6 раздела 08; ресурсы одного окна не создают отдельные задачи обслуживания |

Значения напоминаний за семь и одни сутки, исходный нулевой допуск, форма расписания
и запрет изменения плана после начала перенесены из исходного проектного описания.
Правило возобновления и смены расписания в §7.8 уточнено в этой редакции:
оно отделяет сознательное отключение от технического сбоя и предотвращает применение
новых условий к прошлым датам. Это проектные решения, а не предписания авиационных стандартов.

### Вопросы на границах подсистем
