# 07. Регламентные работы

Подсистема предназначена для планирования и учёта обслуживания ИТ-ресурсов:
обновления программ, замены сертификатов, проверки резервных копий и других
технических работ. Она хранит план, согласования, сроки и результаты обслуживания.
Технические действия выполняет специалист и подтверждает их результат в системе.

Основание описания — требования СТ-РР-01–СТ-РР-12 из
[системной спецификации](requirements/system.md) и ТП-РР-01–ТП-РР-24 из
[спецификации ПО](requirements/software.md).

## 7.1 Порядок работы

1. Специалист создаёт план: выбирает ресурсы, описывает действия и проверку
   результата, назначает исполнителя и сроки.
2. Система определяет затронутые ресурсы, проверяет допустимое время и пересечения
   с другими работами. Специалист рассматривает предупреждения.
3. План проходит согласование по правилам §7.5. Подготовленный план публикуется,
   владельцы ресурсов получают уведомление.
4. Исполнитель подтверждает начало и выполняет обслуживание.
5. Исполнитель указывает результат каждого ресурса. Система сохраняет итоги,
   обновляет состояния ресурсов и передаёт события для оповещений.

Плановые работы проходят эту последовательность. Для аварийных работ предусмотрено
начало по решению руководителя ИТ-отдела с последующим согласованием.
Повторяемые работы создаются из шаблона по расписанию.

| Понятие | Определение |
|---|---|
| Окно работ | Запись об одном выполнении обслуживания: план, участники, сроки и результаты |
| Плановый интервал | Время от планового начала до планового окончания работ |
| Ресурс работ | Ресурс, выбранный для обслуживания |
| Затронутый ресурс | Ресурс работ, зависимый от него ресурс или сосед по серверу |
| Шаблон работ | Описание обслуживания и расписание создания отдельных окон |
| Редакция плана | Сохранённый набор условий работ |
| Учётное состояние | Состояние ресурса, записанное в реестре |

Подсистема использует общее хранилище, очередь и планировщик из
[архитектуры системы](03-architecture.md). Обмен данными организован следующим образом.

| Подсистема | Получаемые данные | Передаваемые данные |
|---|---|---|
| Реестр ресурсов | Ресурсы, владельцы, подразделения и состояния | Состояния ресурсов после начала и завершения |
| Граф зависимостей | Затронутые ресурсы, основания включения и полнота расчёта | Выбранные ресурсы работ |
| Согласование | Решения участников маршрута | План, расчёт влияния и список согласующих |
| Оповещения | История уведомлений для показа в карточке | События публикации, изменения, начала и результата |
| Связь с системой задач | Ссылка на задачу, состояние передачи и ошибка | Запрос создания задачи, изменения плана и результат |

## 7.2 Данные работ

### Окно работ

| Данные | Содержание |
|---|---|
| Идентификатор и название | Постоянный идентификатор записи и название обслуживания |
| Описание | Цель, действия, способ проверки результата и порядок возврата к прежней конфигурации, если он предусмотрен |
| Срочность | Плановые или аварийные работы |
| Состояние выполнения | Текущее состояние по §7.3 |
| Плановые сроки | Начало, окончание и часовой пояс |
| Фактические сроки | Время подтверждённых начала и завершения |
| Исполнитель | Действующий специалист или руководитель ИТ-отдела |
| Подразделение-инициатор | Подразделение создателя разовых работ или подразделение из шаблона |
| Ожидаемая недоступность | Признак недоступности при обслуживании; последствия для ресурсов описываются в плане |
| Ресурсы | Выбранные для обслуживания ресурсы |
| Согласование | Необходимость согласования, его состояние и маршрут |
| Редакция плана | Номер сохранённого набора условий работ |
| Версия записи | Номер для проверки одновременных изменений |
| Основание повторения | Шаблон, его редакция и исходные дата и время выполнения по расписанию |
| Результат | Общий результат, результаты ресурсов и пояснения исполнителя |
| Аварийное основание | Причина начала в аварийном порядке |
| История | Автор и время действия, прежние и новые значения, причины исключений |

Черновик допускает неполные данные. Для публикации и начала обязательны название,
описание действий и проверки, срочность, корректный плановый интервал, подразделение,
действующий исполнитель, признак ожидаемой недоступности и хотя бы один существующий
ресурс. Эти условия действуют и при аварийном начале. Подразделение-инициатор
сохраняется на весь срок существования окна.

Изменение цели, действий, сроков, исполнителя, срочности, ресурсов или оценки
недоступности до начала создаёт новую редакцию плана. Каждое сохранённое изменение
увеличивает версию записи. Прежние редакции и решения сохраняются в истории.
Изменения реестра учитываются повторной проверкой по §7.5.

### Сведения о ресурсе в окне

Один ресурс включается в окно один раз. При начале система записывает его прежнее
состояние, предыдущее окно непрерывного обслуживания и основание восстановления.
Основание восстановления — подтверждённое состояние ресурса до непрерывного периода
обслуживания. Эти сведения вычисляются системой по правилам §7.3 и сохраняются
неизменными. При завершении исполнитель указывает результат, выполненную проверку,
пояснение и итоговое состояние ресурса.

### Шаблон работ

Шаблон содержит название, описание, ресурсы, исполнителя, подразделение-инициатора,
оценку недоступности, расписание, часовой пояс, длительность, срок предварительного
создания, признак активности и редакцию. Длительность задаётся положительным целым
числом минут, срок предварительного создания — неотрицательным целым числом минут.
Подразделение определяется по создателю шаблона. Каждое созданное окно получает
копию условий шаблона и срочность «Плановые».

### Расчёт влияния

Расчёт влияния содержит исходные и найденные ресурсы, основания включения,
владельцев, подразделения, критичность, среду использования, время расчёта,
признак полноты и причину ограничения. Решение согласующего относится к конкретным
редакции плана и расчёту. Сохранённые расчёты остаются в истории.

## 7.3 Выполнение работ

### Состояния и переходы

| Исходное состояние | Действие или условие | Следующее состояние |
|---|---|---|
| Черновик | Передать заполненный план на обязательное согласование | На согласовании |
| Черновик | Опубликовать заполненный план, для которого согласование не требуется | Запланировано |
| На согласовании | Получить все обязательные положительные решения по актуальному плану | Запланировано |
| На согласовании | Получить отрицательное предварительное решение | Отклонено |
| На согласовании или запланировано | Изменить план или обновить значимые данные расчёта; требуется согласование | На согласовании |
| На согласовании или запланировано | Изменить план или обновить значимые данные расчёта; согласование не требуется | Запланировано |
| Запланировано | Подтвердить обычное начало после успешных проверок | Выполняется |
| Черновик, на согласовании или запланировано | Подтвердить аварийное начало по §7.5 | Выполняется |
| Черновик, на согласовании или запланировано | Отменить работы с указанием причины | Отменено |
| Выполняется | Подтвердить результаты и допустимые итоговые состояния всех ресурсов | Завершено |

Публикация — переход в состояние «Запланировано». Редактирование черновика сохраняет
его состояние. «Завершено», «Отклонено» и «Отменено» — конечные состояния.
Повторные работы оформляются новым окном.

Отмена применяется до начала. Она прекращает действующий предварительный маршрут
согласования и сохраняет ранее принятые решения в истории. При отмене и отклонении
состояния ресурсов сохраняются, фактические сроки и результаты остаются пустыми.
Прекращение уже начатых работ оформляется завершением с фактическим результатом.

### Начало

Обычное начало подтверждает назначенный исполнитель либо руководитель ИТ-отдела
с указанием основания замещения. Оно разрешено внутри планового интервала.
Для начала вне этого интервала требуется изменить план или применить аварийный порядок.
До подтверждения начала окно остаётся запланированным, в том числе после наступления срока.

Система проверяет полномочия, обязательные данные, актуальность расчёта и согласования,
время, состояния ресурсов и отсутствие другого выполняемого окна над тем же ресурсом.
Допустимые исходные состояния — «На складе», «Используется», «Ожидает приёмки»
и «На обслуживании», с учётом ограничений типа из
[модели ресурсов](02-domain-model.md), §2.4.

При успешном начале система записывает фактическое время и прежние состояния,
переводит выбранные ресурсы в состояние «На обслуживании». Состояния зависимых
ресурсов и соседей по серверу сохраняются.

### Повторное обслуживание

| Состояние перед началом | Основание восстановления |
|---|---|
| Ресурс находится в допустимом состоянии, отличном от обслуживания | Состояние непосредственно перед началом; ссылка на предыдущее окно отсутствует |
| Ресурс остался в обслуживании после последнего завершённого окна и с тех пор сохранял это состояние | Основание из предыдущего окна, включая пустое; сохраняется ссылка на это окно |
| Ресурс находится в обслуживании, подходящая история отсутствует | Основание и ссылка на предыдущее окно остаются пустыми |

Непрерывность обслуживания подтверждается журналом изменений отдельно для каждого
ресурса. В расчёте участвует только последнее завершённое окно этого ресурса.
Основание вычисляется при сохранении начала.

Например, ресурс ожидал приёмки, затем прошёл неудачное обслуживание и остался
в обслуживании. При успешных повторных работах подтверждённое основание позволяет
вернуть его в ожидание приёмки. Выход из обслуживания между попытками прерывает
наследование этого основания.

### Завершение

| Результат ресурса | Условие и итоговое состояние |
|---|---|
| Успешно | Действия выполнены, проверка подтверждена; исполнитель выбирает допустимое итоговое состояние |
| Частично | Выполнена часть действий или проверок; ресурс остаётся в обслуживании, записываются причина и оставшиеся действия |
| Неудачно | Цель не достигнута, восстановление не подтверждено; ресурс остаётся в обслуживании, записываются причина и дальнейшее действие |
| Прежняя конфигурация восстановлена | Изменения отменены, восстановление проверено; исполнитель выбирает допустимое итоговое состояние |

Завершение требует результата, сведений о проверке и допустимого итогового состояния
каждого ресурса. Для невыполненной проверки указывается причина. При успехе или
восстановлении прежней конфигурации система предлагает известное основание
восстановления. Исполнитель подтверждает предложенное состояние или выбирает другое
допустимое. При пустом основании состояние выбирается явно.

Итоговый переход проверяется по общей модели ресурсов. Состояние «Используется»
требует действующего владельца. Возврат в «Ожидает приёмки» разрешён при таком же
подтверждённом основании восстановления и результате «Успешно» или «Прежняя
конфигурация восстановлена». Частичный и неудачный результаты сохраняют обслуживание.

Если результаты всех ресурсов совпадают, общий результат окна равен этому значению.
При разных результатах общий результат — «Частично». После завершения история окна
сохраняется неизменной; дальнейшие действия с ресурсами выполняются по общей модели.

### Сохранение изменений

Начало и завершение сохраняют состояние окна, фактическое время, состояния ресурсов,
историю и исходящие события одной операцией. При ошибке вся операция отклоняется.
Проверка одновременного обслуживания и запись начала выполняются совместно.
Пока окно выполняется, система отклоняет изменения состояний его ресурсов другими
операциями, включая импорт. События передаются внешним подсистемам после сохранения.

Каждое изменяющее действие имеет идентификатор операции. Для существующей записи
указывается ожидаемая версия. После проверки доступа система проверяет повтор: для уже выполненной операции
с теми же данными возвращает сохранённый результат. Повторное использование
идентификатора с другими данными отклоняется. Для новой операции проверяются
версия и условия выполнения; устаревшая версия отклоняется с сообщением о конфликте.

### Нарушение сроков

| Условие | Нарушение |
|---|---|
| Окно запланировано, текущее время позже планового начала с учётом допуска | Пропущен срок начала |
| Окно выполняется, текущее время позже планового окончания с учётом допуска | Превышен срок окончания |
| Решение ожидается дольше контрольного срока согласования | Просрочено согласование |

Допуск задаётся администратором; предварительное значение — ноль. Нарушения сроков
показываются отдельно от состояния выполнения. После начала плановые сроки неизменны.
Контрольный срок согласования и период проверок подлежат согласованию до реализации.

## 7.4 Затронутые ресурсы

Расчёт выполняет [модуль графа](06-graph.md). Результат состоит из трёх групп.

| Группа | Основание включения |
|---|---|
| Ресурсы работ | Непосредственно выбраны для обслуживания, включая ресурсы без связей |
| Зависимые ресурсы | Найдены при обходе связей зависимости и размещения против их направления |
| Соседи по серверу | Размещены на той же машине, что и ресурс работ |

Если приложение зависит от базы данных, обслуживание базы затрагивает приложение.
Обслуживание сервера затрагивает размещённые на нём ресурсы и их зависимые ресурсы.
Обход продолжается до исчерпания достижимых ресурсов. Каждый ресурс включается
один раз с сохранением всех оснований; циклы обрабатываются без повторов.
Для перезагрузки машины ресурсом работ указывается сама машина.

Влияние распространяется по связям зависимости и размещения. Соседи показываются
отдельной группой потенциального влияния. Ожидаемую недоступность описывает
исполнитель в плане. Полнота расчёта определяется по внесённым связям этих типов.
Ограничения изображения графа, фильтры и размер страницы действуют только на показ.

Расчёт выполняется при изменении плана, перед согласованием, созданием события
оповещения и началом. Значимые данные расчёта — состав ресурсов, владельцы,
подразделения, критичность и среда использования. Их изменение до начала требует
повторной проверки согласования по §7.5. Просмотр расчёта сохраняет состояние окна.
После начала новые сведения используются для оповещений; прежние решения остаются
в истории. Изменение исходных данных между проверкой и записью начала приводит
к отклонению операции целиком.

Для неполного расчёта показывается причина. Система разрешает сохранить черновик
и отклоняет обычное согласование и начало. Аварийное начало требует подтверждения
неполноты руководителем; это подтверждение передаётся с событием.

## 7.5 Согласование и доступ

### Условия согласования

Проверяются все три группы затронутых ресурсов и серверы их цепочек размещения.

| Условие | Согласующий |
|---|---|
| Критический ресурс | Руководитель ИТ-отдела |
| Ресурс рабочей среды | Руководитель ИТ-отдела |
| Отсутствует действующий владелец | Руководитель ИТ-отдела |
| Подразделение ресурса отличается от подразделения-инициатора | Владелец ресурса; при его отсутствии — руководитель ИТ-отдела |

Каждый согласующий включается в маршрут один раз. Вместо создателя или исполнителя
работ назначается другой руководитель ИТ-отдела. При отсутствии подходящего
согласующего обычное начало отклоняется. Администратор может дополнять перечисленные
условия согласования; обязательные условия сохраняются.

Согласование имеет состояния «Не требуется», «Ожидается», «Согласовано» и «Отклонено».
Оно действительно при положительном решении каждого обязательного участника
по текущей редакции плана и актуальному расчёту влияния.

### Изменение плана и повторная проверка

До начала специалист может изменить план. Для уже переданного или опубликованного
плана система заново проверяет обязательные данные, расчёт и условия согласования.
Неполные данные приводят к отказу в сохранении. Если согласование требуется,
устанавливаются состояния «На согласовании» и «Ожидается»; иначе — «Запланировано»
и «Не требуется». Прежние решения сохраняются в истории. Получатели опубликованного
плана уведомляются об изменении, включая возврат на согласование.

При изменении значимых данных реестра предварительное решение или обычное начало
отклоняется с причиной и предложением выполнить действие «Проверить согласование».
Оно доступно специалисту и руководителю для окон «На согласовании» и «Запланировано».

| Результат повторной проверки | Действие системы |
|---|---|
| Значимые данные прежние | Сохраняет действующие расчёт, маршрут, решения и версию записи |
| Расчёт неполный или данные плана недопустимы | Отклоняет операцию с причиной |
| Данные изменились, согласование требуется | Сохраняет новый расчёт и маршрут, устанавливает «На согласовании» и «Ожидается» |
| Данные изменились, согласование не требуется | Сохраняет новый расчёт, устанавливает «Запланировано» и «Не требуется», прекращает действующий маршрут |

При повторной проверке редакция плана сохраняется. При изменении только времени
расчёта действующее решение сохраняется.
Новый расчёт, маршрут, состояния, версия и события записываются совместно.
Для нового маршрута создаётся запрос решения, для ранее опубликованного плана —
событие изменения. Повтор с теми же данными использует сохранённый результат.
Предварительное решение принимается только по текущему маршруту и его расчёту;
решение по прежнему маршруту отклоняется.

После начала плановые условия и состав ресурсов сохраняются неизменными.
Дополнительные работы оформляются отдельным окном с проверкой пересечений.

### Аварийное начало

Аварийное начало разрешено руководителю ИТ-отдела. Он указывает причину срочности,
заполняет обязательные данные и подтверждает предупреждения, включая неполный расчёт.
Ограничение одного выполняемого окна на ресурс действует и в этом случае.

Вместе с началом сохраняются редакция плана, исполнитель, известные затронутые
ресурсы, предупреждения и запрос обязательного последующего согласования
в состоянии «Ожидается». Решение принимают участники по правилам этого раздела.
Отрицательное решение записывается с причиной и направляется исполнителю
и руководителю. Фактические сроки, состояния и результаты работ сохраняются.

### Полномочия

| Действие | Пользователь |
|---|---|
| Создать или изменить план до начала; проверить согласование; отправить дополнительное сообщение | Специалист или руководитель ИТ-отдела |
| Отменить работы до начала | Специалист — создатель или исполнитель окна; руководитель — для любого окна в своей области доступа |
| Подтвердить обычное начало и результат | Исполнитель; руководитель с указанием основания замещения |
| Подтвердить аварийное начало | Руководитель ИТ-отдела |
| Принять решение по согласованию | Участник текущего шага маршрута |
| Изменить правила, шаблоны, расписания и допуски | Руководитель ИТ-отдела |
| Прочитать данные | Пользователь в своей области доступа; аудитору доступно чтение |

Сервер проверяет полномочия при каждом обращении, включая повтор операции.
Карточки, описания и уведомления содержат сведения в пределах текущего доступа.
При невозможности безопасно показать описание используется общее сообщение
без названий и ссылок на закрытые ресурсы.

## 7.6 Допустимое время обслуживания

Плановый интервал включает начало и исключает окончание. Начало строго предшествует
окончанию. Время хранится по всемирному координированному времени и показывается
в выбранном часовом поясе. Фактическое время записывает сервер при подтверждении
действия; окончание допускается только в момент начала или позже.

Для ресурса можно задать часовой пояс и разрешённые недельные интервалы: день
начала, время начала и окончания. Окончание раньше начала по местным часам означает
следующие сутки. Равные значения отклоняются. При отсутствии правила обслуживание
доступно в любое время.

Плановый интервал должен целиком входить в разрешённое время каждого ресурса работ.
Выход за границы показывается предупреждением. Для передачи плана на согласование,
публикации и изменения уже переданного плана требуется указать причину исключения.
Она сохраняется для согласующего. Черновик допускает неподтверждённое предупреждение.
Дальнейшие действия подчиняются общим правилам согласования и начала.

## 7.7 Пересечение работ

Интервалы пересекаются, если начало каждого раньше окончания другого.
Интервалы 02:00–03:00 и 03:00–04:00 считаются смежными. Проверяются запланированные
и выполняемые окна, кроме самого изменяемого окна. Выполняемое окно учитывается
как продолжающееся до фактического завершения.

При пересечении времени конфликт возникает по общему ресурсу работ или серверу
размещения. Для вложенного размещения учитывается вся известная цепочка, включая
сам ресурс, если это сервер или виртуальная машина. Неполнота цепочки показывается
в предупреждении. Причина продолжения при конфликте обязательна на этапах из §7.6;
вместе с ней сохраняются ссылки на конфликтующие окна.

Одновременно над одним ресурсом выполняется не более одного окна. Из одновременных
попыток начала успешно завершается не более одной. Совместные действия над ресурсом
учитываются одним окном. Пересечение по общему серверу требует подтверждения
предупреждения; совместимость действий над разными ресурсами оценивает специалист.

## 7.8 Повторяемые работы

Расписание содержит пять полей: минута, час, день месяца, месяц и день недели.
Для них задаются значения, диапазоны, списки, шаг или все значения. День недели
задаётся числом от 0 до 6, где 0 — воскресенье. Одновременно ограничивать день месяца
и день недели запрещено. Перед сохранением показываются ближайшие даты
в часовом поясе шаблона.

За установленный срок до очередной даты планировщик создаёт окно. Плановое окончание
вычисляется прибавлением длительности к началу. При полных данных и расчёте,
допустимом времени и отсутствии неподтверждённых пересечений окно передаётся
на согласование или публикуется по правилам §7.5.

Неполные данные, неполный расчёт или предупреждение оставляют окно черновиком
с указанием причины. Специалист исправляет данные или подтверждает предупреждение
в этом окне, затем отдельно передаёт план на согласование или публикует его.
Все условия проверяются повторно. Начало подтверждает уполномоченный пользователь.

Исходный момент выполнения — дата и время по расписанию при создании окна.
Он сохраняется при переносе плановых сроков. Для пары шаблона и исходного момента
существует одно окно. Создание окна и отметка
обработанной даты сохраняются совместно, включая создание черновика. Повторный
запуск использует существующее окно и сохраняет его состояние.

| Событие | Обработка расписания |
|---|---|
| Сбой сохранения | Дата остаётся необработанной и повторяется при следующем запуске |
| Восстановление после сбоя | Обрабатываются пропущенные даты начиная с последней успешной; прошедшие сроки показываются как пропущенные |
| Изменение или отключение шаблона | Условия созданных окон сохраняются; перенос и отмена выполняются отдельно |
| Повторное включение шаблона | Обрабатываются даты начиная с включения; период отключения пропускается |
| Изменение расписания | Новая редакция применяется к ещё не созданным окнам с исходным моментом начиная со времени изменения; более ранние необработанные даты относятся к прежней редакции |
| Отсутствующее местное время при переводе часов | Дата пропускается с записью причины и сообщением исполнителю |
| Повторённое местное время | Используется один раз, по первому соответствующему моменту |

Периоды активности и редакции определяются по истории шаблона. Предварительный
просмотр и планировщик используют одинаковые правила времени и часовой пояс шаблона.

## 7.9 Оповещения

Подсистема работ сохраняет события с идентификатором, окном, редакцией плана,
временем и ссылкой на расчёт влияния. Для начала передаётся оценка недоступности,
для завершения — результаты ресурсов, для просрочки — её вид. Каналы, важность
сообщений и доставку определяет
[подсистема оповещений](05-notifications.md), §5.9–5.10.

| Событие | Получатели |
|---|---|
| Публикация или возврат в «Запланировано» | Владельцы затронутых ресурсов |
| Изменение опубликованного плана или значимых данных расчёта | Текущие и прежние получатели окна |
| Напоминание | Владельцы затронутых ресурсов и исполнитель |
| Подтверждённое начало | Владельцы затронутых ресурсов |
| Завершение с общим результатом «Успешно» или «Прежняя конфигурация восстановлена» | Прежние получатели и текущие владельцы затронутых ресурсов |
| Завершение с частичным или неудачным результатом | Те же получатели и руководитель ИТ-отдела |
| Отмена или отклонение ранее опубликованного плана | Прежние получатели; сообщение содержит причину |
| Пропущенное начало или превышенное окончание | Исполнитель и руководитель ИТ-отдела |
| Запрос согласования | Участник текущего шага маршрута |
| Просрочка согласования | Согласующий и руководитель ИТ-отдела |
| Отрицательное последующее решение по аварийным работам | Исполнитель и руководитель ИТ-отдела |
| Подтверждённый выход за разрешённое время | Руководитель ИТ-отдела |
| Дополнительное сообщение специалиста с причиной | Текущие владельцы затронутых ресурсов и прежние получатели |

Владельцы определяются для всех трёх групп §7.4, включая ресурсы без связей.
Отсутствующего владельца заменяет руководитель ИТ-отдела. Отрицательное предварительное
решение передаётся исполнителю механизмом согласования. Для аварийного начала
событие начала создаётся непосредственно при его подтверждении.

Предварительные сроки напоминаний — за семь суток и за одни сутки до начала.
При поздней публикации создаются только будущие напоминания. После переноса прежние
необработанные напоминания снимаются. Перед отправкой проверяются редакция
и состояние окна. Напоминание однозначно определяется окном, редакцией и сроком.
Запрос решения содержит маршрут; запрос по заменённому или прекращённому маршруту
снимается с отправки. Проверяется также актуальность связанного расчёта.

Для одного события пользователь получает одну внутреннюю запись со списком доступных
ему ресурсов. Все сработавшие правила и прежние получатели сохраняются в истории
оповещений. Повторная обработка использует эту запись. Изменение, отмена и завершение
передаются отдельными сообщениями. Оповещение о смене состояний ресурсов в рамках окна
входит в сообщение окна. Перед внешней отправкой повторно проверяются актуальность и доступ.
Уже отправленное сообщение уточняется новым сообщением о переносе или отмене.

## 7.10 Работа пользователя

Специалист открывает список работ с фильтрами по сроку, состоянию, исполнителю,
ресурсу и согласованию. Форма плана показывает затронутые ресурсы, основания
включения, полноту расчёта, пересечения и необходимость согласования.
Каждое предупреждение содержит причину и условие продолжения.

Карточка окна показывает плановые и фактические сроки, часовой пояс, редакцию плана,
исполнителя, согласования, результаты, внешнюю задачу, состояние передачи и историю
уведомлений. Доступные действия определяются полномочиями из §7.5. При устаревшем
расчёте показываются причина отказа в начале и действие «Проверить согласование».
Отмена требует причины, завершение — результатов и проверок каждого ресурса.

В карточке ресурса раздел «Работы» содержит планы и историю с основанием включения.
Сводные списки отдельно показывают просроченные планы, незавершённые согласования
и ресурсы, оставшиеся в обслуживании. Состав сведений ограничивается доступом пользователя.

### Связь с системой задач

При первой публикации создаётся запрос на одну основную внешнюю задачу для окна.
При аварийном начале запрос сохраняется вместе с началом, если задачи ещё нет.
Дальнейшие согласования, изменения сроков, отмена и результат обновляют связанную
задачу через [подсистему связи с системой задач](08-task-tracker.md), §8.4–8.6.

Связь хранит подключение и постоянный идентификатор внешней задачи. Состояние передачи,
ошибка и расхождение состояний показываются исполнителю. Изменение внешней задачи
обновляет сведения о ней; начало и завершение работ подтверждаются в системе учёта.
При отказе внешнего подключения сведения о работах сохраняются. При потере
ответа на создание подсистема связи выясняет результат прежней попытки; неизвестный
результат требует сверки перед повторным созданием.
