# 04. Интеграции

## 4.1 Принципы

- Все внешние системы подключаются через **абстракцию коннектора** — доменный код не знает,
  что за трекер или облако стоит по ту сторону.
- Любая синхронизация **идемпотентна** и повторяема: повторный запуск не создаёт дублей.
- Внешние ID хранятся в самой записи (`external_id`, `external_system`), связь никогда не
  восстанавливается «по имени».
- Отказ внешней системы не ломает основную работу: интеграции деградируют мягко,
  ошибки попадают в журнал синхронизаций и на экран «Интеграции».

## 4.2 Таск-трекер

### Зачем

Заявки на ресурсы, закупки, инвентаризация и офбординг — это работа, которая уже ведётся
в трекере. Система не заменяет его, а **связывает учётную запись ресурса с задачей**.
Подробный договор подключения, порядок обработки и проверяемые случаи приведены в
[разделе 08](08-task-tracker.md).

### Сценарии

| Событие в системе | Действие в трекере |
|---|---|
| Заявка согласована | Создать задачу в настроенном проекте с описанием, заявителем и ссылкой на заявку; ресурс может ещё не существовать |
| При ежедневной проверке срок лицензии, гарантии или сертификата наступает не позднее чем через 30 суток | Создать задачу на продление с датой окончания; пропущенный срок также обрабатывается по правилам §8.2 раздела 08 |
| Начат расчёт по ресурсам с увольняемым сотрудником | Создать задачу с перечнем действующих закреплений; его изменения передавать в ту же задачу |
| Ресурс переведён в `maintenance` вне окна работ | Создать отдельную задачу обслуживания; для изменения внутри окна используется задача окна |
| Окно впервые опубликовано или начато в аварийном порядке | Создать одну основную задачу на окно; повторное согласование новую задачу не создаёт |
| Окно изменено, завершено или отменено | Обновить связанную задачу: сроки, результат по ресурсам либо причина отмены |
| Инвентаризация выявила расхождение | Создать задачу на разбор по каждому расхождению |

| Событие в трекере (вебхук) | Действие в системе |
|---|---|
| Задача заявки закрыта | Выполнить целевое действие и перевести заявку в `done` при допустимом переходе и наличии полномочий; при отказе данные остаются прежними |
| Задача заявки отменена | Перевести заявку в `cancelled` при допустимом переходе и наличии полномочий |
| Изменён исполнитель | Обновить ответственного при однозначном сопоставлении с действующим пользователем, которому разрешена обработка заявки |
| Комментарий добавлен | Отразить в ленте заявки (опционально) |
| Изменена задача окна работ | Сохранить сведения для сверки; не начинать и не завершать работы, не изменять состояния ресурсов |

### Модель связи

`TrackerLink`: `entity_type` (`request` / `resource` / `campaign` / `offboarding` / `maintenance`), `entity_id`,
`integration_id`, `creation_basis`, `role`, `external_id`, `tracker_key` (например, `IT-1234`),
`tracker_url`, `status_mapping_applied_at`.
Внешний идентификатор используется для обмена, ключ и ссылка — для показа.
Пара `(integration_id, external_id)` уникальна. Для заявки, расчёта по ресурсам и окна
работ допускается не более одной основной связи; у ресурса и кампании могут быть
разные задачи по разным основаниям. Поле `creation_basis` отличает срок ресурса,
расхождение или иное основание от повторного события по нему.
Правила приведены в [разделе 08](08-task-tracker.md), §8.4.

### Задачи регламентных работ

Окно работ связано не более чем с одной основной задачей. Основная связь
уникальна по `(entity_type, entity_id)` и указывает подключение и внешнюю задачу. Изменения ресурсов внутри окна передают `maintenance_id`
и не создают отдельных задач обслуживания. Подсистема работ остаётся источником
состояния выполнения; состояние доставки или внешней задачи хранится отдельно.

Создание и обновление выполняются после сохранения исходящего события. Для одного
окна исходящие операции обрабатываются последовательно; устаревшее обновление
не заменяет более новое. При повторной доставке используется тот же идентификатор
операции. Если создание прошло, но ответ потерян, подключение ищет задачу
по устойчивому идентификатору окна либо использует защиту внешней системы от повторов.
Для прочих исходных записей поиск использует точное основание создания, а не только
идентификатор ресурса или кампании. При невозможности однозначной проверки требуется сверка; повторное создание без проверки
запрещено. Правила определены в разделе 07, §7.10.

### Конфигурация подключения

Настраивается администратором в Admin UI: базовый URL, тип трекера, токен сервисной
учётки, проект по умолчанию, тип задачи, маппинг статусов трекера → статусов заявки,
шаблоны заголовка и описания задачи.

### Маппинг статусов (пример)

```
Open, To Do          → in_progress
In Progress          → in_progress
Done, Closed, Resolved → done
Rejected, Won't Do   → cancelled
```

Маппинг задаётся в UI, а не в коде: разные трекеры и разные проекты имеют разные
воркфлоу.
Закрытие внешней задачи завершает заявку только после успешного выполнения её
предметной операции и проверки допустимого перехода. Изменения задачи окна работ
не завершают работы и не меняют состояния ресурсов.

### Поддерживаемые трекеры

Целевой выбирается позже. Абстракция рассчитана на минимальный общий набор операций:
`create_issue`, `get_issue`, `update_issue`, `add_comment`, `verify_event`,
`parse_event`. Подписка на входящие сообщения настраивается для выбранной системы.
Кандидаты: Jira, YouTrack, Yandex Tracker, GitLab Issues, Redmine. Для учебного стенда
разумно начать с одного + заглушка (`mock`), чтобы разрабатывать без внешнего сервиса.

### Надёжность

- Исходящие вызовы — через очередь с ретраями и экспоненциальной задержкой.
- Входящие вебхуки — с проверкой подписи/секрета, дедупликацией по ID события.
- При недоступности внешней системы состояние заявки сохраняется. Ожидание
  создания задачи отражается отдельным состоянием передачи, определённым в §8.5
  [раздела 08](08-task-tracker.md).

## 4.3 Облачные провайдеры (discovery)

### Зачем

Облачные ресурсы создаются быстрее, чем их успевают заводить руками. Импорт даёт
актуальную картину и выявляет «теневые» ресурсы без владельца.

### Сценарий синхронизации

1. По расписанию коннектор выгружает список объектов (ВМ, БД, бакеты, балансировщики).
2. Для каждого объекта ищется `Resource` по `(provider, external_id)`.
3. Для найденного ресурса обновляются технические сведения источника, включая его
   состояние у поставщика. Учётное состояние по §2.4 раздела 02 импорт не меняет.
   Для нового ресурса создаётся запись в `in_stock` с отдельной отметкой
   «обнаружен, требует проверки». Специалист подтверждает владельца и учётное состояние.
4. Отсутствие ресурса в полном успешном перечне поставщика для выбранной области
   создаёт отметку «исчез у поставщика» с сохранением учётной записи.
   Неполный ответ, ошибка доступа и сбой получения не доказывают исчезновение.
5. Метки `owner`, `team`, `project` дают предложение о владельце; назначение
   подтверждает специалист. Предложение не заменяет владельца, указанного человеком.
6. Результат пишется в журнал синхронизации: создано / обновлено / расхождений.

### Важное правило

Импорт **никогда не перетирает поля, заполненные человеком** (владелец, критичность,
комментарий, связи). Он владеет только техническими атрибутами.

Пока над ресурсом выполняются регламентные работы, импорт не изменяет его учётное
состояние. Полученные сведения об остановке или недоступности сохраняются как
сведения источника и не завершают окно работ автоматически.

### Кандидаты коннекторов

Yandex Cloud, AWS, Azure, VK Cloud, on-prem виртуализация (Proxmox/oVirt/vSphere),
Kubernetes (через API кластера). Приоритет определяется позже.

## 4.4 SSO / каталог сотрудников

- **OIDC** для входа: маппинг claim → пользователь, автосоздание при первом входе.
- **LDAP / HR-система** для оргструктуры: подразделения, руководители, статус занятости.
  Сведения об увольнении запрещают вход и запускают расчёт по ресурсам;
  незавершённый возврат не препятствует запрету входа (раздел 02, §2.5).
- Роли в системе не наследуются из SSO автоматически (кроме опционального маппинга групп) —
  назначаются администратором.

## 4.5 Мессенджеры и почта

Каналы доставки оповещений — см. `05-notifications.md`. С точки зрения интеграций это
такие же коннекторы: SMTP, Telegram Bot API, Mattermost/Slack webhook.

## 4.6 Журнал синхронизаций

Единая сущность `SyncRun` для всех коннекторов: `integration_id`, `started_at`,
`finished_at`, `status`, `items_created`, `items_updated`, `items_failed`, `error_summary`.
Экран «Интеграции» показывает последние запуски, ошибки и кнопку ручного запуска.
