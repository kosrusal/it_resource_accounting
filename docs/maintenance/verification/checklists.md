## 1. Применение

Перечень подготовлен для задачи [#33](https://github.com/kosrusal/it_resource_accounting/issues/33).
Он применяется к двум типам: разделу бизнес-требований и тематическим системным
требованиям. Для бизнес-требований используются общие вопросы и вопросы Б-01–Б-02;
для системных — только общие. Этот перечень не заменяет общую процедуру команды
и не объявляется утверждённым примером преподавателя.

Основания: [стандарт требований](../../process/requirements-standard.md), редакция 0.2;
[правила именования](../../process/naming-and-tracing.md), §1–2;
[план управления конфигурацией](../../process/configuration-management.md), §2;
[ИН-05](../../process/procedures.md#ин-05-рассмотрение-результата);
[постановка проверки](../../testing/business-requirements.md), §2–3;
[языковые правила](../../../AGENTS.md).
В таблицах они обозначены кратко: «Стандарт», «Именование», «КУ» и «ИН-05».
Точные проверенные редакции перечислены в протоколе.

Из семинара 24.10.2026 взяты формальная и экспертная части (37:30, 38:07),
реализуемость и необходимость разового протокола (47:30–48:14).
Остальные свойства взяты из опубликованного стандарта команды; неразборчивое
свойство из речи преподавателя не восстанавливалось по догадке.
Критерии требований низкого уровня и авиационной сертификации на постановку
не переносятся. Отсутствие программы не считается отсутствием документа.

## 2. Порядок проверки

До рассмотрения зафиксировать путь, редакцию, состояние, автора и идентификатор Git
каждого объекта. Выделить применимые правила и входные пожелания заказчика.
Затем прочитать весь документ, ответить на каждый вопрос и привести проверяемое
основание: место в тексте, результат подсчёта или источник.

Ответы — «Да» или «Нет». «Нет» означает нарушение либо отсутствие достаточных
свидетельств; причина указывается явно. Каждому «Нет» соответствует замечание.
Нельзя заменять отсутствие доказательства ответом «Да». Не относящиеся к типу
документа вопросы исключаются до заполнения; критерии двух типов приведены отдельно.

Рассмотрение оценивает содержание. Анализ получает числа — количество требований,
источников и связей. Испытание проверяет работающую программу. Наличие описания
будущего испытания не считается его выполнением. Число найденных связей не заменяет
оценку их смысла.

После проверки зарегистрировать замечания и требуемые исправления, не исправляя
объект внутри той же проверки. Исправление выполняется отдельной работой автора.
Повторная проверка получает новый номер протокола и ссылается на прежний.
Принятие возможно после устранения замечаний и независимого рассмотрения;
одобрение заказчика фиксируется отдельно. Слияние протокола не меняет состояние требований.
