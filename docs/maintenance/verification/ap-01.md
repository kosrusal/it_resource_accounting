## 1. Состав и метод

Основание — [стандарт требований](../../process/requirements-standard.md), §5.
Проверена фиксация `b610b81fbf4470ce6fc1693d8fb11f8f5fb82d33`. Идентификаторы содержимого —
в [протоколе ПФИ-РР-01](pfi-rr-001.md), §1. Проверяемая пара — шесть требований
в `docs/maintenance/business-requirements.md` и двенадцать в
`docs/requirements/maintenance-system.md`. Остальные документы — контекст,
а не дополнительные элементы знаменателя.

Строкой требования считается строка таблицы, первый столбец которой целиком
совпадает с обозначением БТ-РР-NN или СТ-РР-NN. Упоминания номеров в пояснениях
не считаются новыми требованиями. Заполненное поле «Источник» считается явной
связью только после проверки существования и смысла указанного основания.
При отсутствии поля явная связь не восстанавливается по сходству текста.

Подсчёт выполнен программно по копиям, чьи идентификаторы Git совпали с полученными
из хранилища. [Числовые данные](measurements.json) содержат результат.
[Средство подсчёта](measure.py) позволяет повторить его по зафиксированной версии
в локальной копии репозитория. Проверка содержимого не требует сети.

28:31–30:54 и 45:27. Строки ниже — аналитическая разбивка для этой проверки,
а не новые номера бизнес-требований.

|---|---|---|
| Сведения для обслуживания, копии и график | БТ-РР-01–02 | Есть; права и ведение ещё требуют уточнения. |

| Ведение сведений в ходе обычной работы без отдельного сотрудника | Нет отдельного положения | Не отражено в организации действий специалиста. |
| Работа по обслуживанию со своей пошаговой инструкцией | Нет | Не отражено; наличие документа о процедуре само по себе не создаёт работу. |

Упоминание ресурса не считается доказательством, что специалист получит все
материалы именно выбранного сервиса. Сохранение инструкции не считается
ведением отдельной работы по ней. Новые пожелания не превращаются в требования
до правки автора. Проблема зарегистрирована как ЗРР-01, [#34](https://github.com/kosrusal/it_resource_accounting/issues/34).

## 6. Нижний уровень и пределы анализа

В проверенной фиксации каталог `docs/requirements/` содержит `system.md` и
`maintenance-system.md`. Файл `maintenance-software.md` отсутствует.
Дополнительный поиск `ТП-РР` в основной ветке результатов не дал.
Для 12 рассматриваемых СТ предъявлено 0 уточнений уровня ПО; записанное покрытие
СТ → ТП в предъявленном комплекте равно 0/12 = 0 %.
Долю ТП без источника вычислять нельзя: знаменатель равен нулю.
Это отсутствие предъявленного уровня, а не положительный результат проверки
пустого набора. Другие ветки не объявляются проверенными.

Сводные СТ-РР-01, 03 и 04 существуют в [общем документе](../../requirements/system.md).
Они не входят в эти двенадцать строк и не считаются требованиями к ПО.
Полная инспекция сводного документа и всего проекта этой задачей не проведена.
Отсутствие ТП зарегистрировано отдельно: ЗРР-06, [#39](https://github.com/kosrusal/it_resource_accounting/issues/39).

Испытания и измерение времени работы программы не выполнялись. Анализ состава
документа не доказывает скорость, надёжность или готовность приложения.
Исполнитель участвовал в подготовке исходных текстов; требуемая §5 независимость
анализа не подтверждена. Результаты доступны для перепроверки; ЗРР-07 остаётся открытым.

## 7. Воспроизведение

В локальной копии репозитория, содержащей проверенную фиксацию, выполнить:

```bash
python3 docs/maintenance/verification/measure.py
```

Средство читает именно указанную фиксацию, а не текущую рабочую копию, проверяет
идентификаторы содержимого и выводит измерения в JSON. Несовпадение содержимого,
отсутствие Git или нужной фиксации завершают проверку с ошибкой.
Смысловые соответствия и ответы инспекции программа не оценивает.
