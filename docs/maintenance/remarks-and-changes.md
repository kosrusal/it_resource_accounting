# Учёт замечаний и запросов на изменение

Редакция 0.1. Проект порядка для рассмотрения командой.
Ответственный за ведение учёта: Байбурин Марсель.

## 1. Какие записи учитываются

Замечание фиксирует обнаруженный недостаток документа или результата работы.
Запрос на изменение фиксирует предлагаемый способ исправления либо изменение
согласованного решения. Несколько замечаний могут устраняться одним изменением;
связи между ними сохраняются.

Это порядок работы команды с её материалами. Он не задаёт обслуживание серверов
и не добавляет функций системе учёта ИТ-ресурсов. Процедуру инспекции, стандарт
требований и правила слияния готовят назначенные за них участники; данный документ
определяет только учёт полученных замечаний и решений.

Рабочие записи ведутся в очереди команды в Яндекс Трекере. Адрес очереди и
соответствие приведённых ниже состояний её настройкам определяются ответственным
за настройку. До этого таблицы служат формой подготовки записей, а не свидетельством
создания задач. Настройка очереди этим документом не изменяется.

## 2. Состав записи

| Поле замечания | Что записывается |
|---|---|
| Номер, автор, дата | Номер рабочей записи, кто и когда обнаружил недостаток. |
| Объект и редакция | Путь документа, идентификатор версии Git, раздел либо номер требования. |
| Наблюдение | Что именно написано, отсутствует или не соответствует проверяемому условию. |
| Основание | Применимое правило, задача или ожидаемый результат; при отсутствии согласованного правила — вопрос для решения, а не установленное нарушение. |
| Значимость | Чем недостаток мешает: пониманию, выполнению действия, проверке либо оформлению. |
| Ответственный и состояние | Кто рассматривает замечание, текущее состояние и следующий шаг. |
| Решение | Исправить, отклонить с причиной или связать с уже существующим замечанием. |
| Подтверждение закрытия | Изменённая редакция, результат повторной проверки, имя проверяющего и дата. |

| Поле запроса на изменение | Что записывается |
|---|---|
| Основание | Номера замечаний или отдельное поручение. |
| Предлагаемое изменение | Что меняется и какой результат требуется получить. |
| Область | Разрешённые файлы и положения; связанные документы других авторов перечисляются отдельно. |
| Влияние | Какие требования, примеры, ссылки или проверки затрагиваются. |
| Решение по запросу | Кто разрешил, отклонил или отложил изменение и почему. |
| Выполнение | Исполнитель, ветка, версии изменений и запрос на слияние. |
| Проверка | Другой участник, проверяемая версия, замечания и вывод. |
| Завершение | Версия после объединения либо основание закрытия без изменения. |

Исходная формулировка замечания не заменяется после обсуждения: уточнения добавляются
отдельно. Номер закрытой записи не используется для нового замечания. Пароли,
служебные ключи и закрытые данные в записи не помещаются.

## 3. Порядок обработки

| Этап | Исполнитель | Результат |
|---|---|---|
| Зарегистрировать | Участник, обнаруживший недостаток. | Запись с объектом, редакцией, наблюдением и основанием. |
| Проверить полноту | Ответственный за учёт. | Недостающие сведения запрошены; совпадающие записи связаны без потери первоначальных формулировок. |
| Принять решение | Автор затронутого раздела; при межтематическом споре — руководитель команды с ответственными участниками. | Зафиксированы решение, причина, исполнитель и границы разрешённого изменения. |
| Подготовить исправление | Назначенный исполнитель. | Изменения в отдельной ветке со ссылкой на запрос; основная ветка не изменена. |
| Проверить исправление | Участник, который не является автором исправления. | Проверена конкретная версия; устранение замечания подтверждено либо запись возвращена исполнителю с причиной. |
| Объединить и закрыть | Ответственный за объединение; затем ответственный за учёт. | После положительной проверки сохранены версия после объединения и связь с замечанием; запись закрыта. |

Предлагаемые состояния учёта: «Зарегистрировано», «Рассматривается», «В работе»,
«На проверке», «Закрыто». Отклонение и дубликат закрываются только с записанным
основанием; дубликат содержит ссылку на основную запись. При повторно обнаруженном
недостатке запись открывается заново с новой редакцией и причиной.

Разрешение подготовить изменение не является результатом его проверки.
Самопроверка автора и автоматическая проверка разметки не заменяют рассмотрение
другим участником. Новая версия после исправления замечаний передаётся на повторную проверку.
Сам факт объединения также не доказывает, что замечание устранено.

## 4. Границы ответственности

Марсель отвечает за полноту учёта и связь замечания с результатом, но не принимает
технические решения за авторов других направлений. В своей теме он определяет
содержание результата; обязательная проверка перед объединением сохраняется.

При замечании к чужому документу записываются точное место и предлагаемое решение.
Чужой файл не редактируется в рамках исправления материалов по обслуживанию.
Изменение нескольких направлений предварительно распределяется между их авторами;
для каждого указываются собственная область и проверяющий.

## 5. Форма записи и сводка

```text
Вид: замечание / запрос на изменение.
Номер рабочей записи:
Автор и дата:
Документ, версия Git, раздел или номер требования:
Наблюдение либо предлагаемое изменение:
Основание и ожидаемый результат:
Связанные записи:
Разрешённая область изменения:
Решение, кто его принял и дата:
Исполнитель и состояние:
Следующий шаг:
Ветка, версия Git и запрос на слияние:
Проверяющий, проверенная версия и результат:
Основание закрытия:
```

Для промежуточного и итогового отчёта из рабочих записей составляется сводка:

| Номер | Объект | Ответственный | Состояние | Следующий шаг | Подтверждение закрытия |
|---|---|---|---|---|---|

Сводка содержит только существующие записи. Пустой шаблон не означает отсутствие
замечаний, а подготовленное исправление не учитывается как закрытое до проверки.
Проведение инспекции и её общий проверочный перечень относятся к работе
ответственного за проверку результатов, а не подменяются этой формой учёта.
