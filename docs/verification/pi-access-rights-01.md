| Э2 | Раздел 5, вопрос 3 | Заказчик уже высказался о числе сотрудников и раздаче прав: централизованная раздача через ИТ работает примерно до 140 (расшифровка: «ста сорока? сорока?») сотрудников, дальше нужен отдельный человек, но выделять его не нужно, права ведёт администратор через роли (24.10). Заказчик: администратор отвечает только за выдачу прав (24.10); просмотр прав сотрудника нужен самому заказчику (10.10) | Роль в БТ-ПРВ-01…05 не должна противоречить ролям ПЗ и записи семинара (Э-03) |
| Э4 | Раздел 3 «Границы» ПЗ-ПРВ; ПЗ-УВД раздел 3 | ПЗ-УВД: круг пользователей сервиса «определяется по правам из ПЗ-ПРВ (З-11)». В ПЗ-ПРВ нет требования и границы, дающих список пользователей, имеющих доступ к сервису: БТ-ПРВ-01…05 дают права одного выбранного сотрудника | Требования и границы смежных разделов не должны расходиться (Э-03) |
| Э5 | БТ-ПРВ-06, БТ-ПРВ-07, БТ-ПРВ-09 | В формулировках не назван объект, на который выдаётся, отзывается или делегируется право (чтение или изменение чего). Наблюдаемый результат («право выдано», «право есть») без объекта не определён | Для каждого БТ должен называться наблюдаемый результат проверки выполнения (Э-05) |
| Э6 | БТ-ПРВ-06…08; раздел 1 | Раздел 1: права в системе выдаёт администратор «через роли»; ПЗ-БЗ строит скрытие служебных сведений на ролях из БТ-ПРВ-08. Ни одно БТ не описывает назначение роли пользователю: БТ-ПРВ-07 назначает право пользователю напрямую, БТ-ПРВ-08 создаёт роли и меняет их наполнение. Заказчик: роли — конечные пользователи с доступом к инструкциям, управление ролями (24.10) | Задача З-12 (роли) должна быть покрыта требованиями целиком (Э-07) |
| Э7 | Раздел 3 «Границы»; раздел 2 | Заказчик назвал среди мест, где проверяется доступ, «Яндекс» (10.10). Документ не включает его в пять сервисов, не исключает и не задаёт вопроса о нём | Границы должны определять, что входит, что не входит (Э-08), в том числе для названного заказчиком сервиса |
| Э8 | Раздел 3, абзац «Смежное»; ПЗ-БЗ раздел 3 | ПЗ-ПРВ: доступ пользователей к инструкциям определяется ролями и «уточняется в ПЗ-БЗ». ПЗ-БЗ: роли и права, на которых строится скрытие служебных сведений, относятся к ПЗ-ПРВ. Каждый раздел отсылает к другому, требования о том, какой роли что видно, нет ни в одном (в ПЗ-БЗ — БТ-БЗ-05 без ролей). Граница изменения прав в сервисах оставлена открытой («требует решения заказчика») | Для смежного должно быть указано, в какой раздел оно отнесено (Э-08) |
| Э9 | БТ-ПРВ-01…05; БТ-ПРВ-09, БТ-ПРВ-10 | «Права» в БТ-01…05 не определены (какие именно, документ сам спрашивает в вопросе 2). В БТ-09, БТ-10 не определено понятие «проект» (в терминах ПЗ его нет) и «в пределах делегированного» (что именно делегируется) | Формулировка должна допускать одно толкование (Э-09; СТТ раздел 4, правила 2 и 5) |
| Э10 | БТ-ПРВ-06; БТ-ПРВ-08 | БТ-06 описывает два действия («выдавать и отзывать»), БТ-08 два действия («создавать роли и менять их наполнение»), у каждого свой наблюдаемый результат | Одно БТ — одно действие и один наблюдаемый результат (Э-10; СТТ раздел 4, правило 1) |
| Э11 | Раздел 1, последнее предложение | «Права в самой системе должен выдавать администратор через роли» — это решение о том, как работает система, а не описание проблемы заказчика | Описание проблемы не должно содержать решения (Э-17) |

Каждое замечание связано с ответом «нет» и с сообщением о проблеме в Issues (номер СП-NN указывается в основании).

## 4. Заключение

Заключение: доработать.

Принять — все ответы «да». Доработать — есть хотя бы один ответ «нет». В предварительном протоколе заключение решения о принятии не содержит.

Предварительный протокол решения о принятии не содержит (ПФИ, раздел 7). Сообщения о проблемах в Issues регистрируются по замечаниям этого протокола.

## 5. Подписи

Предварительный протокол не подписывается.
