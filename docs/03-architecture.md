## 3.2 Доменные модули

| Модуль | Ответственность |
|---|---|
| `registry` | Ресурсы, типы, схемы атрибутов, справочники, поиск и фильтрация |
| `assignments` | Выдача, возврат, подтверждение, история владения |
| `requests` | Заявки и общий механизм маршрутов согласования для заявок и окон работ; связь заявок с внешними задачами |
| `maintenance` | Окна и шаблоны работ, проверки плана и начала, результаты по ресурсам; использование графа, согласований и общих событий |
| `graph` | Связи между ресурсами, обходы, поиск зависимостей и blast radius |
| `notifications` | Правила, шаблоны, каналы доставки, дедупликация |
| `integrations` | Коннекторы: таск-трекер, облачные провайдеры, SSO, мессенджеры |
| `audit` | Журнал изменений, экспорт для аудитора |
| `reports` | Отчёты, дашборды, выгрузки, затраты по командам |
| `iam` | Пользователи, роли, оргструктура, политики доступа |

Модули общаются через явные интерфейсы; `integrations` не вызывается из UI напрямую —
только через доменные сценарии.

## 3.3 Разделение интерфейсов

**User UI** и **Admin UI** — один фронтенд с разными разделами, доступ по ролям, а не два
отдельных приложения (для учебного проекта дублировать сборку не имеет смысла).

Разделы User UI:
- «Мои ресурсы» — карточки, сроки, действия (вернуть, сообщить о проблеме).
- «Мои заявки» — создание и статусы.
- «Команда» (для `team_lead`) — ресурсы и затраты команды, согласование заявок.
- «Граф» — только связанные с пользователем ресурсы.
- Профиль и настройки оповещений.
- Предстоящие работы и история обслуживания доступных пользователю ресурсов.

Разделы Admin UI:
- Реестр — таблица со всеми ресурсами, фильтры, массовые операции, импорт/экспорт.
- Карточка ресурса — все поля, связи, история владения, аудит, привязанные задачи.
- Типы ресурсов и конструктор атрибутов.
- Пользователи, оргструктура, роли.
- Заявки — очередь обработки.
- Инвентаризация — кампании и расхождения.
- Интеграции — подключения, расписания синхронизации, журнал ошибок.
- Правила оповещений.
- Аудит и отчёты.
- Граф целиком с фильтрами.
- Регламентные работы: планирование, согласование, начало, результаты, шаблоны
  и контроль сроков; полномочия определены в разделе 07, §7.5.

## 3.4 Аутентификация и авторизация

- Аутентификация: корпоративный SSO (OIDC) как основной путь, логин/пароль — резервный
  для учебного стенда.
- Сессии: короткоживущий access-токен + refresh.
- Авторизация двухуровневая:
  1. **Роль** определяет набор операций (`resource:read`, `resource:write`,
     `user:manage`, `integration:manage`, `audit:read`, ...).
  2. **Область видимости** ограничивает записи: `self` (свои ресурсы), `org_unit`
     (своя команда и вложенные), `all`.
- Каждое право проверяется на сервере; скрытие пунктов меню на фронте — только UX.
- Сервисные учётные записи для интеграций — с отдельными токенами и минимальными правами.

## 3.5 Хранение данных

- Основное хранилище — реляционная БД. Связи ресурсов хранятся таблицей рёбер;
  обходы графа выполняются рекурсивными запросами. Отдельная графовая БД не нужна на
  ожидаемом объёме (~10k узлов) и добавляется только при доказанной необходимости.
- Атрибуты по схеме типа — в JSON-поле с валидацией по `attribute_schema` на уровне
  приложения; часто фильтруемые атрибуты индексируются отдельно.
- Аудит — append-only таблица, без UPDATE/DELETE из приложения.
- Файлы (фото оборудования, накладные, акты) — объектное хранилище, в БД только ссылки.

## 3.6 Фоновые задачи

Планировщик + очередь нужны для:
- периодической синхронизации с облачными провайдерами и трекером;
- проверки истекающих сроков и постановки оповещений;
- рассылки уведомлений с ретраями;
- пересчёта агрегатов для дашбордов и отчётов;
- запуска и напоминаний по кампаниям инвентаризации;
- предварительного создания окон по шаблонам, напоминаний о работах и контроля
  сроков начала, окончания и согласования. Планировщик не подтверждает фактическое
  выполнение работ.

Повторная обработка фоновой операции не создаёт повторных объектов и событий.
Операции внешних подключений отражаются в журнале синхронизаций, операции
регламентных работ — в журнале работ с идентификатором окна и операции.

### Согласованность данных регламентных работ

Модуль `maintenance` использует общую реляционную базу данных, очередь и планировщик.
При начале и завершении запись окна, состояния ресурсов, записи журнала и исходящие
события сохраняются в одной транзакции. При ошибке ни одно изменение не сохраняется.
Проверки состояния и отсутствия параллельного обслуживания выполняются на сервере
в той же транзакции. Порядок обработки повторных запросов и запросов с устаревшей
версией записи определён в §7.10 [раздела 07](07-maintenance.md).

Исходящее событие сначала сохраняется в базе вместе с предметными данными,
а затем передаётся фоновому обработчику. Обработчик сохраняет идентификатор события.
Потеря ответа внешней системы не считается доказательством, что действие
не выполнено: перед повторным созданием задачи требуется сопоставление либо сверка.
Отдельные правила внешних задач описаны в разделе 04, §4.2.

Механизм согласования принимает тип сущности, её идентификатор, редакцию плана
и маршрут. Он не изменяет состояния ресурсов и не подтверждает начало работ.
Модуль работ применяет принятое решение по правилам раздела 07.

## 3.7 Нефункциональные требования

| Требование | Значение (учебный объём) |
|---|---|
| Объём | ~10 000 ресурсов, ~30 000 связей, ~500 пользователей |
| Ответ списка реестра | ≤ 500 мс при пагинации по 50 записей |
| Построение подграфа глубины 3 | ≤ 2 с |
| Доступность | Не критично, допускается плановый простой |
| Аудит | Все изменения ресурсов, владения и прав — с сохранением before/after |
| Персональные данные | ФИО и email — минимально необходимый набор, экспорт по запросу |
| Секреты интеграций | В хранилище секретов / переменных окружения, не в БД открытым текстом |
| Локализация | Русский интерфейс, даты и валюты по локали |

## 3.8 Контур API (набросок)

```
GET    /api/v1/resources                 фильтры: type, status, owner, org_unit, tag, expires_before
POST   /api/v1/resources
GET    /api/v1/resources/{id}
PATCH  /api/v1/resources/{id}
POST   /api/v1/resources/{id}/transition  смена статуса
GET    /api/v1/resources/{id}/graph       depth, relation_types, direction
GET    /api/v1/resources/{id}/history

GET    /api/v1/me/resources
GET    /api/v1/me/notifications

POST   /api/v1/assignments                выдача
POST   /api/v1/assignments/{id}/return
POST   /api/v1/assignments/{id}/accept

GET    /api/v1/requests
POST   /api/v1/requests
POST   /api/v1/requests/{id}/approve|reject

GET    /api/v1/maintenance               окна работ; остальные операции — раздел 07, §7.10

GET    /api/v1/resource-types
POST   /api/v1/resource-types

GET    /api/v1/graph                      весь граф с фильтрами
GET    /api/v1/audit
GET    /api/v1/reports/{key}

POST   /api/v1/integrations/{id}/sync     ручной запуск
POST   /api/v1/webhooks/tracker           входящий вебхук трекера
```

Ошибки — единый формат с кодом, сообщением и полями валидации. Списки — курсорная или
offset-пагинация с явным `total`.

## 3.9 Открытые вопросы

1. **Стек** — язык/фреймворк бэкенда, фронтенд-фреймворк, библиотека визуализации графа.
   Решается перед началом реализации; документация от него не зависит.
2. Какой таск-трекер целевой (Jira / YouTrack / Yandex Tracker / GitLab) — см. `04-integrations.md`.
3. Какие облачные провайдеры импортировать в первую очередь.
4. Нужен ли отдельный публичный API для внешних систем или достаточно внутреннего.
5. Глубина учёта затрат: только плановая стоимость или фактические счета от провайдеров.
