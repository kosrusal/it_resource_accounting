# 10. Тестирование

Раздел определяет порядок проверки будущей системы учёта ресурсов. В репозитории пока
нет приложения, поэтому приведённые случаи и условия приёмки относятся к этапу
реализации. Конкретные средства проверки выбираются после выбора технологий по
[разделу 03](03-architecture.md), §3.9.

## 10.1 Основания и охват

Проверки строятся по пользовательским сценариям [раздела 01](01-vision.md), §1.6,
правилам предметной области [раздела 02](02-domain-model.md), ограничениям
[раздела 03](03-architecture.md), §3.7, и критериям задач E0-5, E12-1–E12-3
из [перечня задач](backlog.md). Для окон работ применяются случаи РР-01–РР-26
[раздела 07](07-maintenance.md), §7.13; для связи с системой задач — ТР-01–ТР-09
[раздела 08](08-task-tracker.md), §8.7, и требования
[к программному обеспечению](requirements/tracker-software.md); для наблюдаемости —
НБ-01–НБ-06 [раздела 09](09-observability.md), §9.9.

Каждая реализованная задача должна иметь проверку своего критерия приёмки. Для
изменённого правила проверяются разрешённое действие, отказ при нарушении условия
и сохранение данных после отказа. Проверка одного модуля не подменяет проверку
сценария, который проходит через несколько модулей.

## 10.2 Уровни проверок

| Уровень | Что проверяется | Условие выполнения |
|---|---|---|
| Предметные правила | Переходы состояний, обязательность полей, расчёт связей и получателей, сроки, полномочия | Без сети и общего хранилища; одинаковые входные данные дают одинаковый результат |
| Взаимодействие модулей | Операции с базой данных, журналом аудита, исходящими событиями, очередью и подключениями | Отдельная испытательная база; управляемые ответы внешних систем |
| Пользовательские сценарии | Действия сотрудника и специалиста через интерфейс и программный интерфейс, включая U1–U9 | Собранная система с испытательными данными и ролями |
| Нагрузка | Время ответа списка и построения подграфа при объёме из §3.7 [раздела 03](03-architecture.md) | Отдельная среда с указанным объёмом данных и зафиксированными условиями измерения |

Предметные правила проверяются при изменении соответствующего модуля. Проверки
взаимодействия запускаются при изменении хранения, очереди и подключений. Сквозные
сценарии выполняются перед приёмкой соответствующего этапа. Проверки времени ответа
выполняются до приёмки функций, для которых установлены пределы.

## 10.3 Испытательная среда и данные

Испытательная база создаётся заново по тем же изменениям схемы, что применяются
при развёртывании системы. Набор данных включает типы ресурсов с разными схемами
атрибутов, все состояния ресурса и заявки, действующие и завершённые выдачи,
пользователей каждой роли и нескольких организационных единиц. Для графа нужны
цепочка зависимостей, цикл, общий сервер и связь с ресурсом вне области доступа
пользователя. Для работ нужны окна с пересекающимися сроками, несколько ресурсов
с разными результатами и шаблон с повторением при смене местного времени.

Проверки сроков выполняются с заданным временем, чтобы результат не зависел от дня
запуска. Исходящие обращения направляются в испытательные подключения. Они должны
уметь возвращать ошибку, задерживать ответ и имитировать его потерю после успешного
выполнения операции. Для входящих сообщений задаются подлинные, неподтверждённые
и повторные события. Каждая проверка очищает созданные данные либо получает
отдельную базу, чтобы порядок запуска не влиял на результат.

Испытательные данные не содержат настоящих учётных данных и персональных сведений.
Среда не отправляет письма и сообщения действующим пользователям и не создаёт
задачи в рабочей внешней системе.

## 10.4 Проверяемые случаи

| Код | Основание | Условие | Ожидаемый результат |
|---|---|---|---|
| ПР-01 | [Раздел 02](02-domain-model.md), §2.4–2.5; E1-3, E1-5 | Создать ресурс с неверным атрибутом; затем запросить недопустимый переход состояния | Оба изменения отклонены; сохранённые данные и история переходов не изменились |
| ПР-02 | [Раздел 01](01-vision.md), U1, U3, U4; E2-4 | Сотрудник запрашивает список и прямой адрес чужого ресурса; специалист выдаёт ресурс сотруднику и принимает его после возврата | Чужие сведения не раскрыты; разрешённые операции меняют состояние и историю владения один раз |

| ПР-09 | [Раздел 09](09-observability.md), §9.3–9.9 | Повторить фоновую обработку после ошибки и просмотреть технические записи | Записи связаны по `trace_id` и `event_id`; попытки различимы; секреты и содержимое сообщений отсутствуют |
| ПР-10 | [Раздел 01](01-vision.md), U5; E10-7, E10-8 | Сотрудник подтверждает наличие ресурса, затем сообщает о расхождении по другому ресурсу | Подтверждение и расхождение сохранены отдельно; расхождение включено в отчёт и доступно специалисту для разбора |
| ПР-11 | [Раздел 04](04-integrations.md), §4.3; E10-2–E10-4 | Дважды получить ресурс из облака после изменения владельца, критичности и ручной связи в реестре | Запись найдена по внешнему идентификатору без дублирования; сведения, внесённые человеком, сохранены |

| ПР-13 | [Раздел 01](01-vision.md), §1.5; E11-3–E11-5 | Аудитор открывает отчёт, выгружает его с фильтром и пытается изменить ресурс | Выгрузка соответствует отфильтрованному отчёту; изменение отклонено без записи в реестр |

Эта таблица задаёт сквозные случаи. Полный набор проверок дополняется критериями
соответствующей задачи и перечнями случаев в связанных разделах. В записи результата
указываются код случая, редакция проверяемой системы, входные данные, фактический
результат и ссылка на обнаруженную ошибку, если она есть.

## 10.5 Доступ и устойчивость к отказам

Для каждой изменяющей операции проверяются сочетания роли, действия и области
видимости из [раздела 03](03-architecture.md), §3.4. Отдельно проверяются прямой
запрос закрытой записи, получение списка, выгрузка, граф, связь с внешней задачей,
сведения о работах и текст уведомления. Отказ в доступе не должен раскрывать
закрытые поля или менять данные. Проверка только видимости кнопки в интерфейсе
недостаточна: запрос к серверу выполняется напрямую.

При отказе базы данных, очереди, канала уведомлений или внешней системы задач
проверяются сохранённый предметный результат, состояние ожидающей передачи,
повторные попытки и возможность найти причину в технических записях. Для операции,
результат которой неизвестен после потери ответа, проверяется безопасная сверка
перед повтором. Одновременные запросы и устаревшие редакции проверяются для выдачи
ресурса, согласования и начала работ. Повтор запроса с тем же идентификатором
операции не должен создавать второе предметное действие.

## 10.6 Время ответа и приёмка

На объёме около 10 000 ресурсов, 30 000 связей и 500 пользователей измеряются
ответ списка реестра при странице из 50 записей и построение подграфа глубины 3.
Пределы из [раздела 03](03-architecture.md), §3.7, составляют соответственно
500 мс и 2 с. Перед измерением фиксируются состав данных, фильтры, число
одновременных запросов, характеристики среды и способ измерения. Результат
сравнивается с пределом для каждого проверяемого запроса; сведения о времени
сохраняются вместе с условиями измерения.

После реализации E0-5 при каждом запросе на слияние изменений программы выполняются
проверки затронутых предметных правил, взаимодействия модулей, правил оформления
кода и сборки.
Изменение принимается после успешного выполнения связанных с ним проверок и
устранения ошибок, нарушающих критерии приёмки. Перед завершением этапа выполняются
его пользовательские сценарии и проверки прав доступа. Если функция ещё не
реализована, её случай отмечается как не выполненный; отсутствие ошибки в таком
случае не считается успешной проверкой.
