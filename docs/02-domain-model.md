# 02. Доменная модель

## 2.1 Главная идея: один реестр, много типов

Монитор, кластер БД и SaaS-лицензия учитываются по-разному, но ими одинаково владеют,
их одинаково выдают, у них одинаково истекают сроки. Поэтому модель строится как
**единая сущность `Resource` + тип ресурса со схемой атрибутов**, а не как десяток
несвязанных таблиц.

```
ResourceType (справочник, описывает схему)
      │ 1..N
      ▼
  Resource  ──── attributes (значения по схеме типа)
      │
      ├── ownership: владелец, пользователи, команда
      ├── lifecycle: статус, даты, стоимость
      └── relations: связи с другими ресурсами (граф)
```

## 2.2 Основные сущности

### Resource
Учётная единица. Общие поля для всех типов:

| Поле | Описание |
|---|---|
| `id` | Идентификатор |
| `type` | Ссылка на `ResourceType` |
| `name` | Человекочитаемое имя |
| `code` | Инвентарный/внутренний номер, уникален |
| `status` | Статус жизненного цикла (см. 2.4) |
| `criticality` | `low` / `medium` / `high` / `critical` |
| `environment` | `prod` / `stage` / `dev` / `office` |
| `owner_id` | Ответственный (сотрудник) |
| `org_unit_id` | Команда/отдел, на балансе которого ресурс |
| `location_id` | Локация (для физических) |
| `provider_id` | Провайдер/поставщик (для облачных и закупок) |
| `external_id` | ID в системе-источнике (ARN, resource id, серийник) |
| `cost_amount`, `cost_currency`, `cost_period` | Стоимость: разовая или периодическая |
| `acquired_at`, `expires_at`, `decommissioned_at` | Ключевые даты |
| `tags` | Свободные метки |
| `attributes` | Значения атрибутов по схеме типа (JSON) |
| `created_at`, `updated_at` | Служебные |

### ResourceType
Описывает категорию и схему её атрибутов: `key`, `name`, `category`
(`hardware` / `cloud` / `software` / `service` / `data` / `network`), `icon`,
`attribute_schema` (список полей: ключ, тип, обязательность, справочник значений),
`is_assignable` (можно ли выдать на руки сотруднику).

Примеры типов и специфичных атрибутов:

| Категория | Типы | Специфичные атрибуты |
|---|---|---|
| hardware | ноутбук, монитор, док-станция, телефон, сервер, сетевое оборудование | серийный номер, модель, диагональ, разрешение, MAC, гарантия до, поставщик |
| cloud | виртуальная машина, кластер k8s, объектное хранилище, балансировщик | регион, инстанс-тип, vCPU/RAM, публичный IP, аккаунт провайдера |
| data | база данных, очередь, кэш, бэкап-политика | движок и версия, размер, RPO/RTO, шифрование, окно бэкапа |
| service | внутренний сервис, SaaS, API | URL, репозиторий, runbook, SLA, дежурная команда |
| software | лицензия, подписка | вендор, тип лицензии, число мест, срок действия |
| network | домен, TLS-сертификат, VPN, IP-подсеть | регистратор, CN/SAN, издатель, дата истечения |

### User
Сотрудник: `id`, ФИО, email, `org_unit_id`, должность, `manager_id`, статус
(`active` / `on_leave` / `offboarded`), роли, внешние идентификаторы (SSO, логин в трекере,
ID в мессенджере для оповещений).

### OrgUnit
Организационная единица: отдел/команда/проект. Иерархия через `parent_id`.
Используется и для видимости данных, и для отнесения затрат.

### Assignment (владение/пользование)
Факт закрепления ресурса за пользователем: `resource_id`, `user_id`, `role`
(`owner` / `user` / `backup_owner`), `assigned_at`, `returned_at`, `assigned_by`,
`acceptance_status` (сотрудник подтвердил получение или нет). История не удаляется —
по ней видно, у кого ресурс был раньше.

### ResourceRelation (ребро графа)
`source_id`, `target_id`, `relation_type`, `attributes`. Типы связей:

| Тип | Смысл | Пример |
|---|---|---|
| `depends_on` | источник не работает без цели | сервис → БД |
| `hosted_on` | размещён на | БД → виртуальная машина |
| `connected_to` | подключён к | монитор → док-станция |
| `part_of` | входит в состав | нода → кластер |
| `licensed_by` | покрыт лицензией | рабочее место → лицензия |
| `backup_of` | является резервом | реплика → мастер |
| `secured_by` | защищён / обслуживается | домен → TLS-сертификат |

Связи направленные; граф в общем случае — ориентированный, циклы возможны и должны
корректно обрабатываться при обходе.

### Request (заявка)
Обращение сотрудника: `type` (`grant` / `return` / `change` / `decommission` / `new_purchase`),
`requester_id`, `resource_id` или `resource_type_id` (если ресурса ещё нет),
`justification`, `status` (`draft` → `pending_approval` → `approved` / `rejected` →
`in_progress` → `done` / `cancelled`), `approver_id`, ссылка на задачу в трекере.

### AuditLog
Неизменяемый журнал: кто, когда, какую сущность и какие поля изменил (before/after),
источник изменения (UI / API / импорт / интеграция).

### Вспомогательные справочники
`Location` (площадка, кабинет, стойка), `Provider` (AWS/Yandex Cloud/поставщик железа),
`Vendor`, `CostCenter`.

## 2.3 Схема связей (обзор)

```
OrgUnit ──< User ──< Assignment >── Resource >── ResourceType
   │                                  │  │
   │                                  │  └──< ResourceRelation >── Resource
   └──────────< Resource              │
                                      └──< Request ──> (внешняя задача в трекере)
                                      └──< AuditLog
```

## 2.4 Жизненный цикл ресурса

```
  planned ──> ordered ──> in_stock ──> assigned ──> in_use
                              ▲           │           │
                              │           ▼           ▼
                              └────── returned    maintenance
                                          │           │
                                          ▼           ▼
                                    decommissioned / lost
```

- `planned` — заявлен, но не куплен/не создан.
- `ordered` — закуплен/заказан, ещё не поступил.
- `in_stock` — на складе, свободен.
- `assigned` — закреплён, но сотрудник ещё не подтвердил получение.
- `in_use` — активно используется.
- `maintenance` — ремонт/техобслуживание/приостановлен (для облака — stopped).
- `returned` — возвращён, ожидает проверки.
- `decommissioned` — списан/удалён.
- `lost` — утерян.

Переходы между статусами ограничены; каждый переход пишется в аудит. Часть переходов
доступна только ролям `it_specialist` / `it_admin`.

## 2.5 Правила целостности

- У ресурса в статусах `assigned` / `in_use` обязан быть активный `Assignment` с ролью `owner`.
- Нельзя удалить ресурс, на который есть входящие связи, — сначала списание или перенос связей.
- `code` уникален в пределах организации; `external_id` уникален в пределах провайдера.
- Ресурс с `expires_at` в прошлом и статусом `in_use` подсвечивается как нарушение.
- Офбординг сотрудника блокируется, пока за ним числятся ресурсы в активных статусах.

## 2.6 Расширяемость

Новый тип ресурса добавляется как запись `ResourceType` с описанием атрибутов —
без изменения кода и схемы БД. Это ключевое требование: «мониторы, сервисы, БД и др.»
должны заводиться администратором, а не разработчиком.
