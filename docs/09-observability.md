# 09. Наблюдаемость

Раздел описывает, как определять состояние системы учёта ресурсов и находить причину
сбоя. Требования относятся к будущей реализации; конкретные средства сбора и хранения
сведений выбираются перед её началом.

## 9.1 Назначение и границы

Наблюдаемость нужна, чтобы ответить на три вопроса: выполняется ли операция, где она
задержалась и почему завершилась ошибкой. Для этого система формирует технические
записи, числовые показатели и сведения о последовательности действий.

Наблюдаются запросы к системе, работа с основной базой данных, фоновые задачи,
подключения к внешним системам и доставка уведомлений. Сведения об изменениях
ресурсов и правах пользователей хранятся в журнале аудита по
[разделу 03](03-architecture.md), §3.5. Технические записи не заменяют этот журнал.

Система не проверяет доступность и показатели **учитываемых ресурсов** и не объявляет
аварию по техническому сигналу. Эти задачи исключены из [раздела 01](01-vision.md),
§1.4. Аварию ресурса объявляет уполномоченный пользователь по правилам
[раздела 05](05-notifications.md), §5.2. Ошибка собственной работы системы не меняет
учётное состояние ресурса.

## 9.2 Наблюдаемые операции

| Операция | Что требуется установить | Где смотреть результат |
|---|---|---|
| Запрос пользователя | Время ответа, результат, место ошибки | Показатели запросов и технические записи |
| Фоновая задача | Время постановки и начала, число попыток, результат | Показатели очереди и технические записи |
| Синхронизация с внешней системой | Последний успешный запуск, число обработанных записей, причина ошибки | `SyncRun` из [раздела 04](04-integrations.md), §4.6; технические записи |
| Создание или обновление внешней задачи | Исход операции, повторная попытка, необходимость сверки | Состояние передачи и технические записи; правила сверки — [раздел 08](08-task-tracker.md), §8.5 |
| Доставка уведомления | Время ожидания, попытки, окончательное состояние | Журнал доставки из [раздела 05](05-notifications.md), §5.7 |
| Начало и завершение регламентных работ | Автор действия, изменение состояния, исходящее событие | Журнал работ из [раздела 07](07-maintenance.md), §7.2, и технические записи |

Предметные журналы показывают сохранённый результат операции. Технические записи
помогают найти причину отказа, в том числе когда операция не дошла до сохранения.

## 9.3 Связь записей между компонентами

При входящем запросе на сервере создаётся `request_id`. Для всей последовательности действий,
включая постановку в очередь и обработку после ответа пользователю, создаётся
`trace_id`. Задача по расписанию получает собственный `trace_id`. Оба значения
сохраняются в технических записях и передаются фоновому обработчику вместе с
данными задания.

Идентификатор предметного события `event_id` остаётся прежним при повторной обработке.
Повторная попытка имеет отдельный номер `attempt`, но тот же `event_id` и `trace_id`.
Это позволяет отличить повтор от нового действия. Идентификаторы окна работ,
подключения и внешней операции указываются там, где они нужны для поиска записи
в соответствующем журнале. Время записывается в едином часовом поясе с явным
указанием смещения.

Пример пути: запрос на планирование работ → сохранение окна и события → обработка
события → обновление внешней задачи → доставка уведомления. По `trace_id` можно
найти все этапы; по `event_id` — проверить, была ли повторная обработка. Отказ
средства сбора технических сведений не отменяет предметную операцию. Сохранение
записей аудита и исходящих событий подчиняется правилам транзакции из
[раздела 03](03-architecture.md), §3.6.

## 9.4 Технические записи

Каждая запись содержит время, уровень важности, компонент, название операции,
результат и доступные идентификаторы из §9.3. При ошибке указываются её код,
этап выполнения и возможность повторной попытки. Полный текст внешнего ответа
не требуется: достаточно кода ответа и причины, безопасной для хранения.

| Уровень | Когда применяется |
|---|---|
| Сведения | Начало и завершение значимой фоновой операции, итог синхронизации |
| Предупреждение | Повторная попытка, временная недоступность внешней системы, необходимость сверки |
| Ошибка | Необработанное исключение, окончательный отказ операции, нарушение сохранения данных |

Обычные успешные запросы учитываются числовыми показателями; отдельная подробная
запись для каждого из них не обязательна. Ошибки доступа фиксируются без содержимого
запроса и без учётных данных. Технические записи не используются как история изменений:
автор, прежнее и новое значения значимых полей сохраняются в журнале аудита.

## 9.5 Числовые показатели

| Показатель | Измерение | Назначение |
|---|---|---|
| Число и длительность запросов | Шаблон адреса, операция, группа кодов ответа | Выявление ошибок и задержек; сравнение с требованиями §3.7 [раздела 03](03-architecture.md) |
| Число и длительность фоновых задач | Вид задачи, итог | Поиск отказов планировщика и обработчика |
| Число ожидающих задач и возраст старшей | Вид очереди | Обнаружение задержки обработки |
| Число попыток внешних вызовов и отказов | Вид подключения, операция | Выявление недоступного подключения |
| Время с последней успешной синхронизации | Подключение | Обнаружение пропущенного запуска по расписанию |
| Число ожидающих и неудачных доставок | Канал, уровень важности | Контроль доставки, в том числе аварийных уведомлений |
| Число ошибок работы с базой данных | Вид операции | Выявление отказа основной зависимости |

Показатели не содержат идентификаторов пользователей, ресурсов, запросов и событий
в качестве признаков группировки: количество таких значений растёт с каждой
операцией. Эти идентификаторы доступны в технических и предметных журналах.
Показатели не изменяют состояние учитываемых ресурсов.

## 9.6 Последовательность действий

Для операции с несколькими этапами сохраняются время начала, длительность и
результат каждого этапа: обработка запроса, обращение к базе данных, постановка
задания, выполнение задания и вызов внешней системы. Этапы связываются по
`trace_id`. Так можно отделить задержку базы данных от ожидания в очереди или
ответа внешней системы.

Для обычных успешных операций допустимо сохранять только часть подробных
последовательностей; сведения об ошибках и длительных операциях сохраняются
полностью. Правило отбора и срок хранения задаются до реализации. Содержимое
документов, текст уведомлений, учётные данные и значения полей ресурса в эти
сведения не включаются.

## 9.7 Проверка состояния и сигналы сотрудникам ИТ-отдела

Проверка состояния процесса показывает, отвечает ли приложение. Отдельная проверка
готовности показывает, доступна ли основная база данных и может ли приложение
обслуживать основные запросы. Отказ внешней системы отражается как состояние
соответствующего подключения, а не как отказ всего приложения. Проверки не раскрывают
адреса, секреты и подробности внутренних ошибок постороннему пользователю.

| Условие | Что видно сотруднику ИТ-отдела | Действие |
|---|---|---|
| Число серверных ошибок за установленный интервал превышает порог либо время ответа списка реестра или построения подграфа превышает соответствующий предел §3.7 [раздела 03](03-architecture.md) | Показатель и связанные технические записи | Найти ошибочный этап по `trace_id`, проверить базу данных и очередь |
| Возраст старшего задания в очереди превышает установленный порог | Вид очереди и время задержки | Проверить обработчик, затем повторить безопасные задания по их правилам |
| Последняя синхронизация завершилась ошибкой либо плановый запуск пропущен | Последний запуск `SyncRun` и причина | Проверить подключение и запустить синхронизацию повторно после устранения причины |
| Время ожидания доставки превышает установленный порог либо попытки завершились ошибкой | Журнал доставки и состояние канала | Проверить канал и повторные попытки по [разделу 05](05-notifications.md), §5.7 |
| Создание внешней задачи требует сверки | Состояние передачи и идентификатор исходного события | Сопоставить внешнюю задачу; не создавать новую до проверки по [разделу 08](08-task-tracker.md), §8.5 |

При выполнении условия средство наблюдения создаёт технический сигнал с названием
условия, временем и ссылкой на записи, по которым можно установить причину. Повтор
того же условия до его устранения не создаёт новых сигналов. Сигналы доступны
уполномоченным сотрудникам ИТ-отдела.

Ошибка синхронизации уже порождает предметное событие `integration.sync_failed`
для `it_admin` по [разделу 05](05-notifications.md), §5.4. Технический сигнал по той же
ошибке не должен создавать второе пользовательское уведомление. Если нарушена сама
доставка уведомлений, сообщение о нарушении нельзя направлять только через этот
канал: состояние должно оставаться доступным сотруднику ИТ-отдела независимо от него.

## 9.8 Доступ и хранение

Технические сведения доступны уполномоченным сотрудникам ИТ-отдела. Доступ к
журналу аудита определяется отдельно правами из [раздела 03](03-architecture.md),
§3.4. При передаче и хранении технических сведений применяются те же требования
к защите, что и для остальных внутренних данных системы.

В технические записи и сведения о последовательности действий запрещено включать
пароли, ключи доступа, токены, содержимое служебных заголовков, тексты сообщений
и полные ответы внешних систем. Персональные данные указываются только там, где без них
невозможно разобрать сбой; предпочтение отдаётся внутренним идентификаторам.
Срок хранения технических сведений и порядок удаления задаются до реализации
с учётом требований организации. Срок хранения журнала аудита устанавливается
отдельно.

## 9.9 Проверки при реализации

| № | Условие проверки | Ожидаемый результат |
|---|---|---|
| НБ-01 | Запрос порождает фоновое задание | По `trace_id` находятся запрос, постановка и выполнение задания |
| НБ-02 | Обработчик повторяет событие после ошибки | `event_id` и `trace_id` сохраняются, номер попытки меняется; предметный результат не дублируется |
| НБ-03 | Подключение недоступно при синхронизации | Причина видна в `SyncRun` и технических записях; `it_admin` получает одно предметное уведомление |
| НБ-04 | Отказал канал доставки | Неудача и повторные попытки видны в журнале доставки; сведения доступны сотруднику ИТ-отдела без этого канала |
| НБ-05 | Проверяется готовность при недоступном внешнем подключении | Основные запросы остаются доступными, состояние подключения показывает ошибку |
| НБ-06 | Просматриваются технические сведения об ошибке | По ним можно найти этап отказа; секреты и содержимое сообщений отсутствуют |

Выбор средств сбора, числовых порогов для технических сигналов и срока хранения
остаётся решением этапа реализации. Пороги должны учитывать учебный объём из
[раздела 03](03-architecture.md), §3.7, и срок передачи аварийного сообщения
из [раздела 05](05-notifications.md), §5.8.
