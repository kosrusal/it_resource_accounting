# 06. Графовое отображение ресурсов

## 6.1 Зачем

Таблица отвечает на вопрос «что у нас есть». Граф отвечает на вопросы, которые
таблица не берёт:

- Что упадёт, если выключить этот сервер? (**blast radius**)
- Кого заденет перезапуск этого сервиса — кто ещё живёт на том же хосте? (**co-tenancy**)
- От чего зависит этот сервис и кто владельцы всей цепочки?
- Какие ресурсы вообще ни с чем не связаны и, возможно, не нужны?
- Что общего у ресурсов, затронутых инцидентом?
- Что именно нужно вернуть при офбординге и что к этому подключено?

## 6.2 Модель графа

- **Узлы** — `Resource` (все типы в одном графе: железо, облако, БД, сервисы, лицензии).
- **Рёбра** — `ResourceRelation` с типом (`depends_on`, `hosted_on`, `connected_to`,
  `part_of`, `licensed_by`, `backup_of`, `secured_by`) — см. `02-domain-model.md`.
- Граф **ориентированный**, допускает циклы (сервисы могут зависеть друг от друга).
- Пользователи и оргединицы **не являются узлами** графа ресурсов — они отображаются
  как атрибуты узла (цвет/бейдж владельца). Иначе граф превращается в кашу.

## 6.3 Способы получения связей

| Способ | Описание |
|---|---|
| Вручную | Админ добавляет связь в карточке ресурса |
| Из импорта | Провайдер сам знает: БД размещена на этой ВМ, нода входит в этот кластер |
| По правилам | Ресурсы в одной подсети / с общим тегом `service=billing` |
| Из конфигураций | Разбор манифестов/переменных окружения (опционально, поздний этап) |

Источник связи сохраняется (`source`: `manual` / `import` / `rule`), чтобы импорт не
затирал связи, проставленные человеком.

## 6.4 Представления

### Локальный граф (основной режим)
Отталкивается от одного ресурса: соседи на глубину N (по умолчанию 2), с возможностью
разворачивать узлы по клику. Это рабочий режим и для сотрудника, и для админа.

### Граф зависимостей

- По направлению `depends_on`: от чего зависит выбранный ресурс.
- Против направления `depends_on`: какие ресурсы зависят от выбранного.
- Для расчёта последствий обслуживания учитываются также обратные связи `hosted_on`:
  сначала размещённые ресурсы, затем зависимые от них ресурсы; см. раздел 07, §7.4.

В программном интерфейсе `downstream` обозначает обход по направлению связи,
`upstream` — против направления, `both` — в обоих направлениях. На экране используются
смысловые подписи, а не расположение узла выше или ниже. Результат расчёта влияния
содержит ресурсы, владельцев, основания включения и признак полноты.

### Соседи по хосту (co-tenancy)
Отвечает на вопрос «сервис A перезапускаю — что ещё на этой машине». Отдельной сущности
не нужно: соседи выводятся из уже существующей связи `hosted_on` за два шага —
`A --hosted_on--> сервер <--hosted_on-- B, C`.

В UI:
- В карточке и в узле графа всегда виден **хост**: у сервиса, БД, контейнера в подписи
  узла отображается имя сервера, на котором он запущен.
- Узлы, сидящие на одном хосте, обводятся общей рамкой — видно плотность заселения.
- На хосте бейдж с числом размещённых на нём ресурсов; больше одного — уже повод
  посмотреть перед работами.
- Выбор сервиса подсвечивает соседей по хосту **отдельным цветом** (не тем, что у
  зависимостей): это не «от чего я завишу», а «с кем я делю железо».

Перед планированием обслуживания показываются соседи по серверу, их критичность
и владельцы. Соседство означает совместное использование оборудования, но не
доказывает недоступность соседнего приложения при перезапуске выбранного.
Если обслуживается сам сервер, размещённые на нём ресурсы учитываются в расчёте
потенциального влияния по обратным связям `hosted_on`.

Модуль графа возвращает сведения о связях и не принимает решения о начале работ.
Единые условия согласования, включая критичный сервер и рабочую среду соседних
ресурсов, определены в разделе 07, §7.5. Предупреждение о соседстве не заменяет
проверки полноты расчёта и разрешения на начало.

### Обзорный граф
Весь граф с фильтрами и агрегацией: по умолчанию узлы схлопнуты до уровня оргединиц
или типов; разворачиваются по запросу. Без агрегации 10k узлов нечитаемы.

### Групповые представления
Раскладка с группировкой по окружению (`prod` / `stage` / `dev`), по локации или по
команде — рамками вокруг кластеров узлов.

## 6.5 Визуализация

| Канал | Что кодирует |
|---|---|
| Иконка / форма узла | Тип ресурса |
| Цвет узла | Статус или критичность (переключатель) |
| Размер узла | Число связей или стоимость (переключатель) |
| Стиль ребра | Тип связи (сплошная — `depends_on`, пунктир — `connected_to`, ...) |
| Затемнение | Узлы вне выбранного пути/фильтра |

Обязательные элементы UI: легенда, поиск по узлам с центрированием, панель фильтров
(тип, статус, окружение, команда, тип связи, глубина), боковая панель с карточкой
выбранного узла, экспорт в PNG/SVG и выгрузка списка узлов в CSV.

Раскладка: force-directed для локального графа, иерархическая (сверху вниз) для
графа зависимостей — она лучше показывает уровни. Позиции узлов, расставленных
вручную, можно сохранять.

## 6.6 API

```
GET /api/v1/resources/{id}/graph
    ?depth=2
    &direction=both|upstream|downstream
    &relation_types=depends_on,hosted_on
    &resource_types=database,service
    → { nodes: [...], edges: [...], truncated: bool }

GET /api/v1/graph
    ?org_unit=...&environment=prod&group_by=org_unit
    → агрегированный граф

GET /api/v1/resources/{id}/impact
    ?include_cotenants=true
    → { dependents: [...], cotenants: [...], truncated: bool, reason: ... }
      потенциально затронутые ресурсы и соседи; каждый с владельцем,
      критичностью и основанием включения
```

Ответ всегда содержит логический признак `truncated`; при ограничении результата
он равен `true` и сопровождается причиной. Параметры изображения и фильтры текущего
пользователя не определяют полноту служебного расчёта влияния для работ.
Постраничная выдача полного списка не считается вычислительным ограничением.

## 6.7 Производительность и ограничения

- Для изображения подграфа используются ограничения глубины и количества узлов
  (начальная глубина 2, наибольшая глубина 3, максимум 500 узлов). Расчёт влияния для обслуживания
  выполняется отдельно до исчерпания достижимых узлов по правилам раздела 07, §7.4.
  Если вычислительное ограничение не позволило завершить расчёт, результат неполон
  и не разрешает обычное согласование или начало работ.
- Защита от циклов: посещённые узлы отслеживаются при обходе.
- Соседи по хосту — обычный двухшаговый обход по `hosted_on`, отдельного хранения и
  индекса не требует. Денормализованное поле «хост» на ресурсе появится, только если
  подпись узла начнёт тормозить списки.
- Сохранённый результат подграфа зависит от корневого ресурса, параметров и редакции
  связей. Перед каждой выдачей проверяются текущие права пользователя; результат
  с закрытыми сведениями не выдаётся по сохранённым ранее правам.
  Для согласования и начала работ проверяется актуальность не только связей,
  но и владельцев, подразделений, критичности и среды использования ресурсов.
- Отдельная графовая БД (Neo4j и т.п.) **не вводится** на старте: реляционный обход
  покрывает ожидаемый объём. Решение пересматривается, если появятся запросы глубины 5+
  по всему графу.

## 6.8 Видимость

Граф уважает права доступа: сотрудник видит только узлы, доступные ему по области
видимости. Недоступные соседи отображаются как обезличенные «скрытый ресурс» —
чтобы связь не пропадала и картина не искажалась, но детали не утекали.

Для вложенного размещения проверка конфликтов работ проходит по всей известной
цепочке `hosted_on`; простой список непосредственных соседей её не заменяет.
При расчёте влияния исходные ресурсы, найденные ресурсы и все основания включения
объединяются без повторных записей. Циклы не приводят к повторной обработке узлов.
Служебный расчёт выполняется с необходимым доступом к реестру, а его выдача
каждому пользователю ограничивается его правами. Полнота относится к известным
связям поддержанных типов, а не к доказанной полноте реальной инфраструктуры.
