# 08. Система ведения задач

Этап: **постановка задачи и анализ решений**. Здесь сформулировано предложение
для доклада по интеграции. Подключение пока не реализовано; внешний сервис
и доступ команды к нему ещё не согласованы.

## 8.1 Постановка задачи

У сотрудников появляются поручения по ресурсам: выдать оборудование, продлить
лицензию, выполнить обслуживание. Цель — связать ресурс или заявку с задачей,
у которой есть исполнитель, состояние и результат. Из карточки ресурса можно
будет перейти к поручению и понять, кто им занимается.

У трекера есть два применения: планировать работу нашей команды уже сейчас
и в дальнейшем принимать задачи из системы учёта. Для первого достаточно
доступа к сервису и общего порядка ведения задач; второе потребует разработки.

## 8.2 Примеры применения

| Ситуация | Предлагаемое действие |
|---|---|
| Согласована заявка на оборудование | Создать задачу на выдачу со ссылкой на заявку |
| Заканчивается лицензия или сертификат | Создать задачу на продление с датой окончания |
| Сотрудник возвращает ресурсы при увольнении | Вести одну задачу со списком оставшихся ресурсов |
| Обнаружено расхождение инвентаризации | Создать задачу на разбор расхождения |
| Запланировано обслуживание | Связать план работ с задачей исполнителя |

Пример общего сценария: специалист выбирает неисправный сервер на графе и сообщает
об аварии. Модуль графа определяет затронутые ресурсы, модуль оповещений сообщает
их пользователям, а задача в трекере фиксирует поручение ответственному.
Рассылка и задача решают разные вопросы: кого предупредить и кто устраняет проблему.

## 8.3 Сравнение готовых решений

Возможности ниже проверены по документации продуктов. Пригодность для команды
нужно проверить отдельно на доступном учебном подключении.

| Вариант | Что есть для нашей задачи | Что проверить перед выбором |
|---|---|---|
| Яндекс Трекер | Очереди задач; создание задачи через программный интерфейс с названием и очередью | Доступ команды к организации и очереди, исполнители, состояния, условия использования |
| YouTrack | Программный интерфейс и настраиваемые правила обработки задач | Доступная среда, необходимые правила, способы получения изменений |
| GitHub Issues | Задачи рядом с репозиторием; исполнители, метки и программный интерфейс | Достаточен ли такой порядок для обслуживания ресурсов; какие состояния понадобятся |

Предложение для обсуждения: сначала проверить Яндекс Трекер на одной учебной
очереди. GitHub Issues оставить запасным вариантом для планирования команды,
поскольку репозиторий уже находится на GitHub. Это предварительный выбор;
организация, очередь и учётные записи этой работой не создавались.

Основания сравнения: [создание задачи в Яндекс Трекере](https://yandex.ru/support/tracker/ru/api/issues/create-issue),
[интерфейсы и автоматизация YouTrack](https://www.jetbrains.com/help/youtrack/cloud/resources-for-developers.html),
[операции GitHub Issues](https://docs.github.com/en/rest/issues).

## 8.4 Входы, работа и выходы процесса

Предлагаемый порядок подготовки интеграции фиксируется в этой записке и
обсуждается командой перед началом разработки.

| Шаг | Что нужно на входе | Что делаем | Что получаем |
|---|---|---|---|
| Постановка задачи | Сценарии учёта, роли пользователей, границы соседних блоков | Выбираем, какие события требуют поручения | Согласованный список сценариев |
| Выбор сервиса | Список сценариев, доступ команды, документация кандидатов | Сравниваем создание, назначение, изменение и получение состояния задачи | Короткое обоснование выбора и список ограничений |
| Подготовка пробного подключения | Учебная очередь, разрешённый доступ, пример заявки | Уточняем поля задачи и связь с записью учёта | Описание обмена и набор пробных данных |
| Проверка решения | Описание обмена, сценарии, доступная среда | Рассматриваем описание, сравниваем возможности и выполняем пробные действия | Замечания, результаты проверки и решение о следующем этапе |

Минимальная карточка работы команды: название, цель, исполнитель, исходные
материалы, ожидаемый результат и состояние. Для обсуждения достаточно состояний
«запланировано», «в работе», «на проверке», «готово». Конкретные имена участников
и сроки назначает команда.

## 8.5 Предварительная схема обмена

Событие учёта → подготовка поручения → внешний трекер → сохранение ссылки на задачу.
Ответ внешнего сервиса сообщает номер и состояние задачи. Ошибка связи показывается
отдельно; уже сохранённая заявка остаётся в системе учёта.

В следующем этапе нужно решить, как избежать повторного создания после потери
ответа: сначала определить результат прежней попытки, затем решать о повторе.
Повторное событие об одном поручении не должно порождать вторую задачу.
Закрытие внешней задачи само по себе не выдаёт ресурс и не завершает обслуживание:
для учётного действия понадобятся проверка прав и подтверждение допустимости.

Для мессенджера предварительно рассматривается Telegram; выбор и отправка сообщений
относятся к [оповещениям](05-notifications.md). До реализации нужно договориться,
какие сообщения отправляет наша система, а какие — сам трекер, чтобы их не дублировать.

## 8.6 Проверка параллельно подготовке решения

| Способ | Что проверяем сейчас или планируем проверить |
|---|---|
| Рассмотрение | Команда оценивает понятность сценариев, границы ответственности и достаточность входных данных |
| Анализ | Сопоставляем возможности трекеров с нужными действиями; при наличии среды измеряем время пробного обращения и фиксируем условия |
| Испытание | После получения доступа создаём учебную задачу, назначаем исполнителя, меняем состояние и проверяем сохранённую ссылку |

При разработке добавятся случаи отказа связи, повторного события и недопустимого
обратного изменения. Сейчас выполнено сравнение документации; измерения и испытания
подключения ещё не проводились. Общий порядок описан в [разделе 10](10-testing.md).

## 8.7 Короткий доклад

«Мой блок — связь учёта ресурсов с трекером задач. Нужно, чтобы по заявке,
продлению лицензии или обслуживанию появлялось поручение с исполнителем и ссылкой
на исходную запись. Я сравнил Яндекс Трекер, YouTrack и GitHub Issues.
Для первой проверки предлагаю Яндекс Трекер, если команда получит доступ.
На входе нужны сценарии, роли и учебная очередь; на выходе — выбранное решение,
описание обмена и результат пробных действий. Проверку планируем параллельно:
рассмотрение описания командой, анализ возможностей и испытание на учебной задаче.
Сейчас подготовлено предложение; программное подключение будет следующим этапом».
