# 05. Оповещения

## 5.1 Задача

Довести до нужного человека нужное событие вовремя — и при этом не превратиться в
источник шума, который все отключают.

## 5.2 Модель

```
Событие (Event) ──> Правило (NotificationRule) ──> Уведомление (Notification)
                                                          │
                                                          ▼
                                          Каналы доставки (in-app / email / мессенджер)
```

### Event
Факт, произошедший в домене: `event_type`, `entity_type`, `entity_id`, `payload`,
`occurred_at`. События публикуются доменными модулями и не знают о получателях.

### NotificationRule
Настраиваемое администратором правило: на какое событие, кому, по какому каналу,
с каким шаблоном, с какой периодичностью и порогом.

Поля: `event_type`, `conditions` (фильтр по типу ресурса, критичности, оргединице),
`recipients` (роль / владелец ресурса / команда / конкретные пользователи),
`channels`, `template_id`, `throttle` (не чаще чем раз в N часов), `enabled`.

### Notification
Конкретное уведомление конкретному пользователю: `user_id`, `rule_id`, `title`, `body`,
`link`, `severity` (`info` / `warning` / `critical`), `status` (`pending` / `sent` /
`failed` / `read`), `sent_at`, `read_at`.

## 5.3 Каталог событий

| Событие | Кого касается по умолчанию | Severity |
|---|---|---|
| `resource.assigned` | Новый владелец | info |
| `resource.assignment_pending_acceptance` | Владелец (напоминание через 3 дня) | warning |
| `resource.return_requested` | IT-отдел | info |
| `resource.owner_changed` | Прежний и новый владелец, тимлид | info |
| `resource.status_changed` | Владелец (для критичных — команда) | info |
| `resource.expiring_soon` | Владелец, IT-админ | warning (30/14/7/1 день) |
| `resource.expired` | Владелец, IT-админ | critical |
| `resource.orphaned` | IT-админ | warning |
| `resource.discovered_unmanaged` | IT-админ | warning |
| `resource.disappeared_at_provider` | Владелец, IT-админ | warning |
| `request.created` | Согласующий | info |
| `request.approved` / `request.rejected` | Заявитель | info |
| `request.awaiting_approval_too_long` | Согласующий, его руководитель | warning |
| `inventory.campaign_started` | Все участники | info |
| `inventory.confirmation_overdue` | Участник, его тимлид | warning |

| `offboarding.started` | IT-отдел, руководитель сотрудника | warning |
| `offboarding.resources_not_returned` | IT-админ | critical |
| `integration.sync_failed` | IT-админ | warning |
| `budget.threshold_exceeded` | Тимлид, IT-админ | warning |

## 5.4 Каналы

| Канал | Когда использовать | Особенности |
|---|---|---|
| **In-app** | Всегда (базовый) | Колокольчик в UI, список, отметка о прочтении. Работает без внешних сервисов — реализуется первым |
| **Email** | Важное и требующее действия | Шаблоны с HTML, ссылка в систему |
| **Мессенджер** (Telegram / Mattermost / Slack) | Срочное | Требует привязки аккаунта пользователем |
| **Дайджест** | Сводки по некритичному | Ежедневно/еженедельно, одним письмом вместо десяти |

Пользователь управляет своими предпочтениями в профиле: для каждой категории событий —
набор каналов, опция «только дайджест», тихие часы. Критичные события игнорируют
отключение в разумных пределах (например, `offboarding.resources_not_returned`
администратору приходит всегда).

## 5.5 Борьба с шумом

- **Троттлинг**: одно и то же правило по одному ресурсу — не чаще, чем задано в `throttle`.
- **Дедупликация**: ключ `(rule_id, user_id, entity_id, окно времени)`.
- **Агрегация**: 15 истекающих лицензий → одно уведомление со списком, а не 15 писем.
- **Лестница напоминаний** вместо повторов: 30 → 14 → 7 → 1 день, каждое следующее
  выше по severity.
- **Тихие часы и дайджест** по умолчанию включены для `info`.

## 5.6 Доставка

- Отправка — фоновой задачей из очереди, с ретраями (3 попытки, экспоненциальная задержка).
- Провал доставки не теряется: `status = failed` + причина, видно администратору.
- Шаблоны хранятся отдельно от кода и редактируются админом; поддерживают подстановку
  полей ресурса и пользователя.
- Тестовая отправка «себе» для проверки шаблона и канала.

## 5.7 Что реализуется первым

1. In-app уведомления + колокольчик (не требует внешних сервисов).
2. Планировщик проверки сроков (`expiring_soon` / `expired`).
3. Email через SMTP.
4. Настройки пользователя и дайджест.
5. Мессенджер и настраиваемые правила в UI.
