# 05. Оповещения

## 5.1 Задача

Довести до нужного человека нужное событие вовремя — и при этом не превратиться в
источник шума, который все отключают.

## 5.2 Модель

```
Событие → Применение правил → Уведомление → Каналы доставки
```

### Событие — `Event`

Запись о произошедшем факте: `event_id`, `event_type`, `entity_type`, `entity_id`,
`payload`, `occurred_at`. Предметные модули создают события, а подсистема оповещений
определяет получателей.

### Правило — `NotificationRule`

Администратор задаёт вид события, условия применения, получателей, каналы,
шаблон сообщения и ограничения частоты отправки.

Поля: `id`, `event_type`, `conditions` (тип ресурса, критичность, подразделение),
`recipients` (роль / владелец ресурса / команда / конкретные пользователи),
`channels`, `template_id`, `throttle` (не чаще чем раз в N часов), `enabled`.

### Уведомление — `Notification`

Сообщение конкретному пользователю: `id`, `event_id`, `user_id`, `title`, `body`,
`link`, `severity` (`info` / `warning` / `critical`), `status` (`pending` / `sent` /
`failed` / `read`), `sent_at`, `read_at`.

Для уведомления о регламентных работах `event_id` — обязательная ссылка на `Event`;
пара `(event_id, user_id)` уникальна. Для сводки по нескольким событиям других
категорий это поле может отсутствовать; правила таких сводок определены в §5.5.
Одно поле `rule_id` в уведомлении не используется: применённые правила учитываются
отдельными связями.

### Применённое правило — `NotificationRuleMatch`

Связь содержит `notification_id`, `rule_id` и `rule_snapshot` — копию параметров
правила на момент его применения. Пара `(notification_id, rule_id)` уникальна.
У уведомления сохраняются все сработавшие для его получателя правила, а не одно
произвольно выбранное. Изменение или отключение правила не меняет сохранённую копию.

Для событий регламентных работ уведомление и связи со всеми применёнными правилами
сохраняются одной транзакцией. Повторная обработка уже созданного уведомления
использует сохранённые текст и связи, а не новые редакции правил. Актуальность
сообщения и права получателя повторно проверяются перед отправкой по §5.8.

## 5.4 Каналы

| Канал | Когда использовать | Особенности |
|---|---|---|
| **In-app** | Всегда (базовый) | Колокольчик в UI, список, отметка о прочтении. Работает без внешних сервисов — реализуется первым |
| **Email** | Важное и требующее действия | Шаблоны с HTML, ссылка в систему |
| **Мессенджер** (Telegram / Mattermost / Slack) | Срочное | Требует привязки аккаунта пользователем |
| **Дайджест** | Сводки по некритичному | Ежедневно/еженедельно, одним письмом вместо десяти |

Пользователь управляет своими предпочтениями в профиле: для каждой категории событий —
набор каналов, опция «только дайджест», тихие часы. Критичные события игнорируют
отключение в разумных пределах (например, `offboarding.resources_not_returned`
администратору приходит всегда).

## 5.5 Ограничение числа уведомлений

Для событий регламентных работ действуют правила §5.8: разные события не подавляются
ограничением частоты и не объединяются в сводку. Для остальных событий применяются
следующие правила.

- **Ограничение частоты**: одно и то же правило по одному ресурсу применяется
  не чаще, чем задано в `throttle`.
- **Исключение повторов**: перед созданием уведомления проверяется ключ
  `(rule_id, user_id, entity_id, окно времени)`. Здесь `rule_id` обозначает
  применяемое правило, а не поле `Notification`.
- **Объединение сообщений**: сведения о 15 истекающих лицензиях включаются
  в одно уведомление со списком.
- **Последовательные напоминания**: за 30, 14, 7 и 1 день до срока, с повышением
  уровня важности.
- **Тихие часы и сводки** по умолчанию включены для уровня `info`.

## 5.6 Доставка

- Отправка — фоновой задачей из очереди, с ретраями (3 попытки, экспоненциальная задержка).
- Провал доставки не теряется: `status = failed` + причина, видно администратору.
- Шаблоны хранятся отдельно от кода и редактируются админом; поддерживают подстановку
  полей ресурса и пользователя.
- Тестовая отправка «себе» для проверки шаблона и канала.

## 5.7 Что реализуется первым

1. In-app уведомления + колокольчик (не требует внешних сервисов).
2. Планировщик проверки сроков (`expiring_soon` / `expired`).
3. Email через SMTP.
4. Настройки пользователя и дайджест.
5. Мессенджер и настраиваемые правила в UI.

## 5.8 Оповещения о регламентных работах

Каталог событий и обязательные группы получателей определены в [разделе 07](07-maintenance.md),
§7.9. Модуль работ сохраняет событие и результат расчёта затронутых ресурсов;
модуль оповещений определяет пользователей и каналы по правилам и правам доступа.
Неполнота расчёта и ожидаемая недоступность указываются в сообщении явно.

По умолчанию публикация и успешное завершение имеют уровень `info`; напоминание
за одни сутки, начало, изменение, отмена, восстановление прежней конфигурации,
запрос согласования и просрочка — `warning`. Неудачный или частичный результат,
а также отказ при последующем согласовании аварийных работ имеют уровень `critical`.
Напоминание за семь суток и дополнительное сообщение имеют уровень `info`.
Выход за допустимое время имеет уровень `warning`. Аварийное начало без полного
расчёта имеет уровень `critical`. При нескольких основаниях выбирается наибольший
уровень важности; состояние выполнения по нему не определяется.

Уведомление о регламентных работах уникально по `(event_id, user_id)`: ресурсы
объединяются в одном сообщении, а применённые правила сохраняются в
`NotificationRuleMatch` по §5.2. Каналы, выбранные правилами, объединяются без повторов
с учётом пользовательских настроек из §5.4. Доставка учитывается по уведомлению
и каналу, а не по каждому сработавшему правилу.

Изменение плана, отмена и завершение работ являются разными событиями. Уведомления
о них создаются отдельно. Для напоминаний учитываются редакция плана и срок.
Повторные события `resource.status_changed` и `resource.cotenant_maintenance`,
относящиеся к тому же окну, не создают дополнительные сообщения о тех же работах.

Сохраняется список всех пользователей, которым создавались уведомления по окну.
Отмена, изменение и результат направляются также прежним получателям, а не только
владельцам текущего состава ресурсов. Перед отправкой проверяются актуальность
редакции, состояние окна и права получателя; недоступные сведения скрываются.
Устаревшие напоминания снимаются с отправки, уже переданные сообщения не отзываются.
Для прежнего получателя без текущего доступа используется нейтральное сообщение
об изменении ранее объявленных работ без закрытых сведений и прямого доступа к ним.

После повторных неудачных попыток доставки сохраняются причина и состояние ошибки.
Повторная отправка не создаёт вторую внутреннюю запись. Отсутствие повторных писем
или сообщений во внешнем канале гарантируется только при поддержке этим каналом
защиты от повторов; потеря подтверждения доставки без такой поддержки может
привести к повторной внешней отправке. Это не считается новой записью уведомления.
