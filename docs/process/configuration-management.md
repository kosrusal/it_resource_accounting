# План управления конфигурацией

Редакция 0.1. Проект для утверждения командой.

План определяет, где хранятся материалы проекта, откуда исполнитель берёт входные
данные, куда и в каком виде кладёт результат, как работать с ветками, фиксациями
и запросами на объединение. План основан на черновике из ветки
`sasha/requirements-draft` и дополняет его правилами работы с GitHub.

## 1. Термины

| Термин | Значение |
|---|---|
| Хранилище | Репозиторий Git проекта: [kosrusal/it_resource_accounting](https://github.com/kosrusal/it_resource_accounting) |
| Единица конфигурации | Отдельный учитываемый файл или каталог из таблицы §2 |
| Фиксация | Сохранённое в Git изменение с автором, описанием и идентификатором (в Git — `commit`) |
| Ветка | Именованная последовательность фиксаций |
| Запрос на объединение | Предложение включить ветку в `main` с обсуждением и рассмотрением; в интерфейсе GitHub — раздел `Pull requests` |
| Задача | Карточка работы в разделе `Issues` хранилища, см. [правила ведения задач](task-tracker.md) |
| Базовая редакция | Согласованный состав материалов, отмеченный меткой Git (`tag`) |

## 2. Состав хранилища: откуда брать и куда класть

| Каталог или файл | Что хранится | Кто изменяет | Используется как вход для |
|---|---|---|---|
| `README.md` | Назначение проекта, текущий этап, указатель направлений | Ответственный за объединение | Знакомства с проектом |
| `AGENTS.md` | Языковые правила текста | Руководитель проекта | Любой текстовой работы |
| `docs/01-…09-*.md`, `docs/11-*.md` | Разделы направлений: постановка задачи, анализ решений, предметные правила, проектные решения | Ответственный за направление и авторы задач | Требований, проектирования, проверки |
| `docs/requirements/` | Системные требования (`*-system.md`, общий `system.md`) и требования к ПО (`*-software.md`) | Авторы требований | Проектирования, кодирования, испытаний |
| `docs/<направление>/` | Подробные материалы направления, не помещающиеся в один раздел (пример: `docs/maintenance/`) | Ответственный за направление | Раздела направления |
| `docs/process/` | Правила работы команды | Руководитель проекта | Любой работы |
| `docs/backlog.md` | Перечень будущих задач реализации E0–E13 | Руководитель проекта | Планирования этапов реализации |
| `docs/open-questions.md` | Открытые вопросы ОВ-NN | Любой участник | Любой работы, зависящей от решения |
| `docs/10-testing.md` | Порядок проверки и проверочные случаи ПР-NN | Ответственный за проверку | Испытаний |
| `.github/` | Шаблоны задачи и запроса на объединение | Руководитель проекта | Создания задач и запросов |
| `scripts/` | Средства проверки документации (появится после объединения ветки требований) | Автор средства | Проверки перед запросом на объединение |
| Каталоги кода | Определяются задачей E0-2 после выбора технологий (ОВ-03) | Разработчики | Сборки и испытаний |

Правила для всех материалов:

- формат текста — Markdown (`.md`), кодировка UTF-8, язык — русский по `AGENTS.md`;
- схемы хранятся в исходном текстовом виде (Mermaid в Markdown или `.drawio`) рядом
  с документом, изображения — в подкаталоге `img/` того же каталога;
- материалы встреч, присланные файлы и расшифровки, на которых основан документ,
  в хранилище не кладутся: их выводы переносятся в соответствующий раздел;
- учётные данные, ключи, пароли и настоящие персональные данные в хранилище запрещены.

Вход каждой задачи указывается путём к файлу и разделу в `main`, выход — путём,
куда будет положен результат (см. [правила ведения задач](task-tracker.md)).

## 3. Права в хранилище

| Участник | Права GitHub | Что может |
|---|---|---|
| Владелец хранилища (`kosrusal`) | `Admin` | Настройки защиты веток, метки базовых редакций, приглашение участников |
| Участники команды | `Write` | Создание веток, фиксации в своих ветках, задачи, запросы на объединение и их рассмотрение |
| Преподаватель | `Read` или `Triage` по его запросу | Чтение и замечания в задачах |

Защита ветки `main` настраивается владельцем: `Settings → Branches → Add rule` для `main`:

- `Require a pull request before merging`, не менее одного одобрения (`Require approvals: 1`);
- `Dismiss stale pull request approvals when new commits are pushed`;
- `Require conversation resolution before merging`;
- запрет принудительной отправки и удаления ветки (значения по умолчанию правила).

До включения защиты правила ниже соблюдаются вручную.

## 4. Ветки

| Ветка | Назначение | Время жизни |
|---|---|---|
| `main` | Согласованное состояние материалов; прямые фиксации запрещены | Постоянно |
| `<автор>/<номер задачи>-<тема>` | Работа по одной задаче | До объединения, затем удаляется |
| `<автор>/<тема>` без номера | Черновик, ещё не оформленный задачей; в `main` не объединяется, пока не появится задача | До оформления задачи или отказа от черновика |

Правила имени ветки — в [стандарте именования](naming-and-tracing.md#3-ветки).
Пример: `ruslan/27-task-rules`. Ветки, созданные до этих правил
(`mmarss`, `zajivoee_branch`, `notifications_docs` и другие), не переименовываются;
новые работы в них не начинаются.

Одна ветка — одна задача. Посторонние исправления, замеченные по ходу работы,
оформляются отдельной задачей.

## 5. Порядок внесения изменения

### 5.1 Начало работы

```bash
git switch main
git pull --ff-only
git switch -c <автор>/<номер>-<тема>
```

Если `git pull --ff-only` отказывает, в локальной `main` есть посторонние фиксации:
их нужно перенести в отдельную ветку (`git branch <автор>/спасение-<тема>`)
и вернуть `main` к удалённому состоянию (`git reset --hard origin/main`).

### 5.2 Фиксации

- Фиксация содержит одно законченное по смыслу изменение.
- Первая строка описания — до 72 знаков, русский язык, глагол в неопределённой форме:
  «Добавить правила ведения задач», «Уточнить СТ-РЕЕ-03». Точка в конце не ставится.
- После пустой строки — причина изменения, если она не очевидна из первой строки.
- Последняя строка — номер задачи: `Задача: #27`.
- Перед фиксацией выполняется проверка `git diff --staged`: в изменение не попадают
  служебные файлы редактора, временные файлы и чужие правки.

Ветку можно отправлять в GitHub в любой момент: `git push -u origin <ветка>`.
Принудительная отправка (`git push --force-with-lease`) допустима только в своей
ветке до назначения проверяющего.

### 5.3 Запрос на объединение

1. Перед созданием запроса получить свежий `main` и включить его в ветку:
   `git fetch origin && git merge origin/main`. Конфликты разрешаются по смыслу,
   с сохранением чужих изменений; при сомнении — вопрос автору конфликтующей правки.
2. Выполнить проверки из шаблона запроса: ссылки, номера, языковые правила, связь
   с задачей.
3. Создать запрос в GitHub из своей ветки в `main`. Заголовок — как первая строка
   основной фиксации. Описание заполняется по шаблону
   [`.github/pull_request_template.md`](../../.github/pull_request_template.md);
   в нём обязательна строка `Closes #<номер задачи>` — служебное слово GitHub,
   закрывающее задачу при объединении.
4. Назначить проверяющего (`Reviewers`) — ответственного за направление или другого
   участника, не автора. Перевести задачу в состояние «На проверке».

### 5.4 Рассмотрение

Рассмотрение проводится по [ИН-05](procedures.md#ин-05-рассмотрение-результата)
в течение двух рабочих дней после назначения. Замечания пишутся комментариями
к строкам изменения. Автор исправляет замечание новой фиксацией и отвечает
в обсуждении; закрывает обсуждение тот, кто его открыл. Итог: `Approve`
(одобрено) или `Request changes` (требуются изменения).

### 5.5 Объединение

Объединяет автор после одобрения или ответственный за объединение.

- Способ по умолчанию — `Squash and merge`: в `main` попадает одна фиксация на задачу,
  заголовок — заголовок запроса с номером, например
  «Добавить правила ведения задач (#28)».
- `Create a merge commit` применяется, если ветку вели несколько авторов
  и их отдельные фиксации нужно сохранить.
- `Rebase and merge` не применяется.
- После объединения ветка удаляется кнопкой `Delete branch`, локальная копия —
  командой `git branch -d <ветка>`.

Объединение без запроса допускается только для исправления, которое восстанавливает
работоспособность `main` (битая ссылка в указателе, ошибочное объединение), по решению
ответственного за объединение. В описании такой фиксации указывается причина.

## 6. Базовые редакции и восстановление

Базовая редакция создаётся по [ИН-07](procedures.md#ин-07-выпуск-базовой-редакции)
к контрольной точке курса: метка `docs-v<основная>.<дополнительная>`, например
`docs-v0.1`. Для будущих выпусков программы — `v<основная>.<дополнительная>.<исправление>`.
Метка ставится на фиксацию `main` и не переносится.

Ошибочное изменение в `main` отменяется новой фиксацией (`git revert`) через запрос
на объединение. Перезапись истории `main` запрещена. Для получения прежнего состояния
используется метка или идентификатор фиксации: `git switch --detach docs-v0.1`.

Удалённое хранилище и локальные копии участников сохраняют историю Git; это не
заменяет резервирование данных будущей системы (ОВ-05).
