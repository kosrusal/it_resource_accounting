# План разработки

Редакция 0.1. Проект для утверждения командой. Основа — черновик из ветки
`sasha/requirements-draft`, дополненный этапом постановки задачи и ссылками
на инструкции.

## 1. Определения

Этап — часть разработки с заданными входами, работами и выходами. Приращение —
согласованный набор возможностей, выпускаемый совместно. Интеграция — соединение
компонентов и проверка их совместной работы. Приёмка — проверка результата по
требованиям. Контрольная точка — дата курса, к которой предъявляется результат
этапа; в GitHub ей соответствует `Milestone`.

## 2. Жизненный цикл

Этапы выполняются последовательно для каждого направления; разные направления
могут находиться на разных этапах. Противоречие, найденное на этапе, возвращается
на предыдущий этап задачей вида `ошибка` с указанием причины.

| Этап | Вход и условие начала | Работы и инструкции | Выход и условие завершения |
|---|---|---|---|
| 0. Постановка и анализ (текущий) | Тема проекта, назначенные направления | Постановка задачи (ИН-01), анализ готовых решений (ИН-02), открытые вопросы (ИН-06) | Разделы направлений в `docs/` с входами, выходами, предложением и способом проверки |
| 1. Требования | Рассмотренные разделы направлений | Системные требования (ИН-03), затем требования к ПО (ИН-04) | `docs/requirements/*-system.md` и `*-software.md`; закрыты вопросы, влияющие на функции первого приращения |
| 2. Проектирование | Требования выбранного приращения | Выбор технологий (E0-1), компоненты, данные, интерфейсы; инструкция создаётся по ИН-08 до начала этапа | Проектные решения в разделах 02–09 приведены к требованиям |
| 3. Кодирование | Проектные решения, среда, правила кода | Реализация компонентов и проверок; инструкция создаётся по ИН-08 | Компоненты собираются, проверки проходят, есть инструкция запуска |
| 4. Интеграция и испытания | Проверенные компоненты | Совместная сборка, проверка прав, отказов и повторов по `docs/10-testing.md` | Сценарии приращения выполняются; протоколы испытаний записаны |
| 5. Приёмка | Собранная редакция и протоколы | Демонстрация сценариев, выпуск базовой редакции (ИН-07) | Решение о принятии либо список доработок с номерами требований |

Каждый этап начинается с проверки, что для всех его работ есть инструкции
в [procedures.md](procedures.md). Отсутствующая инструкция создаётся первой задачей
этапа.

## 3. Направления и ответственные

| Направление | Основные материалы | Ответственный |
|---|---|---|
| Видение и предметная область | 01, 02 | Назначается по ОВ-01 |
| Интеграции: система задач и мессенджер | 04, 08, 11 | Назначается по ОВ-01 |
| Оповещения | 05 | Назначается по ОВ-01 |
| Граф | 06 | Назначается по ОВ-01 |
| Регламентные работы | 07, `maintenance/`, `requirements/maintenance-system.md` | Назначается по ОВ-01 |
| Проверка и испытания | 10 | Назначается по ОВ-01 |
| Правила работы команды | `process/` | Руководитель проекта |

После решения ОВ-01 столбец заполняется именами участников.

## 4. Приращения

| Приращение | Состав | Условие включения |
|---|---|---|
| 1. Основа учёта | E0–E3, E6; части E4 и E5 для реестра, владения и заявок | Доступ, переходы и выдача проверяются совместно |
| 2. Задачи, граф и оповещения | E7, E9, E8; соответствующие экраны E4 и E5 | Расчёт влияния E9 готов до объявления аварии E8 |
| 3. Расширение | E10, E11, E13; оставшиеся экраны | Используются проверенные функции предыдущих приращений |
| Сквозные работы | E12 и наблюдаемость | Выполняются с первого работающего компонента |

Оценки в [перечне задач](../backlog.md) предварительные и не являются календарным
обязательством. Состав первой демонстрации определяется по ОВ-02.

## 5. Среды

| Этап | Среда |
|---|---|
| 0–1 | Markdown, Git, хранилище GitHub, задачи и доска GitHub; любой текстовый редактор |
| 2 | Текстовые описания, схемы Mermaid или draw.io, искусственные данные |
| 3 | Локальная среда выбранного языка, учебные данные, испытательные заменители внешних систем; состав определяется E0-1 |
| 4–5 | Отдельная учебная среда с зафиксированными версиями компонентов; условия измерений — по ОВ-04 |

## 6. Контроль

Ход работ контролируется по доске на еженедельном разборе
([правила ведения задач](task-tracker.md), §6). Для каждой контрольной точки
выпускается базовая редакция (ИН-07). Сейчас выполняются только проверки
документов; сценарии в спецификациях не считаются пройденными испытаниями.
