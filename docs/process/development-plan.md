## 1. Назначение

План определяет этапы жизненного цикла, вход, работы, выход и условие завершения каждого этапа, интегральные процессы, порядок планирования и среду. На каждом этапе запланирована проверка. Этап завершён, когда выполнено условие в последней колонке таблицы этапов.

## 2. Этапы жизненного цикла

Переход к следующему этапу разрешён, когда выполнено условие завершения предыдущего. Откуда брать вход и куда класть выход, определяет ПКУ. Методы и исполнителей проверки определяет ПВР.

| Этап | Вход и условие начала | Работы | Выход: вид и объём | Проверка и условие завершения |
|---|---|---|---|---|
| 1. Постановка задачи | Пожелания заказчика с семинаров; анализ готовых решений. Начало: конспекты семинаров лежат в хранилище | Выделить проблему и задачи заказчика, сформулировать бизнес-требования, определить границы, описать 2–3 готовых решения, составить вопросы заказчику | Общая часть 2–3 страницы; разделы по направлениям по 0,5–1 странице: проблема, бизнес-требования, границы, готовые решения, вопросы заказчику | Формальная инспекция каждого раздела; анализ покрытия «задачи заказчика → бизнес-требования». Завершение: все разделы приняты, непокрытых задач нет |
| 2. Системные требования | Принятая постановка. Начало: постановка принята | Выделить системные требования, определить способ проверки каждого | Спецификация: номер, формулировка, источник (бизнес-требование), способ проверки | Формальная инспекция; анализ покрытия «бизнес-требования → системные требования». Завершение: спецификация принята, непокрытых бизнес-требований нет |
| 3. Требования к ПО | Принятые системные требования. Начало: спецификация принята | Детализировать системные требования до требований к ПО, описать испытания | Спецификация: номер, формулировка, ссылка на системное требование, описание испытания | Формальная инспекция; анализ покрытия «системные требования → требования к ПО» в обе стороны. Завершение: спецификация принята, покрытие полное в обе стороны |
| 4. Проектирование | Принятые требования к ПО. Начало: спецификация принята | Разработать архитектуру и требования низкого уровня | Архитектура и требования низкого уровня | Формальная инспекция. Завершение: проект принят |
| 5. Кодирование | Принятый проект. Начало: проект принят | Написать код и тесты | Код и тесты | Рассмотрение кода; анализ трассировки. Завершение: замечания устранены, трассировка полная |
| 6. Интеграция и испытания | Код. Начало: код и тесты прошли проверку этапа 5 | Собрать ПО, выполнить испытания | Сборка, протоколы испытаний | Испытание. Завершение: все испытания пройдены или несоответствия оформлены сообщениями о проблеме |

## 3. Интегральные процессы

Интегральные процессы выполняются на каждом этапе и не заменяют работ этапа.

| Процесс | Что обеспечивает на каждом этапе | Где описан |
|---|---|---|
| Управление конфигурацией | Хранение результатов, категории контроля, базовые версии | ПКУ |
| Верификация | Запланированная проверка выхода этапа, протокол или отчёт | ПВР |
| Управление изменениями | Сообщения о проблемах, анализ, запросы на изменение, повторная проверка | ПКУ |
| Контроль качества | Проверка формальной стороны: шаблон, реквизиты, именование, место хранения | Служба качества, СОД |

## 4. Планирование

1. Горизонт планирования: две недели.
2. Руководитель или заместитель составляет план при разборе задач: создаёт задачи в Issues, назначает исполнителей.
3. Задача записывается в Issues с входом, ожидаемым выходом и критерием готовности. Не записанное в задаче не считается заданием.
4. Объём задачи не больше трёх дней работы одного участника. Крупная работа делится на задачи.
5. Загрузка участников равная. Руководитель сверяет её при составлении плана.
6. Разбор задач проводится раз в неделю: состояние задач, блокировки, перераспределение.
7. Состояние готовности видно по задачам (открыта, на проверке, закрыта) и по состоянию документов.

## 5. Среда

| Назначение | Средство |
|---|---|
| Документы | Markdown |
| Хранение и версии | Git, хранилище на GitHub |
| Задачи, сообщения о проблемах, запросы на изменение | GitHub Issues |
| Рассмотрение изменений | Запросы на объединение на GitHub |

## 6. Ответственные за этапы

| Роль | Ответственность |
|---|---|
| Руководитель проекта | Соблюдение плана, распределение задач, переход между этапами |
| Заместитель руководителя | Те же обязанности в отсутствие руководителя |
| Автор | Выход этапа в своей задаче |
| Ведущий инспекции | Проведение запланированной формальной инспекции |
| Служба качества | Проверка формальной стороны выхода |

Условие перехода к следующему этапу проверяет участник, не являющийся автором выхода.
