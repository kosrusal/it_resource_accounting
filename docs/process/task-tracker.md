# Правила ведения задач

Редакция 0.1. Проект для утверждения командой.

Документ описывает, как команда планирует собственную работу. Выбор внешней
системы задач для будущей программы учёта — отдельный вопрос
[раздела 08](../08-task-tracker.md) и ОВ-03; эти правила его не решают.

## 1. Средство

Задачи команды ведутся в разделе `Issues` хранилища GitHub, их состояние —
на доске GitHub Projects «Учёт ИТ-ресурсов», связанной с хранилищем. Основание:
задачи находятся рядом с ветками и запросами на объединение, закрываются
автоматически при объединении, не требуют отдельных учётных записей
([раздел 08](../08-task-tracker.md), §8.3).

Задачи, обсуждения и решения в мессенджере не считаются зарегистрированными, пока
не перенесены в задачу или в открытые вопросы.

## 2. Карточка задачи

Задача создаётся кнопкой `New issue` по шаблону «Задача»
([`.github/ISSUE_TEMPLATE/task.md`](../../.github/ISSUE_TEMPLATE/task.md)).

| Поле | Правило заполнения | Пример |
|---|---|---|
| Название | Глагол в неопределённой форме и объект; до 80 знаков | «Сравнить решения для хранения графа» |
| Цель | Зачем нужен результат, одно-два предложения | «Выбрать способ хранения до проектирования E9» |
| Вход | Пути к файлам и разделам в `main`, номера ОВ и требований, внешние источники | `docs/06-graph.md` §6.3; ОВ-07 |
| Выход | Путь, куда кладётся результат, и его вид | Раздел §6.8 в `docs/06-graph.md`: таблица сравнения и предложение |
| Критерий готовности | Проверяемое условие приёмки результата | «Каждый вариант оценён по критериям §6.7; выбран один с обоснованием» |
| Инструкция | Номер инструкции, по которой выполняется работа | ИН-02 |
| Связи | Номера E, СТ, ТП, ОВ, связанные задачи | E9-3, СТ-ГР-02 |
| Исполнитель (`Assignees`) | Ровно один участник | — |
| Метки (`Labels`) | Одна метка направления и одна метка вида, см. §3 | `граф`, `анализ` |
| Этап (`Milestone`) | Контрольная точка курса, к которой нужен результат | «КТ-2. Системные требования» |

Задача без входа, выхода или критерия готовности остаётся в состоянии «Новые».
Объём задачи — не более трёх дней работы одного участника; большая работа делится
на задачи с отдельными выходами, общая задача связывается с ними списком
`- [ ] #NN` в описании.

## 3. Метки

| Группа | Метки |
|---|---|
| Направление | `видение`, `интеграции`, `оповещения`, `граф`, `регламентные-работы`, `проверка`, `процесс` |
| Вид работы | `постановка`, `анализ`, `требования`, `проектирование`, `код`, `испытание`, `правила`, `ошибка` |
| Особое состояние | `заблокировано` — работа не может продолжаться; в комментарии указаны причина и номер ОВ или задачи |

Новая метка добавляется изменением этого документа.

## 4. Состояния и переходы

| Состояние на доске | Условие входа | Кто переводит |
|---|---|---|
| Новые | Задача создана | Автоматически |
| Запланировано | Заполнены вход, выход, критерий, назначены исполнитель и этап | Ответственный за направление |
| В работе | Исполнитель создал ветку и начал работу | Исполнитель |
| На проверке | Открыт запрос на объединение, назначен проверяющий | Исполнитель |
| Готово | Запрос объединён, задача закрыта ссылкой `Closes #NN` | Автоматически |

Возврат «На проверке» → «В работе» происходит при итоге рассмотрения
`Request changes`. Отказ от задачи — закрытие с причиной `Close as not planned`
и комментарием, почему работа не нужна.

У исполнителя одновременно не более двух задач в состоянии «В работе».

## 5. Связь задачи с хранилищем

- Имя ветки начинается с номера задачи: `ruslan/27-task-rules`.
- Каждая фиксация заканчивается строкой `Задача: #27`.
- Запрос на объединение содержит `Closes #27`.
- Ответ на вопрос, найденный в ходе работы, заносится в задачу комментарием,
  а принятое решение — в документ результата или в `open-questions.md`.

## 6. Разбор доски

Команда разбирает доску на еженедельном собрании, ведущий — руководитель проекта:

1. Пройти «На проверке»: назначен ли проверяющий, нет ли задач старше двух дней.
2. Пройти «В работе»: есть ли `заблокировано`, кто снимает блокировку.
3. Пройти «Новые»: заполнить поля и перевести в «Запланировано» либо закрыть.
4. Сверить этапы с ближайшей контрольной точкой; перенос задачи на другой этап
   записывается комментарием с причиной.

Итог собрания — изменённые карточки; отдельный протокол не ведётся.

## 7. Перенос существующих работ

Задачи E0–E13 из [перечня работ](../backlog.md) переносятся на доску при начале
соответствующего этапа реализации, а не заранее. Номер E указывается в поле «Связи»
и в названии в квадратных скобках: «[E1-3] Проверка полей по описанию типа».
