# Стандарт именования и прослеживаемости

Редакция 0.1. Проект для утверждения командой.

## 1. Файлы и каталоги

| Материал | Правило | Пример |
|---|---|---|
| Раздел направления | `docs/NN-<тема>.md`; `NN` — следующий свободный номер из двух цифр, тема — латиница, строчные буквы, слова через дефис | `docs/11-messenger.md` |
| Подробные материалы направления | `docs/<направление>/<тема>.md` | `docs/maintenance/solutions-analysis.md` |
| Системные требования направления | `docs/requirements/<направление>-system.md` | `maintenance-system.md` |
| Требования к ПО направления | `docs/requirements/<направление>-software.md` | `tracker-software.md` |
| Правила команды | `docs/process/<тема>.md` | `task-tracker.md` |
| Шаблоны | `docs/process/templates/<что>.md` | `templates/review.md` |
| Изображения | `img/<документ>-<что>.png` рядом с документом | `docs/img/05-notifications-flow.png` |

Имена файлов и каталогов не содержат пробелов, кириллицы и заглавных букв.
Освободившийся номер раздела повторно не используется.

Каждый документ начинается с одного заголовка первого уровня и строки состояния:
«Редакция X.Y. Проект.» или «Редакция X.Y. Утверждено <дата>.».

## 2. Обозначения

| Обозначение | Что обозначает | Где выдаётся |
|---|---|---|
| `СТ-<обл>-NN` | Системное требование | `docs/requirements/*-system.md` |
| `ТП-<обл>-NN` | Требование к ПО | `docs/requirements/*-software.md` |
| `ОВ-NN` | Открытый вопрос | `docs/open-questions.md` |
| `E<n>-<m>` | Будущая задача реализации | `docs/backlog.md` |
| `ПР-NN` | Сквозной проверочный случай | `docs/10-testing.md` |
| `ИН-NN` | Инструкция к процессу | `docs/process/procedures.md` |
| `#NN` | Задача или запрос на объединение GitHub | GitHub, автоматически |
| `U<n>` | Пользовательский сценарий | `docs/01-vision.md` §1.6 |

Обозначения областей требований: `РЕЕ` — реестр; `ДСТ` — доступ; `ВЛД` — владение;
`ЗАЯ` — заявки; `УВД` — уведомления; `ГР` — граф; `РР` — регламентные работы;
`ИМП` — импорт; `ОТЧ` — отчёты; `НБ` — наблюдаемость; `КАЧ` — качество;
`ТР` — связь с системой задач; `СОО` — обмен служебными сообщениями.
Новая область добавляется изменением этой таблицы и таблицы
[стандарта требований](requirements-standard.md), §2.

Номер выдаётся один раз: удалённый номер не используется повторно, изменённое
требование сохраняет номер. Перед выдачей номера автор проверяет поиском по
хранилищу, что номер свободен.

## 3. Ветки

Формат: `<автор>/<номер задачи>-<тема>`.

- `<автор>` — постоянное короткое имя участника латиницей, одно для всех его веток
  (`sasha`, `ruslan`, `marsel`); перечень имён ведётся в описании доски проекта;
- `<номер задачи>` — номер задачи GitHub без знака `#`;
- `<тема>` — два-четыре слова латиницей через дефис.

## 4. Фиксации, задачи и запросы на объединение

| Объект | Правило |
|---|---|
| Первая строка фиксации | Глагол в неопределённой форме, до 72 знаков, без точки: «Уточнить СТ-ГР-03» |
| Последняя строка фиксации | `Задача: #NN` |
| Название задачи | Глагол в неопределённой форме и объект; для задач перечня работ — номер в квадратных скобках: «[E9-3] Обход подграфа» |
| Заголовок запроса на объединение | Как первая строка основной фиксации |

## 5. Программный код

Окончательные правила задаются задачей E0-1 после выбора языка (ОВ-03) и дополняют
этот раздел. До того действуют общие правила:

- идентификаторы в коде — английские слова без сокращений, кроме общепринятых
  (`id`, `url`); имена предметных сущностей совпадают с `docs/02-domain-model.md`
  (`Resource`, `ResourceRelation`, `Assignment`);
- стиль написания имён (регистр, разделители) — принятый для выбранного языка
  и проверяемый средством автоматической проверки оформления;
- комментарии и сообщения пользователю — на русском языке по `AGENTS.md`;
- проверка (тест) называется по проверяемому требованию или случаю и содержит его
  обозначение в имени или описании: `test_ST_REE_03_rejects_invalid_field`
  либо описание `"СТ-РЕЕ-03: отклоняет неверное поле"`;
- в коде не хранятся ключи и пароли; настройки берутся из переменных окружения (E0-6).

## 6. Прослеживаемость

Цепочка связей проекта:

```
Сценарий U / раздел направления
   → СТ-<обл>-NN (столбец «Источник» указывает раздел)
      → ТП-<обл>-NN (столбец «Источник» указывает СТ)
         → задача E / #NN (поле «Связи» указывает ТП или СТ)
            → ветка и фиксации (номер задачи)
               → проверка (имя или описание содержит СТ/ТП, случай ПР-NN)
```

Правила:

- ссылка указывает вверх по цепочке: требование — на источник, задача — на требование,
  проверка — на требование; обратные связи получаются поиском по обозначению;
- ссылка на раздел документа записывается как `NN §N.N`, например `07 §7.3`,
  а в тексте — ссылкой Markdown на файл;
- при изменении требования автор ищет его обозначение по хранилищу
  (`git grep "СТ-РЕЕ-03"`) и проверяет все найденные места;
- требование без проверки и проверка без требования отмечаются при рассмотрении
  как замечание.
