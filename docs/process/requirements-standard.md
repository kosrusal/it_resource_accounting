# Стандарт разработки требований

| Реквизит | Значение |
|---|---|
| Обозначение | СТТ |
| Версия | 1.0 |
| Состояние | Действует |
| Автор | Богомолов Арсений |
| Категория контроля | КК2 |

## 1. Назначение

Стандарт задаёт уровни требований, правила записи, обозначения, свойства и порядок разработки. Исполнитель, написавший или проверяющий требование, не имеет процедурных вопросов: ответ есть в этом документе. Свойства из раздела 5 образуют экспертную часть чек-листов формальной инспекции (ПФИ).

## 2. Уровни требований

| Уровень | Обозначение | Что описывает | Где записан | Источник |
|---|---|---|---|---|
| Бизнес-требования | БТ-<КОД>-NN | Возможность, которую получает заказчик. Без технических решений | Постановка задачи (ПЗ и разделы ПЗ-<КОД>) | Задача заказчика (З-NN) |
| Системные требования | СТ-<КОД>-NN | Что делает система. Обычный язык, понятный заказчику | Спецификация системных требований | БТ |
| Требования к ПО | ТП-<КОД>-NN | Поведение программы в терминах ПО | Спецификация требований к ПО | СТ |

Пример различия уровней. Система: «Система должна обеспечивать работу пользователей по защищённому каналу». ПО: «ПО должно принимать соединения по HTTPS», «ПО должно предъявлять сертификат», «ПО должно проверять пользователя через сервис авторизации». Конкретное решение допустимо на уровне системы, если оно задано заказчиком или внешним входом; тогда источник решения указывается в графе «Источник».

## 3. Запись требования

Требования записываются таблицей. Одна строка — одно требование.

| Номер | Требование | Источник | Проверка |
|---|---|---|---|

- Номер: <БТ|СТ|ТП>-<КОД>-NN, где КОД — код раздела, NN — порядковый номер внутри раздела и уровня.
- Номер присваивается один раз. Номер удалённого требования не используется повторно. При изменении формулировки номер сохраняется, изменение проходит по процедуре ПКУ.
- Источник: номер требования или задачи уровнем выше. Для БТ — З-NN.
- Проверка: способ (рассмотрение, анализ, испытание) и критерий успеха одной фразой. Для БТ графа не заполняется: постановка проверяется формальной инспекцией целиком.

## 4. Формулировка

| Уровень | Шаблон |
|---|---|
| БТ | «Система должна позволять <роль> <действие>» |
| СТ | «Система должна <действие, условие, результат>» |
| ТП | «ПО должно <действие, условие, результат>» |

Правила:

1. Одно требование описывает один наблюдаемый результат.
2. Роль, действие и условие названы явно. Значения заданы числом с единицей измерения.
3. Запрещены слова без критерия: «быстро», «удобно», «просто», «гибко», «и т. д.», «и другие», «при необходимости» без указанного условия, «по возможности», «как правило».
4. Требование не содержит способа реализации, если уровень не допускает его (раздел 2).
5. Одно понятие называется одним словом во всех требованиях.

## 5. Свойства требований

Требование принимается, если обладает всеми свойствами.

| Свойство | Что проверяется |
|---|---|
| Корректность | Не противоречит источнику; верно передаёт его смысл |
| Однозначность | Допускает одно толкование |
| Полнота | Описано всё необходимое: роль, действие, условие, результат. Источник покрыт требованиями целиком |
| Непротиворечивость | Нет конфликта с другими требованиями |
| Неизбыточность | Содержание не повторяется в другом требовании; нет требований без источника и без причины |
| Атомарность | Один наблюдаемый результат; требование нельзя разделить на независимые части |
| Проверяемость | Указана конечная процедура проверки с однозначным результатом «выполнено» или «не выполнено» |
| Реализуемость | Выполнимо в известных ограничениях: сроки, стоимость, среда, запреты заказчика |
| Трассируемость | Есть уникальный номер и ссылка на источник |
| Независимость от реализации | Описан результат, а не способ его получения (в пределах уровня) |

## 6. Трассировка

- Ссылка всегда ведёт вверх: ТП → СТ → БТ → З-NN. Ссылку проставляет автор требования.
- Обратную связь («что реализует это требование») не записывают вручную. Её строит анализ покрытия по ПВР.
- Каждое требование верхнего уровня покрыто хотя бы одним требованием нижнего. Каждое требование нижнего уровня имеет источник или помечено как производное.

## 7. Производные требования

Требование без источника наверху (появилось при разработке нижнего уровня) допустимо. В графе «Источник» записывается «Производное: <причина>». Автор передаёт его автору документа верхнего уровня, который решает, нужно ли изменить верхний уровень. Решение фиксируется в сообщении о проблеме или запросе на изменение (ПКУ).

## 8. Процесс разработки требований

| Шаг | Вход | Действие | Выход |
|---|---|---|---|
| 1 | Принятый документ верхнего уровня; задача в трекере (ПКУ) | Выделить элементы источника, каждому дать требования нижнего уровня по разделам 3–4 | Черновик документа версии 0.1 |
| 2 | Черновик | Автор проверяет свойства раздела 5, проставляет источник, способ проверки, помечает производные | Черновик, готовый к проверке |
| 3 | Черновик | Формальная инспекция по чек-листу (ПФИ); проверяет не автор | Протокол инспекции |
| 4 | Протокол с замечаниями | Автор исправляет замечания, версия 0.2; повторная инспекция новым протоколом | Новый протокол |
| 5 | Протокол без замечаний | Состояние «Принят», версия 1.0; документ переходит в КК1 | Принятый документ |
| 6 | Принятые документы двух уровней | Анализ покрытия вверх и вниз (ПВР) | Отчёт анализа покрытия |

Порядок работ, этапы и условия перехода задаёт ПЛР. Хранение и изменения — ПКУ. Методы и исполнители проверки — ПВР, ПФИ.
