# Стандарт на разработку требований к программному обеспечению

Редакция 0.2. Проект для утверждения командой. Ответственный: Богомолов Арсений.
Редакция 0.1 перенесена из ветки `sasha/requirements-draft`; изменения перечислены
в [листе изменений](#лист-изменений). Программное обеспечение далее обозначается «ПО».

## 1. Назначение и область применения

Стандарт задаёт порядок подготовки и проверки бизнес-требований, системных требований
и требований к ПО системы учёта ИТ-ресурсов.
Он применяется к новым требованиям и изменению существующих.
Языковые правила [AGENTS.md](../../AGENTS.md) действуют для всего текста.

Бизнес-требование описывает возможность, которую заказчик получает от системы
для устранения своей проблемы, без технических решений; бизнес-требования записываются
в постановке задачи. Системное требование описывает ожидаемую возможность или ограничение системы.
Требование к ПО уточняет наблюдаемое поведение программы. Проектное решение
описывает устройство реализации и хранится в документах 02–09 отдельно от требований.
Сценарий приёмки — последовательность действий с ожидаемым результатом; один
сценарий может проверять несколько требований. Источник — сценарий, предметное
правило или решение, из которого получено требование. Прослеживаемость — связь
требования с источником, уточняющими требованиями и проверкой.

## 2. Запись требования

Каждое требование занимает отдельную строку таблицы. Обязательные поля:

| Поле | Правило |
|---|---|
| Номер | `БТ-<раздел>-<номер>` для бизнес-требований, `СТ-<раздел>-<номер>` для системного уровня, `ТП-<раздел>-<номер>` для ПО; номер из двух цифр; правила выдачи — [стандарт именования](naming-and-tracing.md#2-обозначения) |
| Формулировка | «Система должна позволять <роль> <действие>» для бизнес-требований; «Система должна…» или «Программное обеспечение должно…» для остальных уровней; условие и один наблюдаемый результат |
| Источник | Для бизнес-требования — проблема заказчика из постановки задачи; для системного уровня — точные номера бизнес-требований, до принятия постановки задачи — документ и раздел; для ПО — точные номера системных требований |
| Проверка | Исходное условие, действие и ожидаемый результат либо предмет анализа; для бизнес-требований не заполняется: постановка задачи проверяется формальной инспекцией целиком |

Обозначения разделов: `РЕЕ` — реестр; `ДСТ` — доступ; `ВЛД` — владение;
`УВД` — уведомления; `ГР` — граф; `РР` — регламентные работы;
`ИМП` — импорт; `ОТЧ` — отчёты; `НБ` — наблюдаемость; `КАЧ` — качество;
`БЗ` — база знаний; `ПРВ` — права сотрудников в сервисах заказчика. Уже выданные номера сохраняются.
Разделы `ЗАЯ` — заявки, `ТР` — связь с внешней системой задач и `СОО` — обмен
служебными сообщениями закрыты 10.10.2026 вместе с исключением этих направлений
из проекта: новые номера в них не выдаются.
Удалённый номер повторно не используется; причина удаления остаётся в истории Git.

Параметры одной записи, например время и причина ошибки, могут перечисляться
в одном требовании, если проверяется создание или показ этой записи. Независимые
действия, например начало работ и рассылка уведомлений, разделяются.
Ожидаемый отказ описывается положительным действием: «должно отклонять переход…».
Слова «быстро», «удобно», «при необходимости» без определённого условия недопустимы.
Сокращение или предметный термин сначала определяется в спецификации либо её словаре.

Требование, у которого нет источника на верхнем уровне, является производным:
в поле «Источник» записывается «Производное: <причина>». Автор передаёт его автору
требований верхнего уровня задачей GitHub. Тот добавляет требование верхнего уровня,
и тогда его номер записывается в источник, либо принимает или отклоняет производное
требование; номер задачи с решением дописывается в поле «Источник».

Неопределённое значение заносится в [открытые вопросы](../open-questions.md).
Предложенное число явно помечается как предварительное. Требование, проверка
которого зависит от такого решения, не считается готовым к приёмке.

## 3. Процесс разработки

Среда: текстовые документы Markdown, Git для истории, GitHub для общего
хранилища и обсуждения изменений. Доступ к хранилищу и локальное чтение документов
являются условиями начала работы. Входы: постановка задачи, описание темы, сценарии 01,
предметная модель 02, решения 03–09 и зарегистрированные вопросы команды.
Выходы: изменённые спецификации, связи с источниками, способы проверки,
перечень нерешённых вопросов и запись изменения в Git.

| Шаг | Действие | Исполнитель | Условие завершения |
|---|---|---|---|
| 1 | Уточнить границу функции и её источник | Автор требований | Есть источник и сценарий применения |
| 2 | Выделить системные требования | Автор требований | Каждая строка описывает один результат без устройства реализации |
| 3 | Уточнить поведение ПО | Автор требований совместно с проектировщиком | Каждое требование ПО связано с системным |
| 4 | Определить проверку | Проверяющий | Заданы исходные данные и наблюдаемый результат |
| 5 | Сопоставить со смежными разделами | Автор и ответственный за смежный раздел | Противоречия устранены либо явно зарегистрированы |
| 6 | Проверить оформление и объединить изменение | Проверяющий и ответственный за объединение | Выполнены [ИН-05](procedures.md#ин-05-рассмотрение-результата) и порядок [плана управления конфигурацией](configuration-management.md) |

Автору нужно знать предметные сценарии и этот стандарт. Проектировщику — границы
компонентов и ограничения внешних систем. Проверяющему — методы проверки
требований и правила доступа. Ответственному за объединение — работу с Git
и порядок разрешения конфликтов. Пошаговый порядок — [ИН-03](procedures.md#ин-03-разработка-системных-требований)
и [ИН-04](procedures.md#ин-04-разработка-требований-к-по). Назначение конкретных
участников пока открыто: ОВ-01. В учебной команде роли могут совмещаться; авторство и проверка указываются
честно, без записи о несуществующем независимом рассмотрении.

## 4. Структура спецификаций и критерии проверки

Системная спецификация содержит назначение, границы, термины, функциональные
требования, ограничения качества, источники и открытые вопросы. Спецификация ПО
содержит введение, общий контекст, пользователей, ограничения, внешние интерфейсы,
функции и способы проверки. Тематический раздел может быть отдельным файлом,
если включён ссылкой в состав спецификации; повторять его требования не требуется.

| Свойство | Что проверяется |
|---|---|
| Корректность | Формулировка соответствует указанному источнику |
| Однозначность | Условия, участник, объект и результат имеют одно толкование |
| Полнота | Для заявленного объёма определены успешный исход, отказ и граничные условия; оставшиеся вопросы перечислены |
| Согласованность | Одинаковые состояния, права и сроки не противоречат друг другу в разных разделах |
| Отсутствие избыточности | Один результат не имеет нескольких независимых требований с одинаковым смыслом |
| Атомарность | Строка требует одного наблюдаемого результата |
| Изменяемость | Номер постоянен, изменение не требует переписывать несвязанные требования |
| Проверяемость | Проверка позволяет установить выполнение; условия измерений определены |
| Прослеживаемость | Источник и уточняющие требования существуют; бизнес-требование имеет системное уточнение, системное требование — уточнение ПО |
| Независимость от реализации | В системных требованиях отсутствуют таблицы хранения, библиотеки, код и адреса операций |

Пояснения и причины решений выносятся из формулировок в соседний текст.
Автоматическая проверка ссылок и номеров дополняет смысловое рассмотрение,
но не доказывает правильность предметных правил. Проект требований допускает
открытые вопросы; для согласованной редакции все вопросы её объёма должны быть
закрыты решением с автором и датой. Наличие файла или успешной проверки разметки
само по себе не означает согласования документа.

## 5. Анализ покрытия

Анализ покрытия подтверждает для пар уровней «бизнес-требования — системные требования»
и «системные требования — требования к ПО», что каждое требование верхнего уровня
уточнено на нижнем, а на нижнем уровне нет требований без источника. Анализ выполняет
участник, не являющийся автором требований: перед формальной инспекцией системных
требований, перед объединением требований к ПО с `main` и после изменения принятого
документа с требованиями.

По полю «Источник» исполнитель составляет таблицу «требование верхнего уровня —
уточняющие требования нижнего уровня» и выписывает замечания:

- требование верхнего уровня не указано ни в одном источнике;
- требование нижнего уровня не имеет источника и не отмечено как производное;
- источник ссылается на несуществующий или удалённый номер;
- у производного требования нет номера задачи с решением.

Результат — отчёт `АП-NN`: дата, исполнитель, идентификатор фиксации `main`, таблица
и замечания; каждое замечание регистрируется сообщением о проблеме в GitHub Issues.
Отчёт разовый и не имеет редакций; повторный анализ оформляется новым отчётом.
Место хранения и категорию контроля отчёта задаёт [план управления конфигурацией](configuration-management.md).
Покрытие полное, когда замечаний нет. Номера можно искать командой `git grep`
или программой проверки; её вывод исполнитель сверяет с документами.
